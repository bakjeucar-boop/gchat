## 문서 구성 판단

### 권장: 계획서를 기술서에 흡수한다

| 문서 | 역할 | 상태 |
|---|---|---|
| **기술서** | 단일 진실 원천. 현재 상태 + 근거 + 이력 | **신규 (계획서 흡수)** |
| **CLAUDE.md** | 에이전트 작업 지시서. 기술서에서 파생된 요약 | 유지 |
| ~~계획서~~ | — | 흡수 후 git 이력에만 보존 |

**근거.** 이 프로젝트에서 계획서 ↔ CLAUDE.md 동기화 차이가 거의 매 세션
발생했다 (부록 A 환경 정보, v1 제외 목록, 2.7.0 배치 원칙, mypy 언급).
세 번째 문서를 얹으면 "어느 게 맞는지" 문제가 세 배가 된다.
계획서는 "무엇을 만들 것인가"를 위한 문서였고 그 역할은 배포로 끝났다.
이제 필요한 것은 "무엇이 있고 어떻게 고치는가"다.

**단, 계획서에서 반드시 살릴 것** — 되돌린 결정과 실패한 시도. 이게 없으면
후임자가 같은 실험을 반복한다. 기술서 6장으로 독립시킨다.

### 문서 간 관계 규칙 (기술서 0장에 명시)

- 기술서가 유일한 진실 원천이다
- CLAUDE.md는 기술서 3·9장의 요약이며, 기술서를 고치면 함께 고친다
- 코드와 기술서가 어긋나면 **고치기 전에 먼저 보고**한다
  (이 프로젝트에서 쓴 방식이며 실제로 잘 작동했다)

## 기술서 목차

### 0장. 이 문서를 읽는 법
- 문서의 목적과 대상 독자
- **질문별 안내표** — "왜 이렇게 복잡한가?" → 3장 /
  "이걸 바꿔도 되나?" → 6장 / "고장났다" → 8장 /
  "새 기능을 넣고 싶다" → 10장
- 문서 간 관계와 갱신 규칙
- 용어 정의 (턴, 예산, 프리셋, 계열 등 이 프로젝트 고유 용어)

### 1장. 개요
- 무엇을 하는 앱인가 (개인용 AI 챗봇, 모델 3종)
- **의도적으로 없는 기능과 그 이유** — 영구 저장, 파일 첨부,
  웹 검색 그라운딩, 샘플링 파라미터
- 접속·저장소 정보
- 프로젝트 연혁 요약 (5일, 세션 9개, 커밋 40여 개)

### 2장. 빠른 시작
- 로컬 실행 (Python 3.12, 전역 pip, secrets.toml)
- 배포 (GitHub → Streamlit Cloud → Secrets)
- 최초 확인 순서

### 3장. 제약 조건 — 이 앱의 설계를 지배하는 것 ★
> **가장 먼저 읽어야 할 장.** 코드가 왜 이런 모양인지가 전부 여기서 나온다.

- Gemini API 무료 등급 한도 (RPM / TPM / RPD, 모델별)
- **TPM은 입력 토큰만 센다** — 근거와 확인 방법
- 모델별 능력 차이표 (샘플링 파라미터, thinking_level, 파일 입력)
- **Gemma는 왜 비상용인가** — TPM 16,000의 의미
- 생성 시간이 TPM보다 우세하다는 발견과 그 파급
- 유도되는 값과 고정된 값의 구분 (무엇을 상수로 두면 안 되는가)

### 4장. 아키텍처
- 모듈 구조와 **의존 계층** (아래에서 위로만 참조)
- 요청 한 번의 전체 흐름
  `fit_to_budget → precheck → record_sent → stream → record_usage_from`
- 상태 관리 (session_state에만 존재, 휘발성)
- 계층 위반을 막는 장치 (프로토콜, AST 검사)

### 5장. 모듈별 상세
각 모듈: 책임 / 공개 인터페이스 / 주의점 / 관련 테스트

- `models.py` — 단일 출처 테이블. **여기만 고치면 되는 것들**
- `state.py` — 대화·메시지 자료구조, 빈 대화 규칙
- `quota.py` — 한도 추적기. 창 기준 시각, 핸들 방식, 429 보정
- `context.py` — 토큰 추정, 예산 절단
- `client.py` — API 래퍼, 파라미터 번역, 예외 6종
- `export.py` — Markdown 생성
- `ui/` — 배치와 각 화면 요소
- `auth.py` — 비밀번호 게이트와 그 한계

### 6장. 설계 판단과 그 근거 ★
> **바꾸기 전에 읽어야 할 장.** "이미 해봤고 안 됐다"의 기록.

- 6.1 확정된 판단 — 무엇을 왜 그렇게 정했나
- 6.2 **되돌린 결정** (되돌린 이유가 핵심)
  - 설정 메뉴: 폐지 → 부활 (Streamlit 반응 속도, 조작 빈도)
  - 웹 검색 그라운딩: v1 포함 → 제외 (무료 티어 차단)
  - 대화 영구 저장: 포함 → 제외 (코드 비중)
  - 휘발성 경고: 상단 → 하단 → 제거
- 6.3 **여러 번 고친 값과 그 궤적**
  - 답변 길이 인스트럭션 3회 (상한만 주면 계속 짧아진다)
  - TPM 병목 경계 4회 (→ 결국 유도식으로)
  - Gemma 컨텍스트 예산·출력 상한
- 6.4 판단 보류 항목 (운영하며 정할 것)

### 7장. 실측 기록 — 이 프로젝트의 자산 ★
> 모델이 바뀌면 **다시 측정해야 하는 값들**. 측정 방법까지 남긴다.

- 측정 도구 (`scripts/probe_models.py`) 사용법
- 7.1 한도 관련 — TPM 계산 방식, 429 형식, quotaId
- 7.2 모델 스펙 — 컨텍스트/출력 상한, thinking_level 수용값
- 7.3 성능 — 생성 속도(모델별), 응답 모드별 지연
- 7.4 토큰 — 언어별 자/토큰 비율, 턴당 증가량
- 7.5 답변 길이 — 인스트럭션 유무별 출력 토큰
- **각 값에 "언제·어떻게 쟀는가"와 "언제 다시 재야 하는가"를 붙일 것**

### 8장. 트러블슈팅 사례집 ★
> 겪은 것만 적는다. 각 사례: 증상 / 원인 / 해법 / 재발 방지

- 8.1 조용히 잘못 도는 부류 (에러가 안 나서 찾기 어려운 것)
  - Gemma에 `thinking_config` 생략 → 사고 모드로 동작
  - 공백을 영어 상수로 세어 한국어 과소 추정
  - TPM 창에 `total_token_count` 사용 (추적기만 과하게 셈)
  - 창 기준 시각을 응답 시각으로 기록 (45초 밀림)
- 8.2 화면에 안 보이는 부류
  - 멈춤 버튼 / 계열 전환 확인 창이 화면 밖에 렌더링
- 8.3 Streamlit 특유의 것
  - 위젯 키 사후 대입 → `StreamlitAPIException`
  - 인증 후 `st.rerun()` 누락
  - 폼 없는 `text_input`의 리런마다 재평가
- 8.4 배포·플랫폼
  - 콜드 부팅 지연 (재부팅 반복이 오히려 방해)
  - `requirements.txt` / `pyproject.toml` 중복 경고
  - `git push`가 에이전트 셸에서 안 끝남
- 8.5 자동화로 판정할 수 없는 것 (사람만 확인 가능)
  - 클립보드, 시각적 배치, 문장 자연스러움

### 9장. 작업 원칙
> 새로 손대는 사람이 지켜야 할 규칙. CLAUDE.md의 출처.

- 값은 `models.py` 테이블에만 (하드코딩 금지)
- 바뀔 값은 상수가 아니라 유도로
- 즉시 반응 UI는 스크롤 위치에 기대지 않는다 (검증 조건 포함)
- 화면 문구 원칙 (개발 용어 금지, 라벨과 단위 일치)
- 오류를 조용히 삼키지 않는다
- 구조로 막는다 (주석으로 막지 않는다)
- 문서와 코드가 어긋나면 고치기 전에 보고

### 10장. 확장하려면

- 10.5 새 모델 추가 절차 — `models.py` 한 곳 + 실측 항목

- ★ 표시한 3·6·7·8장이 **이 문서의 핵심**이다. 나머지는 코드를 보면

- 되돌린 결정은 **지우지 말고 취소선 없이 그대로** 둔다.
  "이렇게 했다가 이래서 되돌렸다"가 정보다
