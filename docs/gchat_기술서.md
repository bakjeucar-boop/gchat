## 1장. 개요

## 2장. 빠른 시작

저장소 첫 화면의 `README.md` 는 이 절차를 짧게 담고 있다. 여기서는 **왜 그렇게 하는지**를
함께 적는다.

### 2.1 로컬 실행

필요한 것은 **Google AI Studio 의 API 키**(무료) 하나다.

```bash
git clone https://github.com/bakjeucar-boop/gchat.git
cd gchat
pip install -r requirements.txt
```

`.streamlit/secrets.toml.example` 을 `.streamlit/secrets.toml` 로 복사하고 값을 채운다.

```toml
GEMINI_API_KEY = "AI Studio 에서 발급한 키"
APP_PASSWORD = "20자 이상 무작위 문자열"
```

**이 파일은 커밋하지 않는다.** `.gitignore` 가 막고 있고, 백업 번들에도 들어가지
않는다 — 그래서 비밀번호는 따로 보관해야 한다 (11.2절).

```bash
streamlit run app.py
```

Python 3.12 를 쓴다. 가상환경 없이 전역 pip 로 설치하는 것이 이 프로젝트의 관행이다.
개발까지 하려면 `pip install -r requirements-dev.txt` (pytest · ruff · 문서 빌드용
markdown-it-py 포함).

### 2.2 배포

1. GitHub 저장소에 push
2. <https://share.streamlit.io> 에서 앱 생성
   - Main file path: `app.py`
   - Advanced settings → **Python version 3.12**
3. 같은 Advanced settings 의 **Secrets** 에 위 두 값을 등록한다.
   TOML 이므로 **따옴표가 필요하다**

무료 계정은 비공개 앱 1개, 공개 앱 무제한이다. 이 저장소가 공개인 이유이며,
접근은 비밀번호가 막는다.

### 2.3 최초 확인 순서

배포 직후 이 순서로 본다. 실패하면 어디가 문제인지 바로 갈린다.

| 순서 | 볼 것 | 실패하면 |

| 1 | 설치 로그에 streamlit · google-genai · tzdata 세 줄 | Python 버전 확인 |
| 2 | 첫 화면이 **비밀번호 입력** | `APP_PASSWORD` 가 안 읽힌 것 |

## 3장. 제약 조건 — 이 앱의 설계를 지배하는 것 ★

이 앱의 코드는 절반이 "모델과 대화하는 일"이고 절반이 **"한도를 넘지 않는 일"** 이다.
`quota.py`와 `context.py`가 존재하는 이유가 전부 이 장에 있다. 이 장을 건너뛰면
그 두 모듈이 과하게 복잡해 보인다.

### 3.1 무료 등급 한도

세 모델의 한도다. 값의 출처는 Google AI Studio 무료 등급이며, RPM과 TPM은
실호출로 확인했다 (7.1절).

| 표시명 | 모델 ID | 계열 | RPM | TPM | RPD |
|---|---|---|---|---|---|
| Gemini 3.5 Flash-Lite (기본) | `gemini-3.5-flash-lite` | gemini3 | 15 | 250,000 | 500 |
| Gemma 4 31B | `gemma-4-31b-it` | gemma4 | 30 | 16,000 | 14,400 |
| Gemma 4 26B A4B | `gemma-4-26b-a4b-it` | gemma4 | 30 | 16,000 | 14,400 |

**세 한도 중 어느 것이 먼저 걸리는지가 모델마다 다르다.** 이것이 설계의 출발점이다.

- **Gemini** — TPM 250,000은 사실상 무제한이다. 병목은 **RPD 500**, 즉 하루 500번의
  주고받음이다. 대화 중에는 느껴지지 않고 하루가 끝날 때 한 번 느껴진다.
- **Gemma** — RPD 14,400은 넉넉하다. 병목은 **TPM 16,000**이며, 이건 대화 도중에
  계속 느껴지는 종류다. 3.4절에서 자세히 다룬다.

이 장에서 계속 나오는 두 낱말을 먼저 정한다. **턴**은 사용자 질문 하나와 모델 답변
하나를 묶은 한 번의 주고받음이고, API 요청 한 번에 해당한다. **컨텍스트 예산**은
한 요청에 실어 보낼 대화 이력의 상한이며, 앱이 정하는 값이다 (모델의 컨텍스트
윈도우와 다르다 — 윈도우는 모델이 받아들일 수 있는 최대치이고, 예산은 한도를 지키려고
그보다 훨씬 낮게 잡은 우리 쪽 제한이다).

한도는 60초 슬라이딩 창으로 관리된다. 고정된 분 단위가 아니라 "지금부터 60초 전까지"의
합이므로, 창이 차면 가장 오래된 기록이 만료되는 시각까지만 기다리면 풀린다.
`quota.py`가 대기 시간을 추정하지 않고 **계산**할 수 있는 이유다.

### 3.2 TPM은 입력 토큰만 센다

이 앱에서 가장 중요한 단일 사실이다. 계획 단계의 전제는
"한 요청이 쓰는 토큰 = 컨텍스트 예산 + 최대 출력"이었고, **그 전제가 틀렸다.**

가장 직접적인 증거는 429가 스스로 밝히는 지표 이름이다.

```text
Quota exceeded for metric:
  generativelanguage.googleapis.com/generate_content_free_tier_input_token_count,
  limit: 16000, model: gemma-4-31b
Please retry in 19.917078239s.
```

`input_token_count`. 한도 16,000은 3.1절 표의 Gemma TPM과 일치한다.

세 갈래 실험이 이를 뒷받침한다 (측정 상세는 7.1절).

| 실험 | 조건 | 결과 |
|---|---|---|
| 큰 입력 / 작은 출력 | 입력 9,012토큰을 두 번 | 두 번째가 429. 입력만으로 16,000을 넘겼다 |
| 작은 입력 / 큰 출력 | 12개 병렬, 누적 출력 19,082토큰 | 직후 보낸 요청이 **통과** |
| 사고 켬 | 8개 병렬, 누적 사고 5,729토큰 | 직후 보낸 요청이 **통과** |

출력이 산입된다면 두 번째 실험에서 진작 429가 났어야 한다. 사고 토큰도 마찬가지다.

**직접 확인하는 방법.** 다음 명령이 위 세 실험을 그대로 재현한다.
토큰을 의도적으로 많이 쓰므로 RPD에 유의한다.

```bash
python scripts/probe_models.py tpm
```

출력에서 볼 것은 두 가지다. 429 본문의 지표 이름이 `input_token_count`인지,
그리고 큰 출력을 쏟아낸 직후의 확인 요청이 통과하는지.

**따라서 코드는 이렇게 되어 있다.**

- TPM 창에 넣는 값은 `prompt_token_count` **하나뿐**이다.
  `record_usage_from()`이 usage 객체에서 입력 토큰만 뽑으므로, 호출자가 실수로
  `total_token_count`를 넘기는 일 자체가 불가능하다 (구조로 막는다 — 9장).
- 최대 출력은 TPM 계산에 들어가지 않는다. 대신 **다음 턴의 입력**이 되어
  간접적으로 예산을 채운다. 출력 상한이 컨텍스트 예산과 무관하지 않은 이유다.

**단, 사고 토큰은 다른 곳에서 비용을 치른다.** TPM에는 안 잡히지만
`max_output_tokens` 예산에서는 그대로 차감된다. 출력 한도가 좁으면
사고만 하다 잘려 **빈 응답**이 나온다 (7.2절 · 8.1절 「Gemma에 `thinking_config`를 생략」).

### 3.3 모델별 능력 차이

| 항목 | Gemini 3.5 Flash-Lite | Gemma 4 (31B · 26B A4B) |
|---|---|---|
| 컨텍스트 윈도우 | 1,048,576 | 262,144 |
| 모델 최대 출력 | 65,536 | 32,768 |
| 앱 기본 컨텍스트 예산 | 32,000 | 9,000 |
| 앱 기본 최대 출력 | 4,096 | 2,048 (코딩 용도만 4,096) |
| `thinking_level` | `minimal` · `medium` · `high` | `minimal` · `high` (2단계) |
| 기본 응답 모드 | `medium` | `minimal` |
| 시스템 인스트럭션 | 지원 | 지원 |
| 파일 입력 | 지원 (v1 미사용) | 미지원 |
| 샘플링 파라미터 | 전달하지 않음 | 전달하지 않음 |

**샘플링 파라미터를 아예 쓰지 않는다.** `temperature` / `top_p` / `top_k` /
`candidate_count`는 어느 모델에도 보내지 않는다. Gemini 3.x가 이들을 폐기했고,
Gemma 4는 문서에 언급 자체가 없어 동작이 불확실하다. 조절해도 아무 일이 일어나지
않는 손잡이를 화면에 두는 것이 최악이므로 `ModelSpec`에 필드조차 두지 않았다.
그래서 **응답 성향을 바꾸는 유일한 수단이 `thinking_level`이다.**

**Gemma에는 `thinking_config`를 반드시 명시해야 한다.** Gemini는 생략하면
`minimal`로 동작하지만 Gemma는 **사고가 켜진 채로** 동작한다. 이 차이를 모르고
생략하면 짧은 출력 한도에서 사고가 예산을 다 먹고 빈 응답이 나온다.
`client.py`는 모든 요청에 이 값을 보낸다.

**Gemma에 `medium`을 보내면 400이다.** 전송 전에 걸러야 한다. 오류 메시지는
"이 모델은 사고 수준을 지원하지 않는다"고 말하지만 실제로는 `minimal`과 `high`가
정상 수용된다 — 문구가 오해를 부를 뿐 동작은 2단계가 맞다.

### 3.4 Gemma가 왜 비상용인가

Gemma는 대체 모델이 아니라 **비상용(fallback)** 이다. Gemini의 RPD가 소진됐거나
응답이 불안정할 때 임시로 쓰는 자리다. 이유는 TPM 16,000 하나다.

요청당 상한은 TPM의 90%로 잡는다 (여유 10%는 추정 오차와 서버 계산 차이를 위한 것).

| 모델 | TPM | 요청당 상한 (90%) |
|---|---|---|
| Gemini 3.5 Flash-Lite | 250,000 | 225,000 |
| Gemma 4 | 16,000 | 14,400 |

여기서 두 가지가 따라 나온다.

- **단일 요청이 14,400토큰을 넘으면 기다려도 소용없다.** 창이 비어도, 날짜가 바뀌어도
  통과하지 못한다. 그래서 `quota.py`의 판정 우선순위에서 `TOO_LARGE`가 가장 앞이다 —
  "잠시 뒤 다시 시도하세요"라고 안내하면 거짓말이 된다.
- **요청이 클수록 분당 횟수가 줄어든다.** 예산 9,000이면 분당 1.6회다.
  같은 계산이 Gemini에서는 32,000 예산에 분당 7회로, 사람이 타이핑하는 속도로는
  절대 닿지 않는다.

컨텍스트 예산 슬라이더의 상한이 14,400인 것도 여기서 나온다. 이 값은 UI에 적혀 있지
않고 `max_request_tokens()`가 테이블에서 유도한다.

**그런데 실사용에서는 이 병목이 거의 느껴지지 않는다.** 다음 절이 그 이야기다.

### 3.5 실제 병목은 TPM이 아니라 생성 시간이다

이 프로젝트에서 가장 중요한 관측이며, 계획 단계의 판단을 여러 개 뒤집었다.

Gemma로 6턴 대화를 실제로 주고받으며 잰 결과다 (7.4절).

| 항목 | 값 |
|---|---|
| TPM 대기 발생 | **0회** |
| 창 최대 사용률 | 29% (4,681 / 16,000) |
| 한 턴 생성 시간 | 22~25초 (출력 768 기준) |

**이유는 단순하다. 생성이 느려서 60초 창이 저절로 비워진다.** 한 요청이 끝나는 데
22초가 걸리면 60초 창에 많아야 2~3건이 겹친다. 사람이 답을 읽고 다음 질문을 쓰는
시간까지 더하면 TPM은 사실상 걸리지 않는다. TPM은 프로브처럼 **몰아 보낼 때만** 걸린다.

이 관측이 바꾼 것들이다.

- Gemma 기본 컨텍스트 예산을 3,000에서 **9,000**으로 올렸다. 3,000은 실제로 걸리지
  않는 병목을 피하려고 답변 길이를 희생하고 있었고, 그 결과 한 답변을 받으려면
  "계속"을 서너 번 입력해야 했다.
- 예산 슬라이더 옆 표시를 "예상 대기 시간"에서 **"유지되는 대화 턴 수"** 로 바꿨다.
  대기 시간은 경계 아래에서 항상 0이라 사용자에게 아무 정보도 주지 못한다.
- TPM이 병목이 되는 지점을 상수가 아니라 **계산으로** 정하게 됐다 (3.6절).

TPM이 실제 병목이 되려면 "TPM상 최소 간격 > 생성 시간"이어야 한다. 두 값이 만나는
지점이 경계이고, 생성 속도와 답변 길이가 그 지점을 결정한다.

### 3.6 무엇을 상수로 두면 안 되는가

값을 셋으로 나눠 다룬다. 이 구분이 `models.py`의 구조를 설명한다.

**1) 서버가 정하는 값 — 테이블에 상수로 둔다.**
RPM·TPM·RPD, 컨텍스트 윈도우, 모델 최대 출력. 우리가 정할 수 없고 API가 바뀌기 전에는
변하지 않는다. `models.py`의 `RateLimits`와 `ModelSpec`에만 적고, UI·client·quota는
참조만 한다.

**2) 측정으로 얻는 값 — 상수로 두되 측정일과 방법을 남긴다.**
생성 속도(초당 34.2토큰), 평균 답변 길이(1,301토큰), 토큰 추정 비율(한국어 1.6자 /
영어 3.5자). 모델이 바뀌면 다시 재야 하므로 7장에 측정 방법과 함께 기록한다.

**3) 앞의 값들에서 파생되는 값 — 절대 상수로 두지 않는다.**

가장 대표적인 것이 **TPM 병목 경계**다. 이 값은 프로젝트 진행 중 12,000 → 11,000 →
9,000으로 세 번 바뀌었는데, 매번 앞선 두 종류의 값이 갱신됐기 때문이다. 상수로 두는 한
같은 수정이 계속 반복된다. 그래서 식으로 바꿨다.

```text
경계 = (평균 답변 토큰 ÷ 초당 생성 토큰) × (요청당 상한 ÷ 60)
```

`models.tpm_boundary_budget()`이 이 식을 계산한다. 같은 식이 모델마다 다른 값을 낸다.

| 모델 | 현재 유도값 |
|---|---|
| Gemma 4 31B | 9,129 |
| Gemini 3.5 Flash-Lite | 142,653 |

평균 답변이 2,000토큰이면 Gemma 경계는 약 14,000으로 올라가고, 510토큰이면 2,877로
내려온다. **상수로는 표현할 수 없는 관계다.** 코드에는 이 숫자들이 어디에도 하드코딩되어
있지 않다.

같은 이유로 "유지되는 대화 턴 수"도 상수를 쓰지 않는다. 그 대화에 모델 응답이 2턴 이상
쌓이면 **실제 입력 증가폭의 평균**을 쓰고, 그 전에만 기본값 1,500토큰을 쓴다
(`context.tokens_per_turn()`). 사용자가 시스템 인스트럭션을 길게 바꾸면 표시가 스스로
따라온다.

### 3.7 이 제약이 코드의 어디로 갔는가

| 제약 | 코드 | 절 |
|---|---|---|
| TPM은 입력만 센다 | `quota.QuotaTracker` — 창에 `prompt_token_count`만 기록 | 3.2 |
| 60초 슬라이딩 창 | `quota` — 대기 시간을 추정이 아니라 만료 시각으로 계산 | 3.1 |
| 단일 요청 14,400 초과는 못 푼다 | `quota` 판정 우선순위에서 `TOO_LARGE`가 최상위 | 3.4 |
| 예산을 넘는 대화 | `context.fit_to_budget()` — 오래된 user/model 쌍부터 제외 | 3.4 |
| 한도 값은 한 곳에만 | `models.py` 테이블. UI·client·quota는 참조만 | 3.6 |
| 파생값은 유도한다 | `models.tpm_boundary_budget()`, `context.tokens_per_turn()` | 3.6 |
| Gemma는 `thinking_config` 필수 | `client.build_config()`가 항상 명시 | 3.3 |
| Gemma에 `medium` 금지 | `models.resolve_thinking_level()`이 전송 전에 되돌림 | 3.3 |

## 4장. 아키텍처

이 장은 코드에 적혀 있지 않은 것만 다룬다. 함수 시그니처와 자료구조 필드는
코드를 보면 되고, 코드는 바뀌지만 이 문서는 안 바뀐다.

### 4.1 의존 계층

모듈은 한 방향으로만 참조한다. 아래가 위를 부르지 않는다.

```text
        app.py            ← 배선만. 순서가 곧 화면 배치다
          │
        ui/               ← streamlit 위젯을 직접 다루는 유일한 계층
          │                 chat.py · sidebar.py · controls.py · export_ui.py
    ┌─────┴─────┐
  export      client      ← 바깥(API·파일)과 닿는 층
    │           │
    └─────┬─────┘
        quota             ← 한도 판정. client 를 부르지 않는다 (4.5절)
          │
       context            ← 토큰 추정과 예산 절단
          │
        state             ← 대화·메시지·설정 자료구조
          │
       models             ← 값의 단일 출처. 아무것도 import 하지 않는다
```

`auth.py`는 이 사슬 밖에 있다. 인증 게이트 하나뿐이고 다른 모듈을 참조하지 않는다.

**규칙 하나로 요약하면 "값은 아래에서 위로만 흐른다"이다.** `models`는 무엇도
import하지 않고, `ui`는 무엇이든 import한다. 이 방향이 지켜지면 아래층 모듈은
streamlit 없이 시험할 수 있다 — 실제로 테스트 205건 중 `ui`를 띄우는 것은 없다.

계층을 나눈 실질적 이득은 **모듈 하나를 통째로 갈아끼울 수 있다**는 것이다.
다만 **아래로 갈수록 교체 비용이 커진다.** `models`는 최하층이라 값 하나만 바꿔도
위 전부가 영향을 받고, `export`는 위쪽 잎이라 통째로 들어내도 다른 모듈이 모른다.

**예외가 하나 있다 — `client`다.** 중간층인데도 갈아끼우기 쉽다. `quota`가 그것을
import하지 않고 **모양만 요구**하기 때문이다 (4.5절). 다른 SDK로 바꾸든 HTTP를 직접
치든 그 모양만 맞추면 된다. 계층 규칙만 보면 중간층 교체는 비싸야 하는데, 그 비용을
줄이려고 넣은 것이 Protocol이다.

모듈별 구체적인 영향 범위는 5장 각 절의 "고칠 때 함께 볼 곳"에 있다.

### 4.2 요청 한 번 — 정상 흐름

사용자가 질문을 보내면 다섯 단계를 거친다. **순서가 중요하다.**

```text
사용자 입력
  │
  ├─ 1. context.fit_to_budget()      예산에 맞게 이력을 자른다
  │                                   (원본은 지우지 않고 표시만 한다)
  ├─ 2. quota.precheck()             보낼 수 있는지 판정한다
  │                                   TOO_LARGE / DAILY_EXHAUSTED / WAIT / OK
  ├─ 3. quota.record_sent()          창에 기록하고 **핸들**을 받는다
  │                                   시각은 이 시점으로 고정된다
  ├─ 4. client.stream()              스트리밍으로 답을 받는다
  │                                   조각은 화면과 session_state 양쪽으로
  └─ 5. quota.record_usage_from()    핸들의 값만 실측으로 갱신한다
                                      시각은 3에서 정해진 그대로다
```

**왜 이 순서인가.**

- 1이 2보다 먼저인 이유는 **판정 대상이 잘라낸 뒤의 크기**이기 때문이다. 자르기 전
  크기로 판정하면 보낼 수 있는 요청을 막는다.
- 3이 4보다 먼저인 이유는 창의 기준 시각이 **전송 시각**이어야 하기 때문이다.
  Gemma는 답 하나에 30~45초를 쓰므로, 응답 시각으로 기록하면 창이 통째로 밀린다
  (8.1절 「한도 창의 기준 시각이 응답 시각으로 밀림」).
- 5가 추정치를 실측으로 **대체**한다. 1의 추정은 문자 수 기반이라 오차가 있고,
  서버가 돌려준 `prompt_token_count`가 진짜다.

### 4.3 실패 경로

정상 흐름만 알면 절반이다. 갈라지는 지점이 셋 있다.

```text
                  ┌─ TOO_LARGE ──────→ 전송 안 함. 모델 전환 안내
                  │                     (기다려도 안 풀린다)
  2. precheck ────┼─ DAILY_EXHAUSTED ─→ 전송 안 함. 다른 모델 추천
                  │
                  ├─ WAIT ────────────→ 전송 안 함. 남은 시간 안내
                  │
                  └─ OK ──────────────→ 3 으로

  4. stream ──────┬─ 429 RateLimited ─→ 추적기를 **서버 기준으로 보정**
                  │                     하고 대기 안내
                  ├─ 503 ─────────────→ 다른 문구 + 재시도 버튼
                  ├─ 400 / 키 오류 ───→ 원문 JSON 없이 안내만
                  └─ 멈춤 버튼 ───────→ 스크립트가 통째로 중단됨 (아래)
```

**세 경로의 성격이 다르다.**

**precheck가 막을 때** — 아직 아무것도 보내지 않았다. 사용자 입력은 대화에 남아
있으므로 "다시 시도"로 같은 입력을 재전송할 수 있다. 네 판정을 구분하는 이유는
사용자가 할 일이 다르기 때문이다. `TOO_LARGE`는 기다려도 날짜가 바뀌어도 풀리지
않으므로 "잠시 뒤 다시"라고 안내하면 거짓말이 된다 — 그래서 판정 우선순위에서
가장 앞이다 (3.4절).

**429가 올 때** — 우리 추적기가 OK라고 했는데 서버가 거절한 경우다. **이것을 비정상
상태로 다루지 않는다.** 추적기는 추정이고 서버가 최종 진실이므로, 429를 받으면
서버가 준 대기 시간으로 추적기를 보정한다. 대기 시간이 없는 429도 실재하므로
(7.1절) 그때는 자체 계산값을 쓰고 "서버가 알려주지 않았다"고 함께 알린다.

**멈춤을 눌렀을 때** — 다른 둘과 종류가 다르다. 멈춤 버튼은 리런을 일으켜 **실행 중인
스크립트를 통째로 중단시킨다.** 예외가 아니라 실행 자체가 사라지므로 4단계 뒤의
정리 코드가 아예 돌지 않는다. 그래서 두 가지 장치가 있다.

- 스트림 조각을 흘려보내면서 `session_state`에도 쌓는다. 중단돼도 남는다
- 다음 실행의 **화면을 그리기 전에** 그 조각을 대화에 붙인다. 그린 뒤에 붙이면
  다음 조작 때까지 안 보인다 (8.2절 「중단분이 다음 조작 전까지 안 보임」)

5단계가 돌지 않으므로 **그 요청의 창 기록은 추정치로 남는다.** 실측으로 대체되지
않을 뿐 기록 자체는 3단계에서 이미 남았으므로 한도 추적은 어긋나지 않는다.

### 4.4 상태 관리

**모든 상태는 `st.session_state`에만 있다.** 서버 파일시스템에도, 브라우저 저장소에도
쓰지 않는다. 이것은 제약이 아니라 판단이었고 (6.2절 「대화 영구 저장」), 결과가 셋 있다.

- **새로고침하면 대화가 사라진다.** 12시간 무접속 후 앱이 잠들었다 깨어날 때도
  마찬가지다. 그래서 Markdown 내보내기가 v1에 들어갔다
- **한도 추적기도 함께 사라진다.** 다시 접속하면 창이 비어 있는 상태에서 시작하지만,
  서버 쪽 한도는 그대로이므로 첫 요청이 429를 맞을 수 있다. 4.3절의 "429는 정상
  경로"가 여기서도 쓰인다
- **동시성 문제가 없다.** 세션 하나가 자기 상태만 본다

대화 자료구조는 `state.py`에 있고 순수 파이썬 dataclass다. streamlit에 매여 있지
않으므로 테스트에서 그대로 만들어 쓸 수 있다.

### 4.5 계층을 지키는 장치

**문제.** `quota`는 API 응답에서 두 가지를 읽어야 한다 — 429의 대기 시간과 usage의
입력 토큰. 그런데 그 두 값을 만드는 곳은 `client`이고, `client`는 `quota`보다 **위층**
이다. 그대로 import하면 순환이 생긴다.

**해법.** `quota`는 `client`를 부르지 않고 **모양만 요구한다.**

```python
@runtime_checkable
class UsageLike(Protocol):
    input_tokens: int
```

`client.Usage`가 이 모양을 만족하므로 그대로 넘길 수 있고, `quota`는 그 클래스의
존재를 모른다. 429 정보도 같은 방식이다.

**이 구조가 준 것.**

- `quota` 테스트가 `client`를 import하지 않는다. 가짜 객체로 시험한다
- **client를 통째로 갈아끼워도 quota는 그대로다.** 다른 SDK로 바꾸든 HTTP를 직접
  치든, 그 모양만 맞추면 된다
- 계층 위반이 **컴파일 시점이 아니라 설계 시점에** 막힌다

`tests/test_quota.py`에 `client의_Usage와_모양이_맞는다`가 있어 두 쪽이 어긋나면
실패한다. 모양으로 연결한 대가로 정적 결합이 사라졌으니, 그 대신 테스트가 계약을
지킨다.

**한계도 있다.** 이 방식은 `quota` ↔ `client` 한 곳에만 적용돼 있다. 다른 계층 위반은
사람이 보는 수밖에 없으며, 자동 검사는 없다.

## 5장. 모듈별 상세

각 모듈에 네 가지를 적는다 — 책임 / **주의점** / 고칠 때 함께 볼 곳 / 관련 절.
주의점이 이 장의 핵심이다. 나머지는 코드를 읽으면 나온다.

### 5.1 `models.py` — 값의 단일 출처

**책임.** 세 모델의 능력·한도·기본값을 한 테이블에 담고, 그 테이블에서 유도되는
값(요청당 상한, TPM 경계, 용도별 출력 상한)을 계산해준다. 이 모듈이 없으면 같은
숫자가 UI·client·quota에 흩어진다.

**여기만 고치면 되는 것들.** 이 프로젝트에서 "값은 테이블 한 곳에"를 지킨 이득이
구체적으로 이것이다.

| 하고 싶은 일 | 고칠 곳 | 함께 할 일 |
|---|---|---|
| 새 모델 추가 | `MODELS` 튜플에 `ModelSpec` 하나 | `probe specs`·`probe thinking`으로 실측 먼저 (10.5절) |
| 한도 변경 (등급 상향 등) | 해당 `RateLimits` | 없음. 요청당 상한과 경계가 따라 움직인다 |
| 기본 컨텍스트 예산·출력 상한 조정 | `default_context_budget` / `default_max_output` | 없음 |
| 기본 응답 모드 변경 | `default_thinking_level` | 테스트가 계획값과 대조하므로 함께 갱신 |
| 답변 길이 문구 변경 | 인스트럭션 상수 | **다시 측정할 것** (6.3절) |
| 용도 프리셋 문구 변경 | `PURPOSE_INSTRUCTIONS` | 없음 |

**주의점.**

- **UI·client·quota는 이 테이블의 값을 하드코딩하지 않는다.** 슬라이더 상한도
  `max_request_tokens()`로 유도하고, 대기 경고 기준선도 `tpm_boundary_budget()`으로
  계산한다. 숫자를 다른 파일에 적는 순간 이 모듈의 존재 이유가 사라진다
- **샘플링 파라미터 필드를 두지 않는다.** 필드가 있으면 언젠가 누가 채우고, 채우면
  UI에 나오고, UI에 나오면 사용자가 조절했다고 믿는다. 실제로는 아무 일도 일어나지
  않는다 (3.3절)
- `default_max_output`은 **일상 상한이 아니라 안전장치**다. 답변 길이를 실제로 정하는
  것은 시스템 인스트럭션이다 (7.5절)
- 가격 필드는 `None`이다. API가 단가를 주지 않아 손으로 채워야 한다 (6.4절)

**고칠 때 함께 볼 곳.** 이 모듈은 최하층이라 모든 것이 딸려 있다.
`tests/test_models.py`가 테이블을 실측값·계획값에 고정하므로, 값을 바꾸면 거기서
먼저 실패한다. 그 실패가 "다른 곳도 봐야 한다"는 신호다.

**관련 절.** 3.1·3.3(값의 출처) · 3.6(무엇을 상수로 두면 안 되는가) ·
8.1절 「모델 스펙을 문서만 보고 잘못 적음」

### 5.2 `state.py` — 대화와 설정

**책임.** 대화·메시지·설정 자료구조와 `session_state` 접근을 담당한다. streamlit에
매이지 않은 순수 함수를 최대한 분리해 두었다.

**주의점.**

- **빈 대화는 최대 하나다.** 새 대화 버튼도, 모델 변경도, 현재 대화가 비어 있으면
  새로 만들지 않는다. 이 규칙이 없으면 목록이 빈 대화로 찬다
- 확정된 모델(`active_model_id`)과 드롭다운 값(`ui_model_id`)이 **분리돼 있다.**
  계열 전환 확인에서 취소를 누르면 드롭다운만 되돌려야 하기 때문이다. 둘을 하나로
  합치면 취소가 동작하지 않는다
- 제목은 **자르지 않고 보관**하고 표시할 때만 줄인다. 사용자가 직접 지정한 제목은
  줄이지 않는다
- 시스템 인스트럭션은 용도 프리셋에서 조합된다. 커스텀으로 넘어갈 때는 **지금 문구를
  그대로 남겨** 이어서 고칠 수 있게 한다

**고칠 때 함께 볼 곳.** `context`(메시지를 읽는다) · `client`(대화를 요청으로 바꾼다) ·
`export`(대화를 문서로 바꾼다) · `ui` 전체. `Message`에 필드를 더하면 이 넷이 모두
영향권이다.

**관련 절.** 4.4(상태가 세션에만 있는 구조) · 6.2절 「대화 영구 저장」

### 5.3 `quota.py` — 한도 추적

**책임.** 60초 창과 일일 카운터를 관리하고, 보내기 전에 판정하고, 429가 오면 서버
기준으로 보정한다. 이 모듈이 없으면 앱은 한도를 모르고 429를 맞을 때까지 보낸다.

**주의점.**

- **창에 넣는 값은 입력 토큰뿐이다.** 그런데 이건 규칙이 아니라 구조다 —
  `record_usage_from()`이 usage 객체에서 자기가 입력 토큰을 뽑으므로 다른 값을 넣을
  자리가 없다. 이 설계의 이유는 8.1절 「TPM 창에 `total_token_count`를 넣을 뻔함」
- **기록의 시각은 전송 시각이다.** `record_sent()`가 핸들을 돌려주고 보정은 그
  핸들의 값만 바꾼다. 보정 시점에 시각이 갱신되면 창이 밀린다
- **대기 시간은 추정이 아니라 계산이다.** 필요한 만큼의 토큰 기록이 만료되는 시각을
  찾아낸다. 그래서 "약 30초"가 아니라 정확한 초가 나온다
- 판정 우선순위가 `TOO_LARGE → DAILY_EXHAUSTED → WAIT → OK`인 데는 이유가 있다.
  각 판정마다 사용자가 할 일이 다르고, 기다려서 풀리지 않는 것을 먼저 알려야 한다
- **추적기가 OK인데 429가 오는 것은 정상이다.** 추정과 서버 계산이 다를 수 있고,
  서버가 최종 진실이다

**고칠 때 함께 볼 곳.** `client`(429 정보와 usage의 모양 — 4.5절의 Protocol) ·
`ui/chat.py`(판정 결과를 문구로 옮기는 곳) · `ui/sidebar.py`(게이지). 테스트가
가짜 시계로 시나리오 7종을 돌리므로, 시간과 관련된 수정은 거기서 먼저 확인된다.

**관련 절.** 3.1·3.2(왜 이렇게 복잡한가) · 3.4(요청당 상한) ·
6.3(경계를 유도로 바꾼 경위) · 8.1절 「TPM 창에 `total_token_count`를 넣을 뻔함」 ·
8.1절 「한도 창의 기준 시각이 응답 시각으로 밀림」

### 5.4 `context.py` — 토큰 추정과 예산 절단

**책임.** 문자 수로 토큰을 추정하고, 예산을 넘으면 오래된 턴부터 컨텍스트에서 뺀다.
경계 근처에서만 실제 `count_tokens`를 호출한다.

**주의점.**

- **추정 상수는 안전한 쪽으로 잡혀 있다.** 한국어 1.6자/토큰, 영어 3.5자/토큰 모두
  실측보다 토큰을 조금 많게 센다. 과소 추정은 429를 부르고 과대 추정은 조금 일찍
  자를 뿐이다. 이 방향을 바꾸지 말 것 (7.4절)
- **공백은 직전 문자의 분류를 따른다.** 공백을 일괄로 영어 상수에 넣으면 한국어를
  과소 추정한다 (8.1절 「공백을 영어 상수로 세어 한국어를 과소 추정」)
- **절단은 삭제가 아니다.** 컨텍스트에서 빠진 메시지도 화면과 내보내기에는 그대로
  남고, 표시만 세운다. 예산을 다시 올리면 되돌아온다
- 시스템 인스트럭션은 예산에서 **먼저** 차감되고 항상 유지된다
- 실호출은 예산 경계 ±15% 안에서만 한다. 매번 부르면 요청 수가 두 배가 된다
- 턴당 토큰은 상수가 아니라 그 대화의 실측 평균이다 (3.6절)

**고칠 때 함께 볼 곳.** `quota`(추정치를 판정에 넘긴다) · `ui/chat.py`(절단 안내
문구) · `ui/controls.py`(슬라이더의 턴 수 표시).

**관련 절.** 3.6(유도되는 값) · 7.4(토큰 실측) · 6.3(턴당 토큰 추정의 궤적)

### 5.5 `client.py` — API 래퍼

**책임.** 앱의 설정을 SDK 파라미터로 번역하고, 스트리밍으로 답을 받고, 오류를 여섯
종류로 구분해 올린다.

**주의점.**

- **`thinking_config`를 항상 보낸다.** 생략하면 Gemma는 사고가 켜진 채로 동작한다
  (8.1절 「Gemma에 `thinking_config`를 생략」)
- **지원하지 않는 사고 수준은 보내기 전에 거른다.** Gemma에 `medium`을 보내면 400이다
- **샘플링 파라미터와 `tools`를 다루지 않는다.** 테스트가 소스에 그 이름이 등장하는지
  까지 검사한다 — 실수로 되살리는 것을 막기 위해서다
- **요청의 마지막 턴이 `model` 역할로 끝나면 안 된다.** Gemini 3.x가 400을 낸다.
  `to_contents()`가 잘라낸다
- 스트리밍은 제너레이터이고, 토큰 수와 `finish_reason`은 **다 받은 뒤에야** 나온다.
  그래서 결과 객체를 미리 넘겨 사후에 채우는 형태다
- 오류 여섯 종을 나눈 이유는 **사용자가 할 일이 다르기 때문**이다. 429는 기다리고,
  503은 다시 시도하고, 키 오류는 설정을 고친다. 원문 JSON은 화면에 내지 않는다

**고칠 때 함께 볼 곳.** `quota`(429 정보와 usage의 모양 — 4.5절) ·
`ui/chat.py`(예외별 화면 문구) · `models`(파라미터 번역의 출처).

**관련 절.** 3.3(모델별 능력 차이) · 7.1·7.2(오류 형태와 스펙 실측) ·
8.1절 「Gemma에 `medium`을 보내 400」

### 5.6 `export.py` — Markdown 내보내기

**책임.** 대화를 Markdown 문서로 만든다. 이 모듈이 영구 저장을 대신한다 (6.2절).

**주의점.**

- **본문을 다시 감싸지 않는다.** 모델 답변에는 코드 블록이 들어 있으므로, 인용이
  필요한 곳에서는 더 긴 울타리를 골라 중첩 펜스가 깨지지 않게 한다
- **서버 파일시스템에 쓰지 않는다.** 문자열을 만들어 다운로드 버튼에 넘길 뿐이다
- 시각은 KST로 변환한다. 배포 서버는 UTC로 돈다 (11장)
- 토큰 수를 "토큰"이라고 정확히 쓴다. 화면에서는 단위를 주장하지 않는 이름을 쓰지만
  (8.4절), 내보낸 파일은 나중에 다시 읽는 기록이라 정확한 이름이 낫다

**고칠 때 함께 볼 곳.** `state`(대화 구조) · `ui/export_ui.py`(버튼).

**관련 절.** 6.2절 「대화 영구 저장」 · 8.4(화면과 문서의 어휘가 다른 이유)

### 5.7 `ui/` — 화면

**책임.** streamlit 위젯을 직접 다루는 유일한 계층. `chat`(대화·입력·오류),
`sidebar`(목록·게이지·설정), `controls`(설정 내용과 배지), `export_ui`(내보내기 버튼).

**주의점.** 이 계층의 함정은 대부분 8장에 사례로 있다.

- **즉시 반응해야 하는 UI를 본문 흐름에 그대로 얹지 않는다.** 대화가 길어지면
  사용자는 늘 문서 맨 아래에 있어 본문 상단은 화면 밖이다. 고정하거나 조작한 위젯
  옆에 그린다 (9장, 8.2절)
- **위젯이 그려진 뒤 그 키에 대입하면 예외가 난다.** 되돌리기가 필요한 조작은
  `on_click` 콜백으로 처리한다 (8.3절)
- **상태를 바꾸는 일은 그리기 전에 끝나야 한다.** streamlit은 위에서 아래로 한 번
  훑는다 (8.2절 「중단분이 다음 조작 전까지 안 보임」,
  8.3절 「인증에 성공해도 비밀번호 칸이 남음」)
- **화면 문구에 개발 용어를 쓰지 않는다.** 라벨을 바꿀 때는 표시되는 숫자의 단위가
  라벨과 맞는지 확인한다 (8.4절)
- 버튼 라벨의 글자 크기는 `button`이 아니라 그 안쪽 `p`에 걸어야 한다 (7.7절)

**고칠 때 함께 볼 곳.** `app.py`(배선 순서가 곧 배치다). 이 계층에는 자동 테스트가
없으므로 **브라우저에서 눈으로 확인**해야 하고, 배치 관련이면 **메시지 20개 이상 쌓인
긴 대화**에서 봐야 한다 (12장).

**관련 절.** 6.2절 「설정 컨트롤의 자리」 · 8.2 · 8.3 · 8.4 전체

### 5.8 `auth.py` — 비밀번호 게이트

**책임.** 앱 전체를 비밀번호 하나로 막는다. 목적은 보안이 아니라 **API 키 남용으로
인한 과금 방지**다.

**주의점.**

- **`st.form`을 쓰는 것이 핵심이다.** 키 없는 `text_input`은 리런마다 같은 값을
  돌려주므로, 반환값을 그 자리에서 판정하면 제출과 무관한 리런에서도 실패 횟수가
  올라간다 (8.3절 「키 없는 `text_input`이 리런마다 재평가됨」)
- 인증 성공 시 `st.rerun()`이 필요하다. 안 그러면 이미 그려진 폼이 화면에 남는다
- 비밀번호를 `session_state`에 저장하지 않는다. 비교는 상수 시간 함수로 한다
- **이건 문 잠금이지 암호화가 아니다.** 앱 URL은 공개이고 서버는 계속 떠 있다

**고칠 때 함께 볼 곳.** `app.py`(게이트 통과 전에는 아무것도 그리지 않는다).

**관련 절.** 8.3절 「인증에 성공해도 비밀번호 칸이 남음」 · 12장 검증 1번

## 6장. 설계 판단과 그 근거 ★

**바꾸기 전에 읽는 장이다.** 여기 적힌 것들은 대부분 한 번 다른 방향으로 가봤다가
돌아온 것이며, 되돌린 이유가 결론보다 중요하다.

8장과의 경계는 이렇다.

- **8장** — 잘못돼서 고친 것. 의도대로 동작하지 않았다
- **6장** — 틀리지 않았는데 바꾼 것. 의도대로 동작했지만 그 의도가 원하는 결과를
  내지 못했다

같은 대상이 두 장에 나뉘어 들어간 경우가 있다. 계열 전환 확인이 그렇다 —
**확인 절차를 두기로 한 판단은 이 장**이고, 그 확인 창이 화면 밖에 그려져 안 보였던
것은 8.2절 「계열 전환 확인 창이 안 뜬다」다. 대화 목록 제목 크기도 마찬가지로,
어느 크기로 할지는 6.3절이고 CSS가 글자에 닿지 않았던 것은 8.3절이다.

### 6.1 확정된 판단

되돌린 적이 없고 앞으로도 유지할 것들이다. 각 판단의 근거를 함께 적는다.

| 판단 | 근거 |
|---|---|
| 샘플링 파라미터를 아예 전달하지 않는다 | Gemini 3.x가 폐기했고 Gemma는 문서에 언급조차 없다. 조절해도 아무 일이 없는 손잡이가 최악이다 (3.3절) |
| 응답은 항상 스트리밍한다 | Gemma는 답 하나에 30~45초가 걸린다 (7.3절). 다 만들어 한 번에 주면 멈춘 것처럼 보인다 |
| 오류를 조용히 삼키지 않는다 | 무엇이 왜 실패했는지 보인다. 다만 원본 JSON은 접기 안으로 (8.4절) |
| 모델별 값은 `models.py` 테이블에만 쓴다 | 하드코딩이 흩어지면 새 모델 추가가 전수 검색이 된다 (3.6절) |
| 계열이 바뀌면 새 대화를 시작한다 | 컨텍스트 예산이 32,000 ↔ 9,000으로 달라져 절단이 불가피하다. 절단된 채 어색하게 잇는 것보다 끊는 편이 명확하다 |
| 내보내기는 `download_button`만 쓴다 | 서버 파일시스템에 쓰지 않는다. 배포 환경에서 그 파일은 사라지고, 남으면 그게 더 문제다 |
| 비밀번호는 게이트 하나로 끝낸다 | 목적이 "보안"이 아니라 **API 키 남용으로 인한 과금 방지**다. 그 목적에는 충분하다 |
| Gemma는 `minimal` 고정이다 | 사고를 켜면 사고 745 + 답변 1,300 = 2,045로 상한 2,048에 부딪혀 잘린다 (7.3절). 상한을 올리면 턴당 컨텍스트가 불어나 비상용이라는 성격과 충돌한다 |
| Gemini 기본은 `medium`이다 | 응답 모드는 한도에 영향이 없고 대가는 시간뿐이다. 바닥값을 기본으로 둘 이유가 없다 (7.3절) |

### 6.2 되돌린 결정

**무엇이 판단을 뒤집었는지**를 유형으로 표시한다.

| 유형 | 뜻 |
|---|---|
| 실측 | 재보니 가정이 틀렸다 |
| 실사용 | 만들어 써보니 체감이 달랐다 |
| 외부 제약 | 우리가 정할 수 없는 것이 발견됐다 |
| 사용자 결정 | 범위·우선순위를 다시 정했다 |

| # | 결정 | 처음 | 되돌린 뒤 | 유형 |
|---|---|---|---|---|
| 1 | 설정 컨트롤의 자리 | 사이드바 → 입력창 위 컨트롤 바 | 사이드바 "설정"으로 복귀 | 실사용 |
| 2 | 사이드바 항목 순서 | 새 대화 → 설정 → 목록 → 게이지 | 새 대화 → 목록 → 내보내기 → 삭제 → 게이지 → 설정(접힘) | 실사용 |
| 3 | 제목 편집 방식 | popover | 인라인 | 실사용 |
| 4 | 메시지 복사 방식 | `st.code` 펼쳐서 아이콘 클릭 | 버튼 한 번 클릭 | 실사용 |
| 5 | 웹 검색 그라운딩 | v1 포함 | v1 제외 | 외부 제약 |
| 6 | 삭제 되돌리기 지속 시간 | 5초 후 자동 소멸 | 다음 조작까지 유지 | 외부 제약 |
| 7 | 휘발성 경고 | 사이드바 상단 고정 | 화면에서 제거 (문구 상수만 보존) | 사용자 결정 |
| 8 | Gemma 기본 컨텍스트 예산 | 3,000 | 9,000 | 실측 |
| 9 | 예산 슬라이더 옆 표시 | 예상 대기 시간 | 유지되는 대화 턴 수 | 실측 |
| 10 | Gemini 기본 응답 모드 | `minimal` | `medium` | 실측 |
| 11 | 대화 영구 저장 | SQLite·Supabase 어댑터로 구현 | v1 제외, 세션에만 보관 | 사용자 결정 |

유형별로 세면 **실사용 4 · 실측 3 · 외부 제약 2 · 사용자 결정 2**다.

**만들기 전에 정한 것 중 뒤집힌 열한 건 가운데 일곱 건이 "재보거나 써봐야 알 수 있는
것"이었다.** 문서를 아무리 읽어도 나오지 않는 종류다 — Gemma의 TPM이 실사용에서
걸리지 않는다는 것(8번)은 여섯 턴을 실제로 주고받아야 나왔고, popover가 무겁다는
것(1번)은 만들어서 눌러봐야 나왔다. 외부 제약 두 건도 문서에는 없었다. 무료 등급에서
검색 도구가 막혀 있다는 사실(5번)은 호출해봐야 알 수 있었고, Streamlit에 시간 기반
자동 소멸 수단이 없다는 것(6번)도 만들려다 알았다.

**후임자에게 주는 함의는 이것이다.** 새 판단을 세울 때 먼저 물어야 할 것은
"이건 재볼 수 있나, 써볼 수 있나"다. 잴 수 있으면 재고 나서 정하는 편이 빠르다.
이 프로젝트에서 문서만 보고 정한 값은 거의 예외 없이 한 번씩 고쳐졌다.

아래는 각 결정의 상세다.

**1. 설정 컨트롤의 자리 (실사용)**

세션 4에서 "설정 메뉴를 둘 만큼 항목이 없다"고 판단해 없애고, 모든 컨트롤을 입력창 위
컨트롤 바(popover)에 몰아넣었다. 세션 5 실사용에서 두 가지가 드러났다.

- **대화 중에 모델을 바꿀 일이 거의 없다.** 시작할 때 정하고 끝까지 간다. 입력창 바로
  위라는 가장 좋은 자리를 거의 안 쓰는 컨트롤이 차지하고 있었다
- **popover는 열고 고르고 닫을 때마다 리런이 걸려 체감이 무겁다.** 자주 안 쓰는
  컨트롤일수록 이 비용이 아깝다

되돌린 뒤 배치는 **조작은 사이드바, 표시는 입력창 위 배지**로 나뉜다. 배지에는 조작
요소를 넣지 않는다. 그 사이 시스템 인스트럭션과 예산 슬라이더가 들어와 항목이 넷이
됐으므로, "설정 메뉴를 둘 만큼 항목이 없다"는 전제 자체도 더 이상 참이 아니었다.

**2. 사이드바 항목 순서 (실사용)**

하루 써보니 실제로 만지는 것은 새 대화·대화 목록·내보내기·삭제였고, 설정은 처음 한 번
정하면 거의 안 건드렸다. 자주 쓰는 것을 위로 올리고 설정을 맨 아래 접었다.

**3. 제목 편집 방식 (실사용)**

popover는 여는 데 리런이 한 번 더 들고, 라벨 옆에 아래꺾쇠가 붙어 보기에도 나빴다.
1번과 같은 이유다 — Streamlit에서 popover는 "가벼운 상호작용"이 아니다.

**4. 메시지 복사 방식 (실사용)**

처음에는 `st.code`로 원문을 펼쳐 보이고 Streamlit이 붙여주는 복사 아이콘을 쓰게 했다.
동작은 했지만 **펼치고 다시 누르는 두 단계**였다. 실사용에서 불편하다는 요청을 받아
`navigator.clipboard.writeText()`를 쓰는 한 번 클릭으로 바꿨다.

이 결정에는 위험이 있었다. 자동화로는 성공을 확인할 수 없어(8.7절) **사람이 눌러볼
때까지 되는지 몰랐다.** 실제 판정까지 네 세션이 걸렸고, HTTPS 배포 환경에서 통과했다.
안 됐다면 `st.code` 방식으로 되돌리는 것이 대비책이었다.

**5. 웹 검색 그라운딩 (외부 제약)**

v1에 넣기로 하고 설계까지 했으나, 측정에서 **무료 등급은 검색 도구를 붙이면 모델과
무관하게 즉시 429**를 받는다는 것이 드러났다. 같은 시각 같은 모델에 도구만 빼면
정상 응답하므로 모델 단위 한도 소진이 아니라 검색 전용 할당량이 0인 것이다.

켤 때마다 실패하는 스위치를 두는 것이 최악이므로 v1에서 뺐다. 코드는 `tools`
파라미터를 아예 다루지 않는다. 되살리려면 무엇이 달라져야 하는지는 10.3절에 있다.

**6. 삭제 되돌리기 지속 시간 (외부 제약)**

"5초 후 자동으로 사라진다"로 설계했으나 **Streamlit에는 시간 기반 자동 소멸 수단이
없다.** 상호작용이 없으면 화면을 다시 그리지 않기 때문이다. 억지로 만들려면 타이머와
강제 리런이 필요한데, 그 비용이 기능의 값어치보다 크다. "다음 조작까지 유지"로 바꿨고
실사용에서 불편이 없었다.

**7. 휘발성 경고 (사용자 결정)**

대화가 세션에만 존재한다는 경고를 상시로 띄우기로 했다. 자리를 두 번 옮긴 끝에
(상단 고정 → 내보내기 버튼 바로 위) 화면에서 뺐다. 매번 보는 사람에게는 정보가 아니라
소음이었다. **문구 상수는 코드에 남겨 뒀다** — 되살릴 때를 위해서다.

**8. Gemma 기본 컨텍스트 예산 (실측)**

3,000은 "TPM 16,000이 대화를 조인다"는 전제에서 나온 값이다. 세션 4 실사용에서 그
전제가 뒤집혔다 — 여섯 턴 내내 TPM 대기가 0회였고 창 사용률은 최대 29%였다 (3.5절).
3,000은 **실제로 걸리지 않는 병목을 피하려고 답변 길이를 희생하고 있었고**, 그 결과
한 답변을 받으려면 "계속"을 서너 번 입력해야 했다. 9,000으로 올렸다.

**9. 예산 슬라이더 옆 표시 (실측)**

처음에는 "이 예산이면 요청 사이에 몇 초 기다린다"를 보이려 했다. 8번과 같은 실측에서
**기본 설정의 대기 시간은 항상 0**이라는 것이 드러났다. 항상 0인 숫자는 정보가 아니다.
대신 "유지되는 대화 턴 수"를 보이고, 경계를 넘어설 때만 대기 경고를 덧붙인다.

**10. Gemini 기본 응답 모드 (실측)**

`minimal`이 API 기본값이라 그대로 뒀는데, 측정해보니 **응답 모드는 한도에 전혀 영향이
없었다.** 세 모드의 입력 토큰이 54로 같았다 (TPM은 입력만 센다 — 3.2절). 대가는
응답 시간 2.2초뿐이고 Gemini는 출력 상한이 넉넉해 사고 토큰이 답변 자리를 빼앗지도
않는다. 바닥값을 기본으로 둘 이유가 없어 `medium`으로 올렸다.

같은 측정이 Gemma에서는 반대 결론을 냈다 (6.1절). 같은 실측 한 번이 두 모델에 서로
다른 판단을 준 사례다.

**11. 대화 영구 저장 (사용자 결정)**

초판 설계에는 저장소 프로토콜 하나와 SQLite·Supabase 두 어댑터, 그리고
conversations / messages 테이블 스키마가 있었다. **세션 하나가 통째로 저장소
구현이었고** 배포 세션에 원격 어댑터를 붙이는 일정이었다.

"영속성이 코드에서 비중이 높다면 제외해 달라"는 요청으로 v1에서 뺐다. 그 자리에
**Markdown 내보내기가 신설**됐고, 전체 세션 수도 일곱에서 여섯으로 줄었다.
기능 하나를 뺀 것이 아니라 앱의 성격을 바꾼 결정이다.

**이 결정이 낳은 결과가 오늘의 동작이다.** 12시간 무접속이면 앱이 잠들고 깨어날 때
대화가 전부 사라진다. 고장이 아니라 이 판단의 결과이며, 그래서 내보내기가 v1에
들어갔다 — 남기고 싶으면 내려받는다. 되살리는 길은 10.1절에 있다.

**근거 주의.** 계획서 초판은 커밋된 적이 없어 저장소에 흔적이 없다. 위 설계 내용은
사용자 기록에 따른 것이다. 저장소에서 확인되는 것은 결과뿐이다 — v1 제외 목록과
`export.py`의 존재.

### 6.3 여러 번 고친 값과 그 궤적

여섯 개의 값이 두 번 이상 바뀌었다. **되돌린 값을 지우지 않고 궤적 그대로 남긴다** —
최종값만 보면 왜 그 값인지 알 수 없기 때문이다.

| 값 | 궤적 | 고친 횟수 |
|---|---|---|
| Gemma 최대 출력 | 2,048 → 768 → 1,536 → 2,048 → 4,096 → 2,048 (코딩만 4,096) | 5 |
| TPM 병목 경계 | 12,000 → 11,000 → 9,100 → 유도식 | 3 |
| 답변 길이 인스트럭션 | 없음 → 상한만 제시 → 상한과 하한을 함께 | 2 |
| 턴당 토큰 추정 | 600 → 1,750 → 용도별 상수 → 대화 실측 평균 | 3 |
| Gemma 기본 예산 | 3,000 → 9,000 | 1 |
| 대화 목록 제목 크기 | 16px → 14px → 12px → 10px → 11px | 4 |

**Gemma 최대 출력 — 왜 다섯 번이나 고쳤나**

이 값이 대표 사례다. 궤적을 따라가면 매번 다른 이유였다.

| 값 | 왜 바꿨나 |
|---|---|
| 2,048 (초안) | 문서를 보고 잡은 잠정값 |
| **768** | TPM은 입력만 센다는 실측 후. 출력은 TPM을 쓰지 않지만 **다음 턴의 입력이 되어** 예산을 채운다. 768이라야 예산 3,000에서 "약 5턴"이 성립한다 |
| **1,536** | 예산을 9,000으로 올린 뒤 768이 너무 좁아졌다. 한 답변에 "계속"을 서너 번 쳐야 했다 |
| **2,048** | 목표 답변 길이가 1,000~1,500토큰인데 상한 1,536은 목표 상단과 너무 가까워 잘림이 생겼다 |
| **4,096** | 코딩 답변의 코드가 끊긴다는 실사용 신고 |
| **2,048 (코딩만 4,096)** | 범용 답변까지 4,096을 허용할 이유가 없다. 용도별로 나눴다 |

**다섯 번 고친 이유는 이 값이 다른 세 값에 매여 있었기 때문이다** — 컨텍스트 예산,
목표 답변 길이, 용도. 셋 중 하나가 움직일 때마다 이 값도 따라 움직여야 했다.
마지막에야 "용도별로 다른 값"이라는 형태를 찾았고, 그 뒤로는 안 고쳤다.

**최종값 2,048만 보면 아무것도 알 수 없다.** 왜 4,096이 아닌지(범용에 그만큼이 필요
없어서), 왜 1,536이 아닌지(목표 상단과 가까워 잘려서)는 궤적에만 있다. 이것이 되돌린
값을 지우지 않는 이유다.

**TPM 병목 경계 — 어떻게 끝냈나**

같은 값을 세 번 고쳤다는 점에서는 위와 같지만, 끝낸 방식이 다르다.

| 값 | 왜 바꿨나 |
|---|---|
| 12,000 | 생성 속도를 초당 30토큰으로 가정해 계산 |
| 11,000 | 생성 속도를 실측하니 33.1이었다 |
| 9,100 | 평균 답변 길이가 1,301토큰으로 안착하면서 경계가 내려왔다 |
| **유도식** | 상수를 버리고 계산으로 바꿨다 |

**세 번 모두 "입력이 바뀌어서" 고쳤다.** 경계는 생성 속도와 답변 길이에서 나오는
값인데, 그 둘이 측정될 때마다 경계도 다시 계산해야 했다. 상수로 두는 한 이 수정은
끝나지 않는다.

네 번째에 식으로 바꿨다.

```text
경계 = (평균 답변 토큰 ÷ 초당 생성 토큰) × (요청당 상한 ÷ 60)
```

**그 뒤로는 한 번도 고치지 않았다.** 답변 길이가 바뀌면 경계가 알아서 따라오고,
모델마다 다른 값이 같은 식에서 나온다 (7.6절). 앞의 최대 출력 사례와 대비된다 —
그쪽은 마지막에 **형태**를 바꿔서 끝났고(단일 값 → 용도별 값), 이쪽은 **종류**를
바꿔서 끝났다(상수 → 유도).

값을 세 번 이상 고치고 있다면 다음 수정을 하기 전에 물어볼 만하다.
**이 값은 무엇에서 나오는가. 그것을 식으로 쓸 수 있는가.**

**답변 길이 인스트럭션 — 세 번의 측정**

문구를 두 번 고쳤고, 매번 같은 질문 3개로 측정했다 (7.5절).

| 문구 | 평균 출력 | 잘림 |
|---|---|---|
| 없음 | 1,221토큰 (968~1,542) | 3턴 중 1턴 |
| 1차 — 상한만 제시 | **435토큰** | 없음 |
| 2차 — 상한과 하한을 함께 | **1,301토큰** (1,144~1,447) | 없음 |

1차 문구는 "2,000자 이내"였고 그것은 약 1,250토큰에 해당한다. 결과는 435토큰,
**지시의 38%**였다. 문구가 작동하지 않은 것이 아니라 너무 잘 작동했다 —
"간결하게"와 "불필요한 서론·요약·반복을 넣지 않는다"에 강하게 반응했다.

2차에서 목표를 범위로 주고 **"너무 짧게 줄이지 말고"** 라는 하한을 넣자 목표 대역에
들어왔고, 편차도 절반으로 줄었다(574 → 303).

인스트럭션 없이도 평균은 비슷하다(1,221 대 1,301). 다른 것은 **편차와 잘림**이다.
지금 이 문구의 역할은 답을 짧게 만드는 것이 아니라 **길이를 목표 대역에 묶어 두는
것**이다.

**문구를 고칠 때 조심할 것.** 상한만 주면 결과가 그 아래 어디에 놓일지 알 수 없다.
그리고 문구 변경은 컴파일도 테스트도 되지 않으므로, 고쳤으면 **다시 재야 한다.**
1차 개정 때 재지 않았다면 "지시대로 2,000자 이내에 들어왔다"고 만족했을 것이다.

**턴당 토큰 추정 — 상수의 수명**

600 → 1,750 → 용도별 상수 → 대화 실측 평균. 앞의 두 값은 "출력 상한을 매 턴 다
채운다"는 가정에서 나왔고, 시스템 인스트럭션이 들어오면서 그 가정이 깨졌다. 실측에서
턴당 증가가 인스트럭션 유무에 따라 445와 1,080으로 갈렸다 (7.4절).

TPM 경계와 같은 방식으로 끝냈다 — 상수를 버리고 **그 대화의 실제 증가폭 평균**을 쓴다.
모델 응답이 2턴 이상 쌓이기 전에만 기본값 1,500을 쓴다.

**대화 목록 제목 크기 — 네 번 고친 다른 이유**

16px → 14px → 12px → 10px → 11px. 앞의 사례들과 달리 이 값은 **판단이 흔들려서가
아니라 측정이 틀려서** 여러 번 고쳐졌다. 14px과 12px 단계에서는 CSS가 실제 글자에
닿지 않아 화면이 바뀌지 않았다 (8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」).
10px까지 내려간 뒤 11px로 한 단계 올린 것만이 실제 취향 조정이다.

궤적을 남기는 것은 같지만, 이 경우 **읽는 사람이 알아야 할 것은 "왜 11px인가"가 아니라
"측정 대상을 잘못 고르면 네 번을 고쳐도 안 바뀐다"** 는 쪽이다.

### 6.4 판단 보류 항목

정하지 않은 채로 둔 것들이다. 정보가 부족해서이며, 운영하면서 채운다.

| 항목 | 왜 보류인가 | 무엇이 있으면 정할 수 있나 |
|---|---|---|
| RPD 리셋 시각 | 하루 이상 관찰이 필요해 세션 안에서 확인할 수 없었다. 문서 근거는 태평양 자정이고 코드도 그 기준이다 | 실사용 중 일일 한도 429를 만났을 때의 `quotaId`와 `retryDelay` |
| 가격 필드 | API가 단가를 돌려주지 않는다 (7.2절). 현재 `None`이라 비용 표시가 비어 있다 | 공개 가격표를 보고 손으로 입력. 무료 등급만 쓰면 필요 없다 |
| 턴 수 표시의 체감 정확도 | 계산은 맞지만 사용자가 느끼는 것과 맞는지는 써봐야 안다 | 며칠 실사용 후의 느낌 |
| 멈춤 후 "계속"의 자연스러움 | 기능은 동작한다. 중단 지점이 문장 중간일 때 이어붙인 글이 매끄러운지는 읽어야 안다 | 실사용 판정 (8.7절) |
| "코딩은 Gemini 권장" 안내 | 실측에서 Gemma도 잘리지 않아 근거가 없었다 (7.5절). 다만 Gemma는 4.4배 느리다 | 느려서 불편하다는 실사용 피드백이 쌓이면 |
| 승급 후보 2건 | 8.8절의 보류 항목 — 문서 동기화 검사와 라벨-단위 검사 | 문서 동기화는 계획서 이동이 끝난 뒤, 라벨-단위는 오탐을 줄일 방법이 생기면 |

**보류를 보류로 적어 두는 것도 판단이다.** 근거 없이 정하면 다음 사람이 그 값을
근거 있는 것으로 오해하고 그 위에 무언가를 쌓는다.

## 7장. 실측 기록 ★

문서로만 알던 값과 실제가 여러 번 달랐다. 이 장은 **실호출로 확인한 값만** 담는다.
각 값에 측정일·측정 방법·다시 재야 하는 시점을 붙인다. API 모델은 바뀌므로
"언제 잰 값인가"가 값 자체만큼 중요하다.

### 7.0 측정 도구와 원본 기록

측정 도구는 `scripts/probe_models.py` 하나다. 서브커맨드로 나뉜다.

```bash
python scripts/probe_models.py sdk         # SDK 표면 (API 호출 없음)
python scripts/probe_models.py list        # 사용 가능한 모델 목록
python scripts/probe_models.py specs       # 모델별 컨텍스트·출력 상한
python scripts/probe_models.py tokens      # count_tokens — 언어별 자/토큰
python scripts/probe_models.py stream      # 스트리밍 동작
python scripts/probe_models.py thinking    # thinking_level 수용값
python scripts/probe_models.py turns       # 한국어 대화의 턴당 토큰 증가
python scripts/probe_models.py tpm         # TPM 산정 기준 (3.2절의 세 실험)
python scripts/probe_models.py grounding   # 웹 검색 그라운딩 가용성
python scripts/probe_models.py modes       # 응답 모드별 토큰·시간·잘림
```

두 번째 인자로 파일 경로를 주면 결과 JSON을 그 파일에도 쓴다.
`tpm`과 `turns`, `modes`는 토큰을 의도적으로 많이 쓰므로 RPD에 유의한다.

**원본 관측 기록: `docs/archive/api_findings.md`**. 429 응답 전문, 실험별 조건과 원시 수치가
그 파일에 있다. 이 장은 그것을 재가공한 요약이며, 세부가 필요하면 원본을 본다.
이 원본은 2026-08-13자 관측에서 동결됐고 갱신하지 않는다.

**재측정을 쌓는 규칙.** 모델이 바뀌어 다시 측정하면 원본을 고치지 않고
`docs/archive/api_findings_YYYYMMDD.md`로 새 파일을 만든다.
**이 장은 항상 최신값만 유지한다.** 옛 값은 이 장에서 지우고 날짜별 원본에만 남긴다.
7장의 존재 이유가 "모델이 바뀌면 다시 재야 하는 값"이므로, 여기에 낡은 값과 새 값이
함께 있으면 목적을 잃는다.

### 7.1 한도

| 값 | 결과 | 측정일 | 방법 |
|---|---|---|---|
| TPM은 입력 토큰만 센다 | 확정 | 2026-08-13 | 세 갈래 실험 (`probe tpm`) — 3.2절 표 |
| 사고 토큰은 TPM에 산입되지 않는다 | 확정 | 2026-08-13 | 사고 5,729토큰 포함 8건 병렬 직후 요청 통과 |
| Gemma TPM 한도 | 16,000 | 2026-08-13 | 429 본문의 `limit: 16000` |
| Gemini RPM 한도 | 15 | 2026-08-13 | 작은 요청 18개 (성공 14 / 429 4)에서 `quotaValue` 확인 |
| TPM은 60초 슬라이딩 창이며 복구된다 | 확정 | 2026-08-13 | 429 후 70초 대기 → 11건 성공, 다시 70초 → 8건 성공 |
| 429에 `retryDelay`가 있다 | 두 곳에 형태가 다름 | 2026-08-13 | `RetryInfo`는 초 단위 문자열, message 본문은 소수점까지 |
| `retryDelay`가 없는 429도 있다 | 확정 | 2026-08-13 | 그라운딩 429에는 `Help` 링크뿐 |
| `quotaId`로 한도 종류를 구분할 수 있다 | 확정 | 2026-08-13 | 분당 한도와 일일 한도가 서로 다른 문자열로 온다 |
| RPD 리셋 시각 | **미측정** | — | 하루 이상 관찰이 필요해 세션 안에서 불가 |

**다시 재야 하는 시점.** API 키 등급이 바뀔 때, 또는 무료 등급 정책이 개편될 때.
`probe tpm` 하나로 위 항목 대부분이 다시 나온다.

RPD 리셋 시각은 아직 열려 있다. 문서 근거는 태평양 시간 자정이고 코드도 그 기준으로
계산하지만, 실측하지 못했다. 실사용 중 일일 한도 429를 만나면 `quotaId`와 `retryDelay`를
기록해 확정한다.

|---|---|---|---|
| 컨텍스트 윈도우 | Gemini 1,048,576 · Gemma 262,144 | 2026-08-13 | `probe specs` (모델 목록 52개 반환) |

입력 토큰 수만 항상 채워진다는 사실이 `client.Usage.from_metadata()`가 None을 0으로
다루는 이유다. 세 모델의 토크나이저가 같다는 것은 **Gemini로 센 토큰 수를 Gemma 예산
판정에 그대로 써도 된다**는 뜻이다.

가격은 실측으로 채울 수 없다. `price_in_per_mtok`와 `price_out_per_mtok`는 공개
가격표를 보고 손으로 넣어야 하며, 현재는 `None`이다 (11장).

### 7.3 성능

생성 속도는 세 번 독립적으로 측정돼 수렴했다.

| 측정 | 값 | 측정일 | 조건 |
|---|---|---|---|
| 1차 | 초당 33.1토큰 | 2026-08-13 | Gemma 31B, 6회 평균 (29.8~34.9) |
| 2차 | 초당 34.2토큰 | 2026-08-14 | Gemma 31B, 3회 |
| 3차 | 초당 34.7토큰 | 2026-08-16 | Gemma 31B, 실사용 1회 (1,063토큰 / 30.6초) |

**코드는 34.2를 쓴다** (`models.GENERATION_TOKENS_PER_SECOND`). 세 값이 4% 안에서
모였다는 사실 자체가 이 상수를 믿을 근거이며, 3.6절의 경계 유도식이 여기에 기댄다.

Gemini는 훨씬 빠르다 — 1,346토큰을 6.9초에 냈으니 초당 약 195토큰으로 Gemma의 5.6배다
(2026-08-16, 실사용 1회). 코딩처럼 긴 출력이 필요한 작업에서 두 모델의 체감이 갈리는
지점이다.

응답 모드는 한도에 영향을 주지 않는다. 대가는 시간뿐이다.

| 모델 | 모드 | 입력 | 사고 | 답변 | 시간 | 잘림 |
|---|---|---|---|---|---|---|
| Gemini | `minimal` | 54 | 0 | 850 | 4.4초 | 아니오 |
| Gemini | `medium` | 54 | 797 | 857 | 6.6초 | 아니오 |
| Gemini | `high` | 54 | 1,360 | 823 | 8.6초 | 아니오 |
| Gemma | `minimal` | 112 | 0 | 1,606 | 45.5초 | 아니오 |
| Gemma | `high` | 112 | 745 | 1,300 | 57.5초 | **예** |

측정일 2026-08-15. 재현 명령은 다음과 같다.

```bash
python scripts/probe_models.py modes
```

읽을 것은 세 가지다.

- **입력 토큰이 모드와 무관하게 같다.** Gemini 세 모드가 모두 54였다. TPM은 입력만
  세므로 (3.2절) 모드를 올려도 한도 소비가 늘지 않는다. 명령 출력에
  `_input_tokens_identical_per_model` 항목으로 이 판정이 함께 나온다.
- 대가는 응답 시간이다. Gemini는 `minimal` 대비 `medium`이 2.2초 더 걸린다. 기본값을
  `medium`으로 둔 근거가 이것이다.
- **Gemma는 사고를 켜면 잘린다.** 사고 745 + 답변 1,300 = 2,045로 출력 상한 2,048에
  부딪혔다. Gemma가 `minimal` 고정인 이유가 이론이 아니라 실측으로 확정된 지점이다.

**다시 재야 하는 시점.** 모델 버전이 올라갈 때. 생성 속도가 바뀌면 3.6절의 경계가 함께
움직이므로, 속도를 다시 잰 뒤에는 `GENERATION_TOKENS_PER_SECOND`를 갱신한다.

콜드 부팅 시간은 **미측정**이다 (초 단위 기록 없음). 12시간 슬립 후 첫 접속에서 상당한
시간이 걸리고, 로그가 멈춘 것처럼 보이는 구간이 길다. 재부팅과 새로고침을 반복하면
프로비저닝이 매번 처음부터 다시 시작되어 오히려 더 안 뜬다. 다음 슬립이 자연히
발생하면 그때 재서 채운다.

### 7.4 토큰

| 값 | 결과 | 측정일 | 방법 |
|---|---|---|---|
| 한국어 자/토큰 | 1.63~1.70 | 2026-08-13 | `probe tokens` — 39자/23토큰, 14,700자/9,002토큰 |
| 영어 자/토큰 | 3.63 | 2026-08-13 | 69자/19토큰 |
| 턴당 증가 (Gemini, 출력 512 상한) | 525~530토큰 | 2026-08-13 | `probe turns` — 5턴 |
| 턴당 증가 (Gemma, 출력 768 상한) | 782~786토큰 | 2026-08-13 | 앱과 같은 경로로 6턴 |
| 턴당 증가 (인스트럭션 없음) | 약 1,080토큰 | 2026-08-13 | 3턴 |
| 턴당 증가 (인스트럭션 있음) | 약 445토큰 | 2026-08-13 | 3턴 |

코드 상수는 **한국어 1.6 / 영어 3.5**다 (`context.KOREAN_CHARS_PER_TOKEN`,
`OTHER_CHARS_PER_TOKEN`). 둘 다 실측보다 토큰을 조금 많게 세는 쪽으로 잡았다. 과소
추정은 한도를 넘겨 429를 부르는 위험한 방향이고, 과대 추정은 조금 일찍 절단하는 안전한
방향이기 때문이다. 초안의 영어 4.0은 실측 3.63보다 커서 과소 추정을 만들었고, 그래서
3.5로 내렸다.

턴당 증가는 조건에 따라 두 배 넘게 달라진다. 위 표의 445와 1,080은 같은 모델의 같은
질문인데 시스템 인스트럭션 유무만 다르다. 이 폭이 3.6절에서 턴 수를 상수로 두지 않기로
한 근거다.

**다시 재야 하는 시점.** 토크나이저는 모델 계열이 바뀔 때. 턴당 증가는 기본 시스템
인스트럭션을 고칠 때마다 — 그 값이 직접 바꾸기 때문이다.

### 7.5 답변 길이와 시스템 인스트럭션

시스템 인스트럭션 문구를 세 번 고쳤고, 그때마다 같은 질문 3개로 측정했다.

| 문구 | 평균 출력 | 편차 | 잘림 | 측정일 |
|---|---|---|---|---|
| 없음 | 1,221토큰 | 968~1,542 | 1/3 (상한 1,536) | 2026-08-13 |
| 1차 상한만 제시 | 435토큰 | 408~449 | 0/3 | 2026-08-13 |
| 2차 상한과 하한을 함께 제시 | **1,301토큰** | 1,144~1,447 | 0/3 (상한 2,048) | 2026-08-14 |

**하한 지시가 결정적이었다.** 1차 문구는 상한만 줬고 모델은 지시의 38% 길이까지
내려갔다. 상한만 주면 모델은 계속 아래로 간다 — 길이를 제어할 다른 곳에도 적용되는
원리다. 2차에서 하한을 넣자 목표 대역에 안정적으로 들어왔고 편차도 줄었다.

인스트럭션 없이도 평균은 비슷하지만(1,221) 편차가 크고 잘림이 생긴다. 지금 인스트럭션의
역할은 "짧게 만들기"가 아니라 **길이를 목표 대역에 묶어 두는 것**이다.

코딩 용도는 길이 목표를 아예 주지 않는다. 코드는 중간에 잘리면 쓸모가 없어서다. 상한만
4,096으로 올려 두고 길이는 모델에 맡긴다. 실측은 다음과 같다.

| 모델 | 출력 | 시간 | 상한 4,096 대비 | 잘림 |
|---|---|---|---|---|
| Gemini 3.5 Flash-Lite | 1,346토큰 | 6.9초 | 33% | 아니오 |
| Gemma 4 31B | 1,063토큰 | 30.6초 | 26% | 아니오 |

측정일 2026-08-16, 웹 API 전체를 작성해 달라는 요청이었다. **상한 근처에도 가지
않았다.** 답변 길이를 실제로 정하는 것은 상한이 아니라 인스트럭션이라는 3.6절의 전제가
여기서 확인된다.

**다시 재야 하는 시점.** 인스트럭션 문구를 고칠 때마다. 이 측정 없이 문구만 바꾸면 1차
개정 때처럼 지시의 38%로 떨어지는 일을 알아채지 못한다.

### 7.6 유도값 — TPM 병목 경계

측정값이 아니라 측정값에서 계산되는 값이다. 별도로 두는 이유는 재측정 대상이 아니라
**재계산 대상**이기 때문이다. 입력이 바뀌면 자동으로 따라온다.

```text
경계 = (평균 답변 토큰 ÷ 초당 생성 토큰) × (요청당 상한 ÷ 60)
```

| 모델 | 유도값 | 기본 예산 | 판정 |
|---|---|---|---|
| Gemma 4 31B | 9,129 | 9,000 | 기본 설정이 경계 바로 아래다 |
| Gemini 3.5 Flash-Lite | 142,653 | 32,000 | 경계에서 한참 멀다 |

산출일 2026-08-15, 입력은 평균 답변 1,301토큰과 초당 34.2토큰이다. 값이 움직이는 폭은
다음과 같다.

| 평균 답변 | Gemma 경계 |
|---|---|
| 510토큰 | 2,877 |
| 1,301토큰 (현재) | 9,129 |
| 2,000토큰 | 약 14,000 |

**코드에는 이 숫자들이 하드코딩되어 있지 않다.** `models.tpm_boundary_budget()`이 매번
계산한다. 이 문서에 적힌 9,129도 "지금 이 정도가 나온다"는 참고치이지 코드에 박아야 할
값이 아니다.

### 7.7 배치 실측 (브라우저)

API가 아니라 화면 좌표를 잰 기록이다. 같은 결함이 두 번 나온 뒤 원칙이 됐다 (9장, 8.2절).

| 대상 | 결과 | 측정일 |
|---|---|---|
| 멈춤 버튼 (수정 전) | 긴 대화에서 문서 상단 기준 2,005px — 화면 높이는 720px | 2026-08-15 |
| 계열 전환 확인 창 (수정 전) | 7,052px 문서를 끝까지 내린 상태에서 화면 6,220px 위 | 2026-08-16 |
| 계열 전환 확인 창 (수정 후) | 드롭다운 148 · 문구 248 · 저장 528 · 전환 584 · 취소 640 | 2026-08-16 |
| Streamlit 기본 글자 크기 | 버튼 16px (상자 40px) · 설정 라벨 14px · 캡션 14px | 2026-08-16 |
| 대화 목록 제목 (현재) | 11px, 상자 20px(한 줄) / 34px(두 줄) | 2026-08-16 |
| 클립보드 권한 | iframe 권한과 보안 컨텍스트는 확보, 자동화로는 성공 확인 불가 | 2026-08-14 |

**이 측정에는 스크립트를 두지 않는다.** 브라우저 자동화 의존성을
`requirements-dev.txt`에 넣을 만큼 자주 쓸 일이 아니고, 모델이 바뀐다고 다시 재야 하는
값도 아니다. 대신 12장에 수동 확인 절차를 둔다 — 긴 대화를 만든 뒤 개발자 도구
콘솔에서 대상 요소의 `getBoundingClientRect()`를 보는 것으로 충분하다.

버튼 라벨의 글자 크기를 다룰 때 주의할 점이 하나 있다. Streamlit은 라벨을 버튼 안쪽
markdown 컨테이너의 `p` 요소로 그리고, **그 `p`가 font-size를 16px로 다시 잡는다.**
`button`에만 크기를 걸면 상자만 줄고 글자는 그대로다 (8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」).

## 8장. 트러블슈팅 사례집 ★

**겪은 것만 적는다.** 일반적인 Streamlit 요령이나 API 사용법은 없다. 이 프로젝트에서
실제로 난 33건과, 자동화로는 판정할 수 없어 사람이 봐야 했던 3건이다.

각 사례는 다음 형식이다. **알아챈 방법**을 반드시 붙였다 — 특히 8.1절은 예외도 안 나고
화면도 멀쩡한 부류라, 다음 사람이 같은 증상을 알아채는 단서가 이 장의 값어치다.

- **증상** — 겉으로 무엇이 보였는가
- **알아챈 방법** — 어떻게 발견했는가 (우연이면 우연이라고 적는다)
- **원인** — 실제로 무엇이 잘못됐는가
- **해법** — 무엇을 고쳤는가
- **재발 방지** — 등급과 내용
- **근거** — 커밋·파일·테스트

### 8.0 증상별 찾아보기와 재발 방지 등급

증상에서 출발할 때 어디부터 볼지의 표다.

| 증상 | 먼저 볼 곳 | 첫 질문 |
|---|---|---|
| 화면에 있어야 할 것이 안 보인다 | 8.2 | 안 그려진 것인가, 화면 밖에 그려진 것인가 |
| 한도 표시나 대기가 이상하다 | 8.1 | 창에 무엇을 넣었나, 그 기록의 시각은 언제인가 |
| 예외가 났다 (`StreamlitAPIException` 등) | 8.3 | 위젯이 그려진 뒤에 그 키를 건드렸나 |
| 답변 길이가 이상하다 | 8.1 · 7.5절 | 인스트럭션이 상한만 주고 있나 |
| 문구가 이상하거나 숫자와 안 맞는다 | 8.4 | 라벨이 주장하는 단위가 값의 단위와 같은가 |
| 배포·부팅·푸시가 안 끝난다 | 8.5 | 우리가 고칠 수 있는 자리인가 (대개 아니다) |
| 문서끼리 어긋난다 | 8.6 | 덮어쓰기로 앞선 수정이 지워졌나 |
| 확인 자체가 안 된다 | 8.7 | 사람이 봐야 하는 항목인가 |

**재발 방지 등급과 집계.**

같은 실수가 다시 나지 않게 막는 방법에는 급이 있다. 무엇으로 막았는지를 한 글자로
표시한다.

| 등급 | 뜻 | 이 프로젝트의 예 |
|---|---|---|
| **A. 구조** | 잘못할 자리가 아예 없다 | `record_usage_from()`이 usage에서 입력 토큰만 뽑는다 — 호출자가 total을 넘길 방법이 없다 |
| **B. 테스트** | 잘못하면 테스트가 실패한다 | `test_창의_기준_시각은_전송_시각이지_응답_시각이_아니다` |
| **C. 원칙** | 사람이 기억해야 한다 | `CLAUDE.md`의 배치 원칙·화면 문구 원칙 |
| **D. 없음** | 알아두는 것뿐 | 콜드 부팅 지연, 에이전트 셸에서 끝나지 않는 `git push` |

집계는 다음과 같다.

| 분류 | A 구조 | B 테스트 | C 원칙 | D 없음 | 합계 |
|---|---|---|---|---|---|
| 8.1 조용히 잘못 도는 것 | 2 | 5 | 1 | 0 | 8 |
| 8.2 화면에 안 보이는 것 | 0 | 0 | 4 | 0 | 4 |
| 8.3 Streamlit 특유 | 1 | 0 | 6 | 1 | 8 |
| 8.4 화면 문구 | 0 | 0 | 3 | 0 | 3 |
| 8.5 배포·플랫폼 | 0 | 0 | 0 | 3 | 3 |
| 8.6 문서·절차 | 0 | 0 | 4 | 0 | 4 |
| 8.7 자동화 불가 | 0 | 0 | 1 | 2 | 3 |
| **합계** | **3** | **5** | **19** | **6** | **33** |

**이 표에서 읽을 것은 C의 비중이다.** 33건 중 19건이 "사람이 기억해야 한다"에 머물러
있고, 8.2·8.4·8.6은 **전부 C다.** 이 세 분류가 다음에 재발할 후보다. 실제로 8.2는
같은 결함이 두 번 났고(멈춤 버튼, 계열 전환 확인 창) 두 번째가 나서야 원칙이 됐다.

A와 B가 8.1에 몰린 것도 우연이 아니다. 조용히 잘못 도는 부류는 사람이 알아챌 수 없어서
구조나 테스트로 막을 수밖에 없다. 반대로 8.5(플랫폼)는 우리가 손댈 수 있는 자리가
없어 D가 정상이다.

승급 후보는 8.8절에 따로 모았다.

### 8.1 조용히 잘못 도는 부류

예외가 나지 않고 화면도 정상으로 보이는 것들이다. **다섯 건이 측정 중에,
두 건이 코드·문서 검토 중에 발견됐다.** 실사용으로 발견된 것은 한 건뿐이다.

**Gemma에 `thinking_config`를 생략 (B)**

- **증상** — Gemma 응답 본문이 빈 문자열로 오고 `finish_reason`이 `MAX_TOKENS`다.
  예외는 나지 않는다.
- **알아챈 방법** — 계획에 없던 발견이다. 스트리밍 동작만 확인하려던 측정에서
  Gemma 두 모델만 본문이 비어 나왔고, `usage_metadata`를 보니 사고 토큰 47이
  기록돼 있었다.
- **원인** — Gemini는 `thinking_config`를 생략하면 `minimal`로 동작하지만
  **Gemma는 사고가 켜진 채로 동작한다.** 사고 토큰이 `max_output` 50을 전부 삼켰다.
- **해법** — `client.build_config()`가 모든 요청에 `thinking_config`를 명시한다.
- **재발 방지 (B)** — `test_thinking_config를_항상_보낸다`가 세 모델 전부에 대해
  `cfg.thinking_config is not None`을 확인한다.
- **근거** — `api_findings.md` A-3·A-4 / 커밋 `52b65ac` / `tests/test_client.py`

**TPM 창에 `total_token_count`를 넣을 뻔함 (A)**

- **증상** — (코드에 반영되기 전에 잡았다) 반영됐다면 한도 추적기가 실제보다 빨리 차서
  서버는 허용하는데 앱이 스스로 대기를 걸었을 것이다.
- **알아챈 방법** — 문서 검토. TPM 실험을 끝낸 뒤 그 전에 써 둔 관측 노트를 다시 읽다가
  "사후 보정은 total 하나만 쓰면 된다"는 문장이 실험 결과와 모순된다는 것을 발견했다.
  **실험보다 먼저 쓰인 문장이 남아 있었다.**
- **원인** — `total_token_count`는 입력 + 출력 + 사고의 합인데 TPM은 입력만 센다
  (3.2절).
- **해법** — 창에 넣는 값을 `prompt_token_count` 하나로 고정했다.
- **재발 방지 (A)** — `record_usage_from()`이 usage 객체를 받아 **자기가 입력 토큰만
  뽑는다.** 호출자가 total을 넘기고 싶어도 넘길 자리가 없다. 테스트
  `usage_객체에서_입력_토큰만_뽑는다`와 `출력_크기는_TPM_판정에_영향을_주지_않는다`가
  이를 다시 확인한다.
- **근거** — `api_findings.md` A-6 정정 / 커밋 `ab3580d`·`31a7ca7` / `tests/test_quota.py`

**한도 창의 기준 시각이 응답 시각으로 밀림 (A)**

- **증상** — 이미 한도가 풀린 요청을 최대 45초 더 막는다. 사용자에게는 "왜 아직도
  기다리라고 하지"로 보인다.
- **알아챈 방법** — 구현 검토. 당시 코드도 시각 자체는 전송 시각이었지만,
  "`record_sent`를 스트림 시작에 부른다"는 **관례**와 "마지막 기록을 덮어쓴다"는
  구현에 기대고 있었다. Gemma가 긴 응답 하나에 45초를 쓴다는 실측(7.3절)과 겹쳐 보니,
  호출 순서가 한 번만 어긋나도 창이 통째로 밀리는 구조였다.
- **원인** — 보정 시점에 창 기록의 **시각까지** 갱신될 수 있는 구조.
- **해법** — `record_sent()`가 기록 핸들을 돌려주고, 보정은 그 핸들의 값만 바꾼다.
  시각은 전송 시각 그대로 남는다.
- **재발 방지 (A)** — 핸들 방식이라 보정이 시각을 건드릴 수 없다. 덤으로 스트림이
  60초를 넘겨 기록이 만료된 경우 엉뚱한 기록을 부풀리는 대신 보정을 버린다.
  테스트 3건이 이 동작을 고정한다.
- **근거** — 커밋 `c9af8f2` / `tests/test_quota.py`의 `창의_기준_시각은…`,
  `보정이_늦어도_창이_밀리지_않는다`, `스트림이_창보다_길면_보정을_버린다`

**공백을 영어 상수로 세어 한국어를 과소 추정 (B)**

- **증상** — 토큰 추정이 실제보다 작게 나온다. 겉으로는 아무 일도 없지만 한도를 넘겨
  429를 부르는 **위험한 방향**이다.
- **알아챈 방법** — 테스트를 쓰다가. 실측 표본(한국어 39자 = 23토큰)을 넣어 보니
  추정이 21이 나왔다. 안전한 쪽으로 어긋나야 할 값이 반대로 어긋나 있었다.
- **원인** — 공백을 일괄로 영어 상수(3.5자/토큰)에 할인해 넣었다. 한국어 문장은
  공백 비중이 높아 그만큼 낮게 추정된다.
- **해법** — 공백은 **직전 비공백 문자의 분류**를 따르게 했다.
- **재발 방지 (B)** — `공백은_직전_문자의_분류를_따른다`와
  `실측_표본을_과소_추정하지_않는다`가 실측값 이상을 요구한다. 두 번째 테스트는

- **근거** — 커밋 `31a7ca7` / `tests/test_context.py`

**Gemma에 `medium`을 보내 400 (B)**

- **증상** — 요청이 400으로 거절된다. 메시지는 "이 모델은 사고 수준을 지원하지

- **원인** — Gemma는 켜기/끄기 2단계뿐인데 UI 값이 그대로 전달됐다. 참고로 오류 문구는
  오해를 부른다 — `minimal`과 `high`는 정상 수용되므로 "지원하지 않는다"가 아니라

- **해법** — `resolve_thinking_level()`이 전송 전에 `minimal`로 되돌린다.
  `build_config()`가 유일한 설정 조립 경로라 우회할 자리가 없다.
- **재발 방지 (B)** — `지원하지_않는_사고_수준은_보내기_전에_걸러진다`.
- **근거** — `api_findings.md` A-5 / 커밋 `52b65ac` / `tests/test_client.py`

**모델 스펙을 문서만 보고 잘못 적음 (B)**

**코딩 답변의 코드가 중간에서 끊김 (B)**

### 8.2 화면에 안 보이는 부류

**네 건 모두 C이며, 네 건 모두 사용자 신고로 발견됐다.** 자동 검사는 요소가
"존재하는지"만 볼 수 있고 "보이는지"는 보지 못한다. 이 분류가 존재하는 이유다.

**멈춤 버튼이 안 보인다 (C)**

- **증상** — 스트리밍 중에 멈춤 버튼이 화면에 없다.
- **알아챈 방법** — 사용자 신고. 브라우저에서 재현해 보니 **버튼은 렌더링되고 있었다**
  (1.5초 간격으로 5회 확인해 모두 검출). 문제는 위치였다 — 문서 상단 기준 2,005px,
  화면 높이는 720px.
- **원인** — 본문 흐름에 그리면 대화가 길어질수록 아래로 밀린다. 사용자는 늘 문서 맨
  아래에 있으므로 위쪽에 그린 것은 화면 밖이다.
- **해법** — `st.container(key=...)` + `position: fixed`로 입력창 위에 고정했다.
  `sticky`는 스크롤이 그 지점까지 가야 붙어서 부족했다.
- **재발 방지 (C)** — 배치 원칙(9장). 자동 테스트는 없다.
- **근거** — 커밋 `6789984` / 7.7절

**계열 전환 확인 창이 안 뜬다 (C)**

- **증상** — 모델을 다른 계열로 바꿔도 확인 창이 나오지 않는다. 새 대화를 누르면
  그제야 나타난다.
- **알아챈 방법** — 사용자 신고. "새 대화를 누르니 그제야 보인다"가 결정적 단서였다 —
  새 대화로 문서가 짧아지면 보인다는 뜻이므로 렌더링 문제가 아니라 위치 문제다.
  실측하니 7,052px 문서를 끝까지 내린 상태에서 확인 창은 **화면 6,220px 위**에 있었다.
- **원인** — 멈춤 버튼과 같다. 본문 맨 위에 그렸다.
- **해법** — 사이드바의 모델 드롭다운 **바로 아래**로 옮겼다. 조작한 위젯 옆이라
  스크롤 위치와 무관하다. 좁은 폭에 맞춰 3버튼을 세로로 쌓았다.
- **재발 방지 (C)** — **같은 결함이 두 번 나서야 원칙이 됐다.** 배치 원칙에는 해법
  두 가지(`position: fixed` / 조작한 위젯 옆)와 검증 조건(메시지 20개 이상)이 함께
  들어갔다.
- **근거** — 커밋 `bd93978` / 9장 / 12장 검증 4·5·6번

**멈춤을 누르면 받은 답이 통째로 사라짐 (C)**

- **증상** — 멈춤 버튼을 누르면 그때까지 받은 답이 화면에서 사라진다.
- **알아챈 방법** — 사용자 신고.
- **원인** — 멈춤 버튼이 리런을 일으켜 실행 중인 스크립트가 중단되므로, 성공 경로의
  `append_message()`가 아예 실행되지 않는다.
- **해법** — `_capture()`가 스트림 조각을 `session_state`에 쌓고, 다음 실행에서
  `stopped_by_user` 메시지로 붙인다.
- **재발 방지 (C)** — "리런으로 중단되는 경로에서는 성공 경로의 뒷정리가 돌지 않는다"는
  이해가 필요하다. 자동 테스트로 만들지 못했다.
- **근거** — 커밋 `f1fcf77` / `Message.stopped_by_user`

**중단분이 다음 조작 전까지 안 보임 (C)**

- **증상** — 멈춘 뒤 답이 안 보이다가, "계속"이라고 입력하면 그제야 나타나면서 이어
  쓴다.
- **알아챈 방법** — 사용자 신고. "계속이라고 하면 사라졌던 답이 보인다"는 서술이
  단서였다 — 데이터는 살아 있고 그리는 시점만 늦다는 뜻이다.
- **원인** — 중단분을 붙이는 처리를 입력창 단계에서 했는데, 그 시점엔 이력이 이미
  그려진 뒤다.
- **해법** — `_commit_interrupted()`를 `render_history()` 맨 앞으로 옮겼다.
- **재발 방지 (C)** — 함수 docstring에 이유를 남겼다. Streamlit은 위에서 아래로 한 번
  훑으므로 **상태를 바꾸는 일은 그리기 전에** 끝나야 한다.
- **근거** — 커밋 `a18a007` / `gchat/ui/chat.py`

### 8.3 Streamlit 특유의 것

**위젯 키를 사후 대입 — 일괄 삭제 (C)**

### 8.4 화면 문구

**세 건 모두 C다.** 문구는 컴파일되지 않고 테스트되지도 않는다. 사람이 읽어야 안다.

**개발 문서 용어가 화면에 노출 (C)**

- **재발 방지 (C)** — 화면 문구 원칙(9장).
- **근거** — 커밋 `a18a007`

- **해법** — 단위를 주장하지 않는 "분당 사용량"으로 바꿨다. 메시지 메타의 "글자분"도

**같은 낱말이 서로 다른 것을 셈 (C)**

- **알아챈 방법** — 앞 사례를 고치면서 **숫자를 동반한 화면 문구를 전수 감사**하다

- **원인** — "대화"라는 낱말을 두 가지 뜻으로 썼다.
- **해법** — 절단 안내 세 곳을 "앞선 메시지 N개"로 바꿨다.
- **재발 방지 (C)** — 원칙뿐이다. 참고로 내보내기 파일은 "토큰"으로 정확히 쓰고 있어
  건드리지 않았다 — 값이 토큰이 맞고, 기록 문서에는 정확한 이름이 낫다.

### 8.6 문서·절차

코드에는 전혀 나타나지 않지만 세션마다 시간을 먹은 부류다. **네 건 모두 C이고, 이
프로젝트가 문서를 코드만큼 중요하게 다뤘기 때문에 생긴 문제들이다.** 같은 방식으로
일할 사람에게는 코드 결함만큼 실질적이다.

**설계 문서가 자기 모순을 품음 (C)**

- **증상** — 문서가 "상세 설정에서 늘리세요"라고 안내하는데 그런 UI가 없다.
- **알아챈 방법** — 문서와 코드를 대조하다가.
- **원인** — 해당 기능을 v1에서 빼기로 하면서 그 기능을 전제한 문장이 남았다.
- **해법** — 모순 문구를 지우고, 함께 유실됐던 항목들을 복원했다.
- **재발 방지 (C)** — 기능을 뺄 때 그 기능을 **언급한 모든 곳**을 찾는다.
- **근거** — 커밋 `ab3580d`

**문서 편집 중 항목 번호가 유실됨 (C)**

- **증상** — 검증 항목 목록에서 번호 두 개가 사라졌다.
- **알아챈 방법** — 번호를 세다가.
- **원인** — 전체 덮어쓰기 방식의 편집.
- **해법** — 번호를 복구했다.
- **재발 방지 (C)** — 번호가 있는 목록은 개수를 세어 확인한다.
- **근거** — 커밋 `ab3580d`

**덮어쓰기로 이전 동기화분이 원복됨 (C)**

- **증상** — 앞선 세션에서 맞춰 둔 부분이 다음 문서 갱신 후 옛 내용으로 돌아가 있다.
- **알아챈 방법** — 문서 간 대조. 설계 문서의 부록과 실제 지시서를 diff로 비교하는

- **해법** — 덮어쓰기를 받을 때마다 두 문서의 공통부를 diff로 재대조하는 절차를 넣었다.

**문서가 도착했다고 가정하고 작업을 시작함 (C)**

- **증상** — "문서를 갱신했다"는 말을 받고 작업을 시작했는데 파일은 이전 판이었다.
- **알아챈 방법** — 새 절의 특징 문자열을 `grep`으로 찾다가 0건이 나왔다.
- **원인** — 갱신했다는 말과 실제 저장 시점이 어긋났다.
- **해법** — 그 사실을 먼저 알리고 기다린 뒤, 도착을 확인하고 작업했다.
- **재발 방지 (C)** — **받았다고 가정하지 않고 내용으로 확인한다.** `git status`로
  변경 여부를, 새 절의 특징 문자열로 도착 여부를 본다. 이 절차를 쓴 뒤로는 미도착을
  즉시 발견해 헛일이 없었다.
- **근거** — 세션 2 기록 / 이후 세션에서 같은 절차로 조기 발견

### 8.7 자동화로 판정할 수 없는 것

**무엇을 자동으로 확인할 수 없는지 아는 것도 문서의 몫이다.** 이 셋은 사람이 직접
확인해야 한다.

**클립보드 복사 (D)**

- **왜 자동화가 안 되는가** — `navigator.clipboard.writeText()`는 문서 포커스를
  요구한다. 자동화 환경에서는 `NotAllowedError: Document is not focused`가 나며,
  이는 사람이 실제로 클릭하는 상황에서는 나지 않는 오류다.
- **어디까지 확인했는가** — iframe에 `clipboard-write` 권한이 있고 보안 컨텍스트도
  참이라는 것까지는 확인했다. 성공 여부만 확인하지 못했다.
- **최종 판정** — 사람이 눌러 통과. 로컬(localhost)은 보안 컨텍스트가 자동 통과라
  판정이 되지 않았고, **HTTPS 배포 환경의 확인이 진짜 판정**이었다. 네 세션을 끌었다.
- **재발 방지 (D)** — 없다. 확인 절차를 12장에 둔다.

**시각적 배치 (C)**

- **왜 자동화가 안 되는가** — DOM에 존재하는 것과 화면에 보이는 것이 다르다.
  8.2절의 두 사례가 정확히 이 틈에서 났다.
- **어디까지 확인했는가** — 요소의 좌표를 재는 방식으로 **판정 가능해졌다.**
  존재 여부만 보면 통과하지만 좌표를 보면 화면 밖인 것이 드러난다.
- **최종 판정** — 통과 (긴 대화 상태에서 확인).
- **재발 방지 (C)** — 12장에 수동 확인 절차를 뒀다. 스크립트로 만들지 않은 이유는
  브라우저 자동화 의존성을 상시로 들일 만큼 자주 쓰지 않기 때문이다.

**문장이 자연스러운가 (D)**

- **왜 자동화가 안 되는가** — 멈춤 뒤 "계속"으로 이어받은 글이 매끄러운지는 읽어야
  안다. 중단 지점이 문장 중간이면 어색할 수 있다.
- **어디까지 확인했는가** — 기능은 동작한다(멈춘 답이 남고 이어 쓴다). 품질은
  미판정이다.
- **최종 판정** — **미판정.** 실사용에서 느낌으로 정할 항목이다.
- **재발 방지 (D)** — 없다.

## 9장. 작업 원칙

이 장이 `CLAUDE.md`의 출처다. **각 원칙에 어디서 나왔는지를 붙였다** — 근거 없는
원칙은 지켜지지 않는다.

### 9.1 값을 다루는 원칙

**모델별 값은 `models.py` 테이블에만 쓴다.**
어디서 왔나 — 3.6절. 같은 숫자가 여러 파일에 있으면 새 모델 추가가 전수 검색이 된다.
슬라이더 상한도 UI에 적지 않고 `max_request_tokens()`로 유도한다. 지금 코드에
경계값 하드코딩은 0건이다.

**바뀔 값은 상수가 아니라 유도로 둔다.**
어디서 왔나 — 6.3절 「TPM 병목 경계 — 어떻게 끝냈나」. 같은 값을 12,000 → 11,000 → 9,100으로 세 번
고쳤고, 세 번 모두 "입력이 바뀌어서"였다. 네 번째에 식으로 바꾼 뒤로는 한 번도
고치지 않았다. **값을 세 번 이상 고치고 있다면 그 값이 무엇에서 나오는지 묻고, 식으로
쓸 수 있는지 본다.**

**측정한 값에는 측정일과 방법을 붙인다.**
어디서 왔나 — 7장 전체. 모델은 바뀌고 그때 다시 재야 하는데, 언제 어떻게 잰 값인지
모르면 다시 잴 수도 없다.

### 9.2 잘못할 자리를 없애는 원칙

**주석으로 막지 말고 구조로 막는다.**
어디서 왔나 — 8.1절의 A등급 세 건. 셋 다 "조심하자"로 끝낼 수 있었지만 구조를 바꿨다.

- `record_usage_from()`이 usage에서 입력 토큰을 **자기가** 뽑는다. 호출자가 total을
  넘길 자리가 없다
- `record_sent()`가 핸들을 돌려주고 보정은 그 값만 바꾼다. 시각을 건드릴 자리가 없다
- 비밀번호는 `st.form` 안에서만 판정한다. 제출하지 않은 리런에서 실패가 쌓일 자리가 없다

**막을 수 없으면 테스트로 잡는다.**
어디서 왔나 — 8.1절의 B등급 다섯 건. 구조로 못 막는 것은 잘못하면 실패하게 만든다.
`client.py`가 샘플링 파라미터를 쓰지 않는다는 것은 소스에 그 이름이 등장하는지까지
검사한다.

**알아채기 쉬운 결함일수록 방어가 약해진다.**
어디서 왔나 — 8.0절 등급표. 33건 중 19건이 C(사람이 기억해야 함)이고, 8.2·8.4·8.6은
**전부 C**다. 조용히 잘못 도는 부류(8.1)에 A·B가 몰린 것은 사람이 알아챌 수 없어
구조나 테스트로 막을 수밖에 없었기 때문이다. 반대로 눈에 띄는 결함은 "보면 아니까"
하고 넘어가다 재발한다 — 8.2절은 실제로 같은 결함이 두 번 났다.
**고친 뒤 "이건 눈에 띄니까 괜찮다"는 생각이 들면 그때가 위험한 지점이다.**

### 9.3 화면을 다루는 원칙

**즉시 반응해야 하는 UI를 본문 흐름에 그대로 얹지 않는다.**
어디서 왔나 — 8.2절 「멈춤 버튼이 안 보인다」와 「계열 전환 확인 창이 안 뜬다」.
같은 원인이 두 번 났다. 대화가 길어지면 사용자는 늘 문서 맨 아래에 있으므로 본문
상단에 그린 것은 화면 밖이다. 해법은 둘 중 하나다 — 화면에 고정하거나, 조작한 위젯
바로 옆에 그린다.

**그리고 긴 대화에서 검증한다.** 짧은 대화에서는 위 두 결함 모두 재현되지 않았다.
검증 조건이 원칙의 일부다 (12.4절).

**화면 문구에 개발 용어를 쓰지 않는다.**
어디서 왔나 — 8.4절 세 건. 문서 절 번호, HTTP 상태 코드, 원본 오류 JSON은 화면에
내지 않는다. 근거는 주석에 남기고 화면에는 결과만 쓴다.

**라벨을 바꿀 때 표시되는 숫자의 단위가 라벨과 맞는지 확인한다.**
어디서 왔나 — 8.4절 「라벨과 값의 단위가 다름」. 개발 용어를 걷어내다가 "분당 토큰"을
"분당 글자"로 바꿨는데, 값은 여전히 토큰이라 약 1.6배 틀린 표시가 됐다.
**용어를 다듬는 작업이 값을 틀리게 만들 수 있다.**

**상태를 바꾸는 일은 그리기 전에 끝낸다.**
어디서 왔나 — 8.2절 「중단분이 다음 조작 전까지 안 보임」과
8.3절 「인증에 성공해도 비밀번호 칸이 남음」. streamlit은 위에서 아래로 한 번 훑는다.

### 9.4 실패를 다루는 원칙

**오류를 조용히 삼키지 않는다.**
어디서 왔나 — 4.3절. 무엇이 왜 실패했고 무엇을 하면 되는지 보인다. 여섯 종류를
구분하는 이유는 사용자가 할 일이 다르기 때문이다. 다만 원본 JSON은 접기 안에 둔다.

**추적기가 OK인데 서버가 거절하는 것을 정상으로 다룬다.**
어디서 왔나 — 4.3절, 7.1절. 우리 추적은 추정이고 서버가 최종 진실이다. 어긋남을
버그로 다루면 그때마다 코드를 고치게 된다.

### 9.5 판단하는 원칙

**재볼 수 있으면 먼저 재고 정한다.**
어디서 왔나 — 6.2절 유형 집계. 뒤집힌 판단 11건 중 7건이 "재보거나 써봐야 알 수 있는
것"이었다. 문서만 보고 정한 값은 거의 예외 없이 한 번씩 고쳐졌다.

**측정할 때는 무엇을 재는지 정확히 고른다.**
어디서 왔나 — 8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」. 버튼 요소의 글자 크기를
재고 "줄었다"고 두 번 보고했지만, 실제 글자는 그 안쪽 요소에 있었다.
**잘못 고른 측정은 통과 판정을 만들어내므로 측정하지 않는 것보다 나쁘다.**

**문서와 코드가 어긋나면 고치기 전에 보고한다.**
어디서 왔나 — 8.6절. 이 프로젝트에서 실제로 쓴 방식이고 잘 작동했다. 조용히 맞추면
어느 쪽이 옳았는지가 사라진다.

### 10.1 대화 영구 저장

**먼저 읽을 절** — 6.2절 「대화 영구 저장」. 왜 뺐는지가 거기 있다. 기능이 어려워서가
아니라 개인용 앱에 코드 비중이 맞지 않아서였고, 그 자리에 Markdown 내보내기가 들어왔다.

**첫 손댈 파일** — 새 모듈 하나(`store.py`)와 `state.py`. 대화를 읽고 쓰는 지점이
`state.py`에 모여 있으므로, 그 함수들이 저장소를 거치게 바꾸는 것이 시작이다.

**걸리는 것.**

- **계층상 위치를 먼저 정해야 한다.** 저장소는 바깥과 닿으므로 `client`와 같은 층이
  맞고, `state`가 그것을 직접 부르면 계층이 뒤집힌다. `quota` ↔ `client`에서 쓴
  Protocol 방식이 그대로 참고가 된다 (4.5절)
- **`session_state`만 있다는 전제가 코드 곳곳에 깔려 있다** (4.4절). 동시성 문제가
  없다는 가정, 한도 추적기가 세션과 함께 사라진다는 가정이 그것이다
- 내보내기와 역할이 겹친다. 영구 저장이 들어오면 `export.py`의 위치를 다시 정해야 한다
- 접근 통제가 비밀번호 하나뿐이다 (5.8절). 데이터가 서버에 남으면 그 수준으로
  충분한지 다시 판단해야 한다

### 10.2 파일 첨부

**먼저 읽을 절** — 3.3절 모델별 능력 차이. **Gemma는 파일 입력을 지원하지 않는다.**

**첫 손댈 파일** — `client.py`의 요청 조립부와 `ui/chat.py`의 입력부.
`models.supports_file_input`이 이미 있으므로 UI 게이팅은 그 값으로 한다.

**걸리는 것.**

- **모델 전환과 충돌한다.** Gemini에서 파일을 붙인 대화를 Gemma로 옮기면 그 첨부는
  보낼 수 없다. 계열 전환이 새 대화를 시작하는 지금 규칙이 이 문제를 반쯤 덮어주지만,
  계열 내 전환은 이력을 유지하므로 별도 처리가 필요하다
- **토큰 산입이 미확인이다.** PDF 페이지당·이미지 타일당 실제 토큰 수를 재지 않았다.
  `count_tokens`로 확인할 수 있고, 그 값이 예산 계산에 들어가야 한다 (3.4절)
- 파일 크기와 형식 제한, 업로드한 파일의 수명도 확인 대상이다

### 10.3 웹 검색 그라운딩

**먼저 읽을 절** — 6.2절 5번과 7.2절. **무료 등급에서는 호출 자체가 막혀 있다** —
검색 도구를 붙이면 모델과 무관하게 즉시 429가 오고, 같은 시각 도구만 빼면 정상
응답한다. 모델 단위 한도 소진이 아니라 검색 전용 할당량이 0인 것이다.

**전제 — 유료 전환이 필요하다.** 이 항목만은 코드를 고쳐서 될 일이 아니다. 결제를
붙이지 않으면 켜는 순간 실패하는 스위치가 된다. 10.4절을 함께 본다.

**첫 손댈 파일** — `client.py`의 `build_config()`. 지금은 `tools` 파라미터를 아예
다루지 않으며, 테스트가 소스에 `GoogleSearch`와 `tools=`가 등장하는지까지 검사한다.
되살리려면 **그 테스트부터 고쳐야 한다** — 실수로 되살아나는 것을 막으려고 넣은
장치이므로, 의도적으로 되살릴 때는 그 의도가 테스트에 드러나야 한다.

**걸리는 것.**

- **출처 표시 의무를 확인해야 한다.** 검색 결과를 쓰면 그것을 화면에 표시할 요건이
  따라붙는 것으로 알려져 있으나, **이 프로젝트에서 확인하지 않았다.** 되살리기 전에
  API 문서에서 확인할 것
- **분기 자체는 간단하다.** 측정에서 `grounding_metadata`는 속성이 항상 존재하고 값이
  `None`임을 확인했다 (7.2절). 출처 영역 표시 여부는 이 값 하나로 갈린다
- **과금 필드가 미확인이다.** 검색 쿼리 과금이 응답의 어느 필드로 잡히는지 그라운딩
  응답을 한 번도 받지 못해 확인할 수 없었다. 유료 전환 후 재측정 대상이다
- **Gemma는 도구를 거부하지 않지만 검색하지도 않는다.** 200이 오지만
  `grounding_metadata`가 항상 `None`이다. Gemini 전용으로 두는 것이 맞다
- TPM 영향도 재측정 대상이다. 검색 결과가 입력에 합쳐지면 입력 토큰이 늘어난다 (3.2절)

### 10.4 유료 전환 시

**먼저 읽을 절** — 7.1절(한도)과 7.2절(가격이 조회되지 않는다는 것).

**첫 손댈 파일** — `models.py`. 두 가지가 한 곳에서 끝난다.

- `price_in_per_mtok` / `price_out_per_mtok`를 공개 가격표에서 채운다.
  **API가 단가를 돌려주지 않으므로 손으로 넣어야 한다**
- `RateLimits`를 새 등급 값으로 바꾼다. 요청당 상한과 TPM 경계는 따라 움직인다 (5.1절)

**걸리는 것.**

- **한도가 올라가면 3장의 전제 일부가 바뀐다.** Gemma가 비상용인 이유가 TPM
  16,000이었으므로 (3.4절), 그 값이 달라지면 모델 배치를 다시 판단할 여지가 생긴다
- 비용 표시는 값이 채워지면 바로 살아나지만, 사고 토큰을 출력으로 볼지 결정해야 한다
  (7.2절)
- 검색 그라운딩이 열린다 (10.3절)

### 10.5 새 모델 추가

**먼저 읽을 절** — 5.1절 「여기만 고치면 되는 것들」. 코드 수정은 `models.py`의
`MODELS`에 `ModelSpec` 하나를 더하는 것으로 끝난다.

**표에 없는 것이 하나 더 필요하다 — 실측이다.** 새 모델의 값은 문서만 보고 채우면 안
된다 (8.1절 「모델 스펙을 문서만 보고 잘못 적음」). 다시 재야 할 항목은 다음과 같다.

| 재야 할 것 | 방법 | 7장 |
|---|---|---|
| 컨텍스트 윈도우 · 최대 출력 | `probe specs` | 7.2 |
| `thinking_level` 수용값과 생략 시 기본 동작 | `probe thinking` · 생략 요청 1회 | 7.2 |
| 토크나이저가 기존 모델과 같은가 | `probe tokens` | 7.4 |
| 응답 모드가 입력 토큰·시간·잘림에 주는 영향 | `probe modes` | 7.3 |
| 생성 속도 (초당 토큰) | 실제 대화 1턴의 출력 토큰 ÷ 소요 시간 | 7.3 |
| 기본 인스트럭션이 답변 길이에 주는 효과 | 같은 질문 3개를 문구 유무로 | 7.5 |

**마지막 두 개가 중요하다.** 생성 속도는 TPM 경계 유도식의 입력이고 (7.6절),
답변 길이는 그 모델에 어떤 인스트럭션을 줄지를 정한다. 둘 다 `probe`에 명령이 없으므로
직접 재야 한다.

**걸리는 것** — 새 계열이면 `THINKING_LABELS`에 계열별 라벨을 더해야 하고, 계열 전환
규칙(6.1절)이 그 계열에도 적용된다. 같은 계열의 변형이면 이력을 유지하므로 예산과
한도가 같은지 확인한다.

## 11장. 운영

### 11.1 배포와 재배포

배포 절차는 2장에 있다. 여기서는 **다시 배포할 때 주의할 것**을 적는다.

- **앱을 지우고 새로 만들면 URL이 바뀐다.** 그리고 **Secrets를 다시 등록해야 한다** —
  앱 설정에 넣은 값은 저장소가 아니라 그 앱에 붙어 있다
- Python 버전을 3.12로 명시한다. 기본값이 더 높으면 의존성 설치가 어긋날 수 있다
- Secrets는 TOML이므로 값에 따옴표가 필요하다. 빠뜨리면 앱은 "키가 없다"고 안내한다
- **첫 접속 점검 순서** — 설치 로그 3줄(streamlit·google-genai·tzdata) → 비밀번호
  화면이 먼저 나오는지 → 틀린 비밀번호로 잠금 안내 → 맞는 비밀번호로 입장 →
  질문 하나 → 내보낸 md의 시각이 KST인지 (서버는 UTC로 돈다)

**`git push`는 사람이 해야 한다.** 자격 증명 관리자가 GUI 로그인 창을 띄우므로
비대화형 셸에서는 끝나지 않는다. 최초 1회 이후에는 캐시돼 창 없이 진행된다
(8.5절 「`git push`가 에이전트 셸에서 끝나지 않는다」).

### 11.2 백업

```bash
git bundle create ../gchat-backup/gchat_YYYYMMDD_HHMM.bundle --all
git bundle verify ../gchat-backup/gchat_YYYYMMDD_HHMM.bundle
```

번들 하나에 전체 이력이 들어간다. `verify`가 "complete history"라고 답하면 그 파일만
있으면 저장소를 복원할 수 있다.

**주의 — `.streamlit/secrets.toml`은 번들에 들어가지 않는다.** 추적 대상이 아니기
때문이다(그것이 맞다). 따라서 **API 키와 앱 비밀번호는 따로 보관해야 한다.**
백업을 복원해도 이 둘이 없으면 앱은 뜨지 않는다. 키는 발급처에서 다시 만들 수 있지만
앱 비밀번호는 그렇지 않다.

### 11.3 한도가 소진됐을 때

| 상황 | 화면 | 할 일 |
|---|---|---|
| 분당 요청·토큰 초과 | 남은 대기 시간 안내 | 기다린다. 60초 창이라 곧 풀린다 |
| 일일 요청 소진 | 다른 모델 추천 | Gemma로 넘어간다. RPD가 14,400이라 사실상 안 걸린다 |
| 단일 질문이 너무 김 | 모델 전환 안내 | **기다려도 안 풀린다.** 질문을 줄이거나 Gemini로 (3.4절) |

앱이 추천을 낼 때는 RPD 여유가 있고 이번 요청이 들어가는 모델 중 기본 모델을
우선한다. 모두 막혀 있으면 가장 빨리 풀리는 모델과 대기 시간을 안내한다.

### 11.4 문서 빌드

기술서는 Markdown이 원본이고 HTML은 거기서 생성한다.

```bash
python scripts/build_docs.py            # docs/gchat_기술서.html 갱신
python scripts/build_docs.py --check    # 갱신이 필요한지만 확인
```

**HTML 은 단일 파일 자체 완결형이다.** CSS 를 문서 안에 넣고 외부 링크를 걸지 않으므로
인터넷 없이 열리고, 파일 하나만 보내면 그대로 읽힌다. 목차는 제목에서 자동으로 만들고
앵커는 절 번호에서 뽑으므로(`s-3-2` 같은 형태) 문장을 다듬어도 링크가 깨지지 않는다.

**드리프트를 테스트로 막는다.** md 를 고치고 HTML 을 다시 만들지 않으면
`tests/test_docs.py` 가 실패한다. 이 프로젝트가 반복해서 겪은 문서 어긋남(8.6절)을
같은 방식으로 두지 않으려는 것이다.

그러려면 **같은 md 에서 언제나 같은 HTML 이 나와야 한다.** 생성 시각을 넣으면 매번
달라지므로 그렇게 하지 않았다.

- 본문과 목차는 md 내용만으로 결정된다
- 하단에 md 의 **내용 해시**(SHA-256 앞 16자)를 적는다. 이 값은 결정론적이다
- 원본 커밋 해시와 커밋 시각은 git 에서 읽으므로 실행 환경에 따라 달라질 수 있다.
  그 줄에는 `data-volatile` 표시를 달았고, 비교할 때 그 줄만 제외한다

같은 검사를 명령으로도 할 수 있다 — `--check` 는 갱신이 필요하면 1을 돌려준다.

### 11.5 알려진 이슈와 관찰 중인 항목

| 항목 | 상태 | 언제 닫히나 |
|---|---|---|
| RPD 리셋 시각 | 문서 근거는 태평양 자정. **실측 미확인** | 실사용 중 일일 한도 429를 만났을 때 `quotaId`와 `retryDelay`를 기록 |
| 콜드 부팅 소요 시간 | **미측정.** 오래 걸린다는 관측만 있다 | 다음 12시간 슬립 때 재면 된다 |
| 가격 필드 | `None`. 비용 표시가 비어 있다 | 유료 전환 시 (10.4절) |
| 저장소의 requirements 중복 경고 | 무해. 현재 빌드 도구는 `requirements.txt`를 고른다 | 빌드 도구가 바뀌면 재확인 |
| 12시간 슬립 후 대화 소실 | **설계대로다.** 고장이 아니다 | 영구 저장을 넣으면 (10.1절) |

**콜드 부팅 중에는 재부팅과 새로고침을 반복하지 않는다.** 프로비저닝이 매번 처음부터
다시 시작되어 오히려 더 안 뜬다 (8.5절).

## 12장. 검증

### 12.1 통합 시험 38항목

계획서 5절의 38항목은 배포 후 전부 통과했다. **자동으로 확인되는 것과 사람이 봐야
하는 것을 나누면 다음과 같다.** 이 분류는 현재 테스트 구성을 보고 나눈 것이다.

| 구분 | 항목 수 | 성격 |
|---|---|---|
| 자동 테스트가 로직을 덮는 것 | 15 | 값·판정·번역·조립. 화면 없이 시험된다 |
| 사람이 화면에서 봐야 하는 것 | 22 | 배치·문구·흐름·체감 |
| 해당 없음 | 1 | 휘발성 경고 위치 — 화면에서 뺐다 (6.2절) |

**자동 테스트가 덮는 것** — 기본 모델이 하나인지, 계열 내 전환이 이력을 유지하는지,
지원하지 않는 응답 모드가 되돌아가는지, 단일 입력 초과 차단, 429 보정, 503과 429 구분,
대기 시간이 없는 429 처리, `thinking_config`가 항상 붙는지, 잘못된 키의 원문 노출 금지,
내보내기 형식, 빈 대화가 쌓이지 않는지, 제목 축약.

**사람이 봐야 하는 것** — 비밀번호 흐름, 멀티턴 참조, 계열 전환 확인 3종, TPM 대기
안내, 슬라이더 표시, 배지 일치, 잘림 후 "계속", 설정 변경의 반영, 삭제와 되돌리기,
새로고침 소실, 복사, 답변 길이, 멈춤, 코딩 길이, 커스텀 노출, 제목 인라인 편집.

### 12.2 자동 테스트가 지키는 것

pytest 205건은 화면을 띄우지 않는다. 무엇을 지키고 있는지로 나누면 이렇다.

발견됐다. 이 공백을 일부 메우는 방법이 8.8절에 있다.

### 12.3 긴 대화에서만 재현되는 항목

**메시지 20개 이상 쌓인 상태에서 봐야 하는 것들이다.** 짧은 대화에서는 통과한다.

- 멈춤 버튼이 화면 안에 있는가 (스트리밍 중)
- 계열 전환 확인 창이 보이는가 (모델을 바꾼 직후, 스크롤을 올리지 않은 채)
- 컨텍스트 절단 안내가 뜨는가
- 새로 추가한 즉시 반응 UI가 보이는가

앞의 둘은 실제로 짧은 대화에서 재현되지 않아 배포 후에야 잡혔다 (8.2절).

### 12.4 배치 수동 확인 절차

새 UI를 추가할 때마다 쓰는 절차다. 스크립트를 두지 않은 이유는 7.7절에 있다.

1. 코딩 프리셋으로 긴 답변을 받아 **메시지 20개 이상**을 만든다
2. 마지막 답변을 읽은 자리(문서 맨 아래)에서 **스크롤을 올리지 않는다**
3. 확인할 동작을 한다 (스트리밍 시작, 모델 변경 등)
4. 개발자 도구(F12) 콘솔에서 대상 요소의 위치를 잰다

```javascript
const el = document.querySelector('[class*="st-key-대상키"]');
const r = el.getBoundingClientRect();
console.log({ top: Math.round(r.top), 화면높이: window.innerHeight,
              화면안: r.top >= 0 && r.top < window.innerHeight });
```

`화면안`이 `false`면 요소는 존재하지만 보이지 않는 것이다 — 8.2절의 두 결함이 정확히
