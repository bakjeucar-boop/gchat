1장. 개요

gchat 은 Google Gemini API 를 쓰는 개인용 AI 챗봇이다. Streamlit 으로 만들었고 Streamlit Community Cloud 에 배포돼 있다. 혼자 쓰려고 만든 앱이며, 무료 등급 한도 안에서 도는 것이 설계 목표였다.

1.1 일부러 없는 기능

이 앱은 없는 것이 많고 전부 이유가 있다. 그 이유를 먼저 알아야 나머지가 납득된다.

없는 것 왜 되살리려면
대화 영구 저장 (DB·파일) 개인용 앱에 저장소 코드 비중이 맞지 않았다. 그 자리에 Markdown 내보내기가 들어왔다 6.2절 「대화 영구 저장」 → 10.1절
웹 검색 그라운딩 무료 등급에서 호출 자체가 막혀 있다. 켤 때마다 실패하는 스위치가 된다 6.2절 「웹 검색 그라운딩」 → 10.3절
파일 첨부 Gemma 가 지원하지 않고, 토큰 산입도 미확인이다 10.2절
샘플링 파라미터 (temperature 등) Gemini 3.x 가 폐기했고 Gemma 는 문서에 언급조차 없다. 조절해도 아무 일이 없는 손잡이가 최악이다 3.3절 (되살릴 계획 없음)

컨텍스트 요약 압축 예산을 넘으면 요약하지 않고 오래된 턴부터 뺀다. 요약은 또 다른 호출이고 또 다른 오류원이다 5.4절

2장. 빠른 시작

저장소 첫 화면의 README.md 는 이 절차를 짧게 담고 있다. 여기서는 왜 그렇게 하는지를 함께 적는다.

2.1 로컬 실행

필요한 것은 Google AI Studio 의 API 키(무료) 하나다.

git clone https://github.com/bakjeucar-boop/gchat.git
cd gchat
pip install -r requirements.txt

.streamlit/secrets.toml.example 을 .streamlit/secrets.toml 로 복사하고 값을 채운다.

GEMINI_API_KEY = "AI Studio 에서 발급한 키"
APP_PASSWORD = "20자 이상 무작위 문자열"

이 파일은 커밋하지 않는다. .gitignore 가 막고 있고, 백업 번들에도 들어가지 않는다 — 그래서 비밀번호는 따로 보관해야 한다 (11.2절).

streamlit run app.py

Python 3.12 를 쓴다. 가상환경 없이 전역 pip 로 설치하는 것이 이 프로젝트의 관행이다. 개발까지 하려면 pip install -r requirements-dev.txt (pytest · ruff · 문서 빌드용 markdown-it-py 포함).

2.2 배포

  1. GitHub 저장소에 push
  2. https://share.streamlit.io 에서 앱 생성
    • Main file path: app.py
    • Advanced settings → Python version 3.12
  3. 같은 Advanced settings 의 Secrets 에 위 두 값을 등록한다. TOML 이므로 따옴표가 필요하다

무료 계정은 비공개 앱 1개, 공개 앱 무제한이다. 이 저장소가 공개인 이유이며, 접근은 비밀번호가 막는다.

3장. 제약 조건 — 이 앱의 설계를 지배하는 것 ★

이 앱의 코드는 절반이 "모델과 대화하는 일"이고 절반이 "한도를 넘지 않는 일" 이다. quota.py와 context.py가 존재하는 이유가 전부 이 장에 있다. 이 장을 건너뛰면 그 두 모듈이 과하게 복잡해 보인다.

3.1 무료 등급 한도

세 모델의 한도다. 값의 출처는 Google AI Studio 무료 등급이며, RPM과 TPM은 실호출로 확인했다 (7.1절).

표시명 모델 ID 계열 RPM TPM RPD
Gemini 3.5 Flash-Lite (기본) gemini-3.5-flash-lite gemini3 15 250,000 500
Gemma 4 31B gemma-4-31b-it gemma4 30 16,000 14,400
Gemma 4 26B A4B gemma-4-26b-a4b-it gemma4 30 16,000 14,400

세 한도 중 어느 것이 먼저 걸리는지가 모델마다 다르다. 이것이 설계의 출발점이다.

  • Gemini — TPM 250,000은 사실상 무제한이다. 병목은 RPD 500, 즉 하루 500번의 주고받음이다. 대화 중에는 느껴지지 않고 하루가 끝날 때 한 번 느껴진다.
  • Gemma — RPD 14,400은 넉넉하다. 병목은 TPM 16,000이며, 이건 대화 도중에 계속 느껴지는 종류다. 3.4절에서 자세히 다룬다.

이 장에서 계속 나오는 두 낱말을 먼저 정한다. 턴은 사용자 질문 하나와 모델 답변 하나를 묶은 한 번의 주고받음이고, API 요청 한 번에 해당한다. 컨텍스트 예산은 한 요청에 실어 보낼 대화 이력의 상한이며, 앱이 정하는 값이다 (모델의 컨텍스트 윈도우와 다르다 — 윈도우는 모델이 받아들일 수 있는 최대치이고, 예산은 한도를 지키려고 그보다 훨씬 낮게 잡은 우리 쪽 제한이다).

한도는 60초 슬라이딩 창으로 관리된다. 고정된 분 단위가 아니라 "지금부터 60초 전까지"의 합이므로, 창이 차면 가장 오래된 기록이 만료되는 시각까지만 기다리면 풀린다. quota.py가 대기 시간을 추정하지 않고 계산할 수 있는 이유다.

3.2 TPM은 입력 토큰만 센다

이 앱에서 가장 중요한 단일 사실이다. 계획 단계의 전제는 "한 요청이 쓰는 토큰 = 컨텍스트 예산 + 최대 출력"이었고, 그 전제가 틀렸다.

가장 직접적인 증거는 429가 스스로 밝히는 지표 이름이다.

Quota exceeded for metric:
  generativelanguage.googleapis.com/generate_content_free_tier_input_token_count,
  limit: 16000, model: gemma-4-31b
Please retry in 19.917078239s.

input_token_count. 한도 16,000은 3.1절 표의 Gemma TPM과 일치한다.

세 갈래 실험이 이를 뒷받침한다 (측정 상세는 7.1절).

실험 조건 결과
큰 입력 / 작은 출력 입력 9,012토큰을 두 번 두 번째가 429. 입력만으로 16,000을 넘겼다
작은 입력 / 큰 출력 12개 병렬, 누적 출력 19,082토큰 직후 보낸 요청이 통과
사고 켬 8개 병렬, 누적 사고 5,729토큰 (전체 16,486) 직후 보낸 요청이 통과

출력이 산입된다면 두 번째 실험에서 진작 429가 났어야 한다. 사고 토큰도 마찬가지다.

직접 확인하는 방법. 다음 명령이 위 세 실험을 그대로 재현한다. 토큰을 의도적으로 많이 쓰므로 RPD에 유의한다.

python scripts/probe_models.py tpm

출력에서 볼 것은 두 가지다. 429 본문의 지표 이름이 input_token_count인지, 그리고 큰 출력을 쏟아낸 직후의 확인 요청이 통과하는지.

따라서 코드는 이렇게 되어 있다.

  • TPM 창에 넣는 값은 prompt_token_count 하나뿐이다. record_usage_from()이 usage 객체에서 입력 토큰만 뽑으므로, 호출자가 실수로 total_token_count를 넘기는 일 자체가 불가능하다 (구조로 막는다 — 9장).
  • 최대 출력은 TPM 계산에 들어가지 않는다. 대신 다음 턴의 입력이 되어 간접적으로 예산을 채운다. 출력 상한이 컨텍스트 예산과 무관하지 않은 이유다.

단, 사고 토큰은 다른 곳에서 비용을 치른다. TPM에는 안 잡히지만 max_output_tokens 예산에서는 그대로 차감된다. 출력 한도가 좁으면 사고만 하다 잘려 빈 응답이 나온다 (7.2절 · 8.1절 「Gemma에 thinking_config를 생략」).

모델 최대 출력 65,536 32,768
앱 기본 컨텍스트 예산 32,000 9,000

샘플링 파라미터를 아예 쓰지 않는다. temperature / top_p / top_k / candidate_count는 어느 모델에도 보내지 않는다. Gemini 3.x가 이들을 폐기했고, Gemma 4는 문서에 언급 자체가 없어 동작이 불확실하다. 조절해도 아무 일이 일어나지 않는 손잡이를 화면에 두는 것이 최악이므로 ModelSpec에 필드조차 두지 않았다. 그래서 응답 성향을 바꾸는 유일한 수단이 thinking_level이다.

Gemma에는 thinking_config를 반드시 명시해야 한다. Gemini는 생략하면 minimal로 동작하지만 Gemma는 사고가 켜진 채로 동작한다. 이 차이를 모르고 생략하면 짧은 출력 한도에서 사고가 예산을 다 먹고 빈 응답이 나온다. client.py는 모든 요청에 이 값을 보낸다.

Gemma에 medium을 보내면 400이다. 전송 전에 걸러야 한다. 오류 메시지는 "이 모델은 사고 수준을 지원하지 않는다"고 말하지만 실제로는 minimal과 high가 정상 수용된다 — 문구가 오해를 부를 뿐 동작은 2단계가 맞다.

3.4 Gemma가 왜 비상용인가

Gemma는 대체 모델이 아니라 비상용(fallback) 이다. Gemini의 RPD가 소진됐거나 응답이 불안정할 때 임시로 쓰는 자리다. 이유는 TPM 16,000 하나다.

요청당 상한은 TPM의 90%로 잡는다 (여유 10%는 추정 오차와 서버 계산 차이를 위한 것).

모델 TPM 요청당 상한 (90%)
Gemini 3.5 Flash-Lite 250,000 225,000
Gemma 4 16,000 14,400

여기서 두 가지가 따라 나온다.

  • 단일 요청이 14,400토큰을 넘으면 기다려도 소용없다. 창이 비어도, 날짜가 바뀌어도 통과하지 못한다. 그래서 quota.py의 판정 우선순위에서 TOO_LARGE가 가장 앞이다 — "잠시 뒤 다시 시도하세요"라고 안내하면 거짓말이 된다.
  • 요청이 클수록 분당 횟수가 줄어든다. 예산 9,000이면 분당 1.6회다. 같은 계산이 Gemini에서는 32,000 예산에 분당 7회로, 사람이 타이핑하는 속도로는 절대 닿지 않는다.

컨텍스트 예산 슬라이더의 상한이 14,400인 것도 여기서 나온다. 이 값은 UI에 적혀 있지 않고 max_request_tokens()가 테이블에서 유도한다.

그런데 실사용에서는 이 병목이 거의 느껴지지 않는다. 다음 절이 그 이야기다.

3.5 실제 병목은 TPM이 아니라 생성 시간이다

이 프로젝트에서 가장 중요한 관측이며, 계획 단계의 판단을 여러 개 뒤집었다.

Gemma로 6턴 대화를 실제로 주고받으며 잰 결과다 (7.4절).

항목 값
TPM 대기 발생 0회
창 최대 사용률 29% (4,681 / 16,000)
한 턴 생성 시간 22~25초 (출력 768 기준)

이유는 단순하다. 생성이 느려서 60초 창이 저절로 비워진다. 한 요청이 끝나는 데 22초가 걸리면 60초 창에 많아야 2~3건이 겹친다. 사람이 답을 읽고 다음 질문을 쓰는 시간까지 더하면 TPM은 사실상 걸리지 않는다. TPM은 프로브처럼 몰아 보낼 때만 걸린다.

이 관측이 바꾼 것들이다.

  • Gemma 기본 컨텍스트 예산을 3,000에서 9,000으로 올렸다. 3,000은 실제로 걸리지 않는 병목을 피하려고 답변 길이를 희생하고 있었고, 그 결과 한 답변을 받으려면 "계속"을 서너 번 입력해야 했다.
  • 예산 슬라이더 옆 표시를 "예상 대기 시간"에서 "유지되는 대화 턴 수" 로 바꿨다. 대기 시간은 경계 아래에서 항상 0이라 사용자에게 아무 정보도 주지 못한다.
  • TPM이 병목이 되는 지점을 상수가 아니라 계산으로 정하게 됐다 (3.6절).

TPM이 실제 병목이 되려면 "TPM상 최소 간격 > 생성 시간"이어야 한다. 두 값이 만나는 지점이 경계이고, 생성 속도와 답변 길이가 그 지점을 결정한다.

3.6 무엇을 상수로 두면 안 되는가

값을 셋으로 나눠 다룬다. 이 구분이 models.py의 구조를 설명한다.

1) 서버가 정하는 값 — 테이블에 상수로 둔다. RPM·TPM·RPD, 컨텍스트 윈도우, 모델 최대 출력. 우리가 정할 수 없고 API가 바뀌기 전에는 변하지 않는다. models.py의 RateLimits와 ModelSpec에만 적고, UI·client·quota는 참조만 한다.

2) 측정으로 얻는 값 — 상수로 두되 측정일과 방법을 남긴다. 생성 속도(초당 34.2토큰), 평균 답변 길이(1,301토큰), 토큰 추정 비율(한국어 1.6자 / 영어 3.5자). 모델이 바뀌면 다시 재야 하므로 7장에 측정 방법과 함께 기록한다.

3) 앞의 값들에서 파생되는 값 — 절대 상수로 두지 않는다.

가장 대표적인 것이 TPM 병목 경계다. 이 값은 프로젝트 진행 중 12,000 → 11,000 → 9,000으로 세 번 바뀌었는데, 매번 앞선 두 종류의 값이 갱신됐기 때문이다. 상수로 두는 한 같은 수정이 계속 반복된다. 그래서 식으로 바꿨다.

경계 = (평균 답변 토큰 ÷ 초당 생성 토큰) × (요청당 상한 ÷ 60)

models.tpm_boundary_budget()이 이 식을 계산한다. 같은 식이 모델마다 다른 값을 낸다.

모델 현재 유도값
Gemma 4 31B 9,129
Gemini 3.5 Flash-Lite 142,653

평균 답변이 2,000토큰이면 Gemma 경계는 약 14,000으로 올라가고, 510토큰이면 2,877로 내려온다. 상수로는 표현할 수 없는 관계다. 코드에는 이 숫자들이 어디에도 하드코딩되어 있지 않다.

같은 이유로 "유지되는 대화 턴 수"도 상수를 쓰지 않는다. 그 대화에 모델 응답이 2턴 이상 쌓이면 실제 입력 증가폭의 평균을 쓰고, 그 전에만 기본값 1,500토큰을 쓴다 (context.tokens_per_turn()). 사용자가 시스템 인스트럭션을 길게 바꾸면 표시가 스스로 따라온다.

4장. 아키텍처

이 장은 코드에 적혀 있지 않은 것만 다룬다. 함수 시그니처와 자료구조 필드는 코드를 보면 되고, 코드는 바뀌지만 이 문서는 안 바뀐다.

4.1 의존 계층

모듈은 한 방향으로만 참조한다. 아래가 위를 부르지 않는다.

        app.py            ← 배선만. 순서가 곧 화면 배치다
          │
        ui/               ← streamlit 위젯을 직접 다루는 유일한 계층
          │                 chat.py · sidebar.py · controls.py · export_ui.py
    ┌─────┴─────┐
  export      client      ← 바깥(API·파일)과 닿는 층
    │           │
    └─────┬─────┘
        quota             ← 한도 판정. client 를 부르지 않는다 (4.5절)
          │
       context            ← 토큰 추정과 예산 절단
          │
        state             ← 대화·메시지·설정 자료구조
          │
       models             ← 값의 단일 출처. 아무것도 import 하지 않는다

auth.py는 이 사슬 밖에 있다. 인증 게이트 하나뿐이고 다른 모듈을 참조하지 않는다.

규칙 하나로 요약하면 "값은 아래에서 위로만 흐른다"이다. models는 무엇도 import하지 않고, ui는 무엇이든 import한다. 이 방향이 지켜지면 아래층 모듈은 streamlit 없이 시험할 수 있다 — 실제로 테스트 205건 중 ui를 띄우는 것은 없다.

계층을 나눈 실질적 이득은 모듈 하나를 통째로 갈아끼울 수 있다는 것이다. 다만 아래로 갈수록 교체 비용이 커진다. models는 최하층이라 값 하나만 바꿔도 위 전부가 영향을 받고, export는 위쪽 잎이라 통째로 들어내도 다른 모듈이 모른다.

예외가 하나 있다 — client다. 중간층인데도 갈아끼우기 쉽다. quota가 그것을 import하지 않고 모양만 요구하기 때문이다 (4.5절). 다른 SDK로 바꾸든 HTTP를 직접 치든 그 모양만 맞추면 된다. 계층 규칙만 보면 중간층 교체는 비싸야 하는데, 그 비용을 줄이려고 넣은 것이 Protocol이다.

모듈별 구체적인 영향 범위는 5장 각 절의 "고칠 때 함께 볼 곳"에 있다.

4.2 요청 한 번 — 정상 흐름

사용자가 질문을 보내면 다섯 단계를 거친다. 순서가 중요하다.

사용자 입력
  │
  ├─ 1. context.fit_to_budget()      예산에 맞게 이력을 자른다
  │                                   (원본은 지우지 않고 표시만 한다)
  ├─ 2. quota.precheck()             보낼 수 있는지 판정한다
  │                                   TOO_LARGE / DAILY_EXHAUSTED / WAIT / OK
  ├─ 3. quota.record_sent()          창에 기록하고 **핸들**을 받는다
  │                                   시각은 이 시점으로 고정된다
  ├─ 4. client.stream()              스트리밍으로 답을 받는다
  │                                   조각은 화면과 session_state 양쪽으로
  └─ 5. quota.record_usage_from()    핸들의 값만 실측으로 갱신한다
                                      시각은 3에서 정해진 그대로다

왜 이 순서인가.

  • 1이 2보다 먼저인 이유는 판정 대상이 잘라낸 뒤의 크기이기 때문이다. 자르기 전 크기로 판정하면 보낼 수 있는 요청을 막는다.
  • 3이 4보다 먼저인 이유는 창의 기준 시각이 전송 시각이어야 하기 때문이다. Gemma는 답 하나에 30~45초를 쓰므로, 응답 시각으로 기록하면 창이 통째로 밀린다 (8.1절 「한도 창의 기준 시각이 응답 시각으로 밀림」).
  • 5가 추정치를 실측으로 대체한다. 1의 추정은 문자 수 기반이라 오차가 있고, 서버가 돌려준 prompt_token_count가 진짜다.

4.3 실패 경로

정상 흐름만 알면 절반이다. 갈라지는 지점이 셋 있다.

                  ┌─ TOO_LARGE ──────→ 전송 안 함. 모델 전환 안내
                  │                     (기다려도 안 풀린다)
  2. precheck ────┼─ DAILY_EXHAUSTED ─→ 전송 안 함. 다른 모델 추천
                  │
                  ├─ WAIT ────────────→ 전송 안 함. 남은 시간 안내
                  │
                  └─ OK ──────────────→ 3 으로

  4. stream ──────┬─ 429 RateLimited ─→ 추적기를 **서버 기준으로 보정**
                  │                     하고 대기 안내
                  ├─ 503 ─────────────→ 다른 문구 + 재시도 버튼
                  ├─ 400 / 키 오류 ───→ 원문 JSON 없이 안내만
                  └─ 멈춤 버튼 ───────→ 스크립트가 통째로 중단됨 (아래)

세 경로의 성격이 다르다.

precheck가 막을 때 — 아직 아무것도 보내지 않았다. 사용자 입력은 대화에 남아 있으므로 "다시 시도"로 같은 입력을 재전송할 수 있다. 네 판정을 구분하는 이유는 사용자가 할 일이 다르기 때문이다. TOO_LARGE는 기다려도 날짜가 바뀌어도 풀리지 않으므로 "잠시 뒤 다시"라고 안내하면 거짓말이 된다 — 그래서 판정 우선순위에서 가장 앞이다 (3.4절).

429가 올 때 — 우리 추적기가 OK라고 했는데 서버가 거절한 경우다. 이것을 비정상 상태로 다루지 않는다. 추적기는 추정이고 서버가 최종 진실이므로, 429를 받으면 서버가 준 대기 시간으로 추적기를 보정한다. 대기 시간이 없는 429도 실재하므로 (7.1절) 그때는 자체 계산값을 쓰고 "서버가 알려주지 않았다"고 함께 알린다.

멈춤을 눌렀을 때 — 다른 둘과 종류가 다르다. 멈춤 버튼은 리런을 일으켜 실행 중인 스크립트를 통째로 중단시킨다. 예외가 아니라 실행 자체가 사라지므로 4단계 뒤의 정리 코드가 아예 돌지 않는다. 그래서 두 가지 장치가 있다.

  • 스트림 조각을 흘려보내면서 session_state에도 쌓는다. 중단돼도 남는다
  • 다음 실행의 화면을 그리기 전에 그 조각을 대화에 붙인다. 그린 뒤에 붙이면 다음 조작 때까지 안 보인다 (8.2절 「중단분이 다음 조작 전까지 안 보임」)

5단계가 돌지 않으므로 그 요청의 창 기록은 추정치로 남는다. 실측으로 대체되지 않을 뿐 기록 자체는 3단계에서 이미 남았으므로 한도 추적은 어긋나지 않는다.

4.4 상태 관리

모든 상태는 st.session_state에만 있다. 서버 파일시스템에도, 브라우저 저장소에도 쓰지 않는다. 이것은 제약이 아니라 판단이었고 (6.2절 「대화 영구 저장」), 결과가 셋 있다.

  • 새로고침하면 대화가 사라진다. 12시간 무접속 후 앱이 잠들었다 깨어날 때도 마찬가지다. 그래서 Markdown 내보내기가 v1에 들어갔다
  • 한도 추적기도 함께 사라진다. 다시 접속하면 창이 비어 있는 상태에서 시작하지만, 서버 쪽 한도는 그대로이므로 첫 요청이 429를 맞을 수 있다. 4.3절의 "429는 정상 경로"가 여기서도 쓰인다
  • 동시성 문제가 없다. 세션 하나가 자기 상태만 본다

대화 자료구조는 state.py에 있고 순수 파이썬 dataclass다. streamlit에 매여 있지 않으므로 테스트에서 그대로 만들어 쓸 수 있다.

4.5 계층을 지키는 장치

문제. quota는 API 응답에서 두 가지를 읽어야 한다 — 429의 대기 시간과 usage의 입력 토큰. 그런데 그 두 값을 만드는 곳은 client이고, client는 quota보다 위층 이다. 그대로 import하면 순환이 생긴다.

해법. quota는 client를 부르지 않고 모양만 요구한다.

@runtime_checkable
class UsageLike(Protocol):
    input_tokens: int

client.Usage가 이 모양을 만족하므로 그대로 넘길 수 있고, quota는 그 클래스의 존재를 모른다. 429 정보도 같은 방식이다.

이 구조가 준 것.

  • quota 테스트가 client를 import하지 않는다. 가짜 객체로 시험한다
  • client를 통째로 갈아끼워도 quota는 그대로다. 다른 SDK로 바꾸든 HTTP를 직접 치든, 그 모양만 맞추면 된다
  • 계층 위반이 컴파일 시점이 아니라 설계 시점에 막힌다

tests/test_quota.py에 client의_Usage와_모양이_맞는다가 있어 두 쪽이 어긋나면 실패한다. 모양으로 연결한 대가로 정적 결합이 사라졌으니, 그 대신 테스트가 계약을 지킨다.

한계도 있다. 이 방식은 quota ↔ client 한 곳에만 적용돼 있다. 다른 계층 위반은 사람이 보는 수밖에 없으며, 자동 검사는 없다.

5장. 모듈별 상세

각 모듈에 네 가지를 적는다 — 책임 / 주의점 / 고칠 때 함께 볼 곳 / 관련 절. 주의점이 이 장의 핵심이다. 나머지는 코드를 읽으면 나온다.

5.1 models.py — 값의 단일 출처

책임. 세 모델의 능력·한도·기본값을 한 테이블에 담고, 그 테이블에서 유도되는 값(요청당 상한, TPM 경계, 용도별 출력 상한)을 계산해준다. 이 모듈이 없으면 같은 숫자가 UI·client·quota에 흩어진다.

여기만 고치면 되는 것들. 이 프로젝트에서 "값은 테이블 한 곳에"를 지킨 이득이 구체적으로 이것이다.

하고 싶은 일 고칠 곳 함께 할 일
새 모델 추가 MODELS 튜플에 ModelSpec 하나 probe specs·probe thinking으로 실측 먼저 (10.5절)
한도 변경 (등급 상향 등) 해당 RateLimits 없음. 요청당 상한과 경계가 따라 움직인다
기본 컨텍스트 예산·출력 상한 조정 default_context_budget / default_max_output 없음
기본 응답 모드 변경 default_thinking_level 테스트가 계획값과 대조하므로 함께 갱신
답변 길이 문구 변경 인스트럭션 상수 다시 측정할 것 (6.3절)
용도 프리셋 문구 변경 PURPOSE_INSTRUCTIONS 없음

주의점.

  • UI·client·quota는 이 테이블의 값을 하드코딩하지 않는다. 슬라이더 상한도 max_request_tokens()로 유도하고, 대기 경고 기준선도 tpm_boundary_budget()으로 계산한다. 숫자를 다른 파일에 적는 순간 이 모듈의 존재 이유가 사라진다
  • 샘플링 파라미터 필드를 두지 않는다. 필드가 있으면 언젠가 누가 채우고, 채우면 UI에 나오고, UI에 나오면 사용자가 조절했다고 믿는다. 실제로는 아무 일도 일어나지 않는다 (3.3절)
  • default_max_output은 일상 상한이 아니라 안전장치다. 답변 길이를 실제로 정하는 것은 시스템 인스트럭션이다 (7.5절)
  • 가격 필드는 None이다. API가 단가를 주지 않아 손으로 채워야 한다 (6.4절)

고칠 때 함께 볼 곳. 이 모듈은 최하층이라 모든 것이 딸려 있다. tests/test_models.py가 테이블을 실측값·계획값에 고정하므로, 값을 바꾸면 거기서 먼저 실패한다. 그 실패가 "다른 곳도 봐야 한다"는 신호다.

관련 절. 3.1·3.3(값의 출처) · 3.6(무엇을 상수로 두면 안 되는가) · 8.1절 「모델 스펙을 문서만 보고 잘못 적음」

5.2 state.py — 대화와 설정

책임. 대화·메시지·설정 자료구조와 session_state 접근을 담당한다. streamlit에 매이지 않은 순수 함수를 최대한 분리해 두었다.

주의점.

  • 빈 대화는 최대 하나다. 새 대화 버튼도, 모델 변경도, 현재 대화가 비어 있으면 새로 만들지 않는다. 이 규칙이 없으면 목록이 빈 대화로 찬다
  • 확정된 모델(active_model_id)과 드롭다운 값(ui_model_id)이 분리돼 있다. 계열 전환 확인에서 취소를 누르면 드롭다운만 되돌려야 하기 때문이다. 둘을 하나로 합치면 취소가 동작하지 않는다
  • 제목은 자르지 않고 보관하고 표시할 때만 줄인다. 사용자가 직접 지정한 제목은 줄이지 않는다
  • 시스템 인스트럭션은 용도 프리셋에서 조합된다. 커스텀으로 넘어갈 때는 지금 문구를 그대로 남겨 이어서 고칠 수 있게 한다

고칠 때 함께 볼 곳. context(메시지를 읽는다) · client(대화를 요청으로 바꾼다) · export(대화를 문서로 바꾼다) · ui 전체. Message에 필드를 더하면 이 넷이 모두 영향권이다.

관련 절. 4.4(상태가 세션에만 있는 구조) · 6.2절 「대화 영구 저장」

5.3 quota.py — 한도 추적

책임. 60초 창과 일일 카운터를 관리하고, 보내기 전에 판정하고, 429가 오면 서버 기준으로 보정한다. 이 모듈이 없으면 앱은 한도를 모르고 429를 맞을 때까지 보낸다.

주의점.

  • 창에 넣는 값은 입력 토큰뿐이다. 그런데 이건 규칙이 아니라 구조다 — record_usage_from()이 usage 객체에서 자기가 입력 토큰을 뽑으므로 다른 값을 넣을 자리가 없다. 이 설계의 이유는 8.1절 「TPM 창에 total_token_count를 넣을 뻔함」
  • 기록의 시각은 전송 시각이다. record_sent()가 핸들을 돌려주고 보정은 그 핸들의 값만 바꾼다. 보정 시점에 시각이 갱신되면 창이 밀린다
  • 대기 시간은 추정이 아니라 계산이다. 필요한 만큼의 토큰 기록이 만료되는 시각을 찾아낸다. 그래서 "약 30초"가 아니라 정확한 초가 나온다
  • 판정 우선순위가 TOO_LARGE → DAILY_EXHAUSTED → WAIT → OK인 데는 이유가 있다. 각 판정마다 사용자가 할 일이 다르고, 기다려서 풀리지 않는 것을 먼저 알려야 한다
  • 추적기가 OK인데 429가 오는 것은 정상이다. 추정과 서버 계산이 다를 수 있고, 서버가 최종 진실이다

고칠 때 함께 볼 곳. client(429 정보와 usage의 모양 — 4.5절의 Protocol) · ui/chat.py(판정 결과를 문구로 옮기는 곳) · ui/sidebar.py(게이지). 테스트가 가짜 시계로 시나리오 7종을 돌리므로, 시간과 관련된 수정은 거기서 먼저 확인된다.

관련 절. 3.1·3.2(왜 이렇게 복잡한가) · 3.4(요청당 상한) · 6.3(경계를 유도로 바꾼 경위) · 8.1절 「TPM 창에 total_token_count를 넣을 뻔함」 · 8.1절 「한도 창의 기준 시각이 응답 시각으로 밀림」

5.4 context.py — 토큰 추정과 예산 절단

책임. 문자 수로 토큰을 추정하고, 예산을 넘으면 오래된 턴부터 컨텍스트에서 뺀다. 경계 근처에서만 실제 count_tokens를 호출한다.

주의점.

  • 추정 상수는 안전한 쪽으로 잡혀 있다. 한국어 1.6자/토큰, 영어 3.5자/토큰 모두 실측보다 토큰을 조금 많게 센다. 과소 추정은 429를 부르고 과대 추정은 조금 일찍 자를 뿐이다. 이 방향을 바꾸지 말 것 (7.4절)
  • 공백은 직전 문자의 분류를 따른다. 공백을 일괄로 영어 상수에 넣으면 한국어를 과소 추정한다 (8.1절 「공백을 영어 상수로 세어 한국어를 과소 추정」)
  • 절단은 삭제가 아니다. 컨텍스트에서 빠진 메시지도 화면과 내보내기에는 그대로 남고, 표시만 세운다. 예산을 다시 올리면 되돌아온다
  • 시스템 인스트럭션은 예산에서 먼저 차감되고 항상 유지된다
  • 실호출은 예산 경계 ±15% 안에서만 한다. 매번 부르면 요청 수가 두 배가 된다
  • 턴당 토큰은 상수가 아니라 그 대화의 실측 평균이다 (3.6절)

고칠 때 함께 볼 곳. quota(추정치를 판정에 넘긴다) · ui/chat.py(절단 안내 문구) · ui/controls.py(슬라이더의 턴 수 표시).

관련 절. 3.6(유도되는 값) · 7.4(토큰 실측) · 6.3(턴당 토큰 추정의 궤적)

5.5 client.py — API 래퍼

책임. 앱의 설정을 SDK 파라미터로 번역하고, 스트리밍으로 답을 받고, 오류를 여섯 종류로 구분해 올린다.

주의점.

  • thinking_config를 항상 보낸다. 생략하면 Gemma는 사고가 켜진 채로 동작한다 (8.1절 「Gemma에 thinking_config를 생략」)
  • 지원하지 않는 사고 수준은 보내기 전에 거른다. Gemma에 medium을 보내면 400이다
  • 샘플링 파라미터와 tools를 다루지 않는다. 테스트가 소스에 그 이름이 등장하는지 까지 검사한다 — 실수로 되살리는 것을 막기 위해서다
  • 요청의 마지막 턴이 model 역할로 끝나면 안 된다. Gemini 3.x가 400을 낸다. to_contents()가 잘라낸다
  • 스트리밍은 제너레이터이고, 토큰 수와 finish_reason은 다 받은 뒤에야 나온다. 그래서 결과 객체를 미리 넘겨 사후에 채우는 형태다
  • 오류 여섯 종을 나눈 이유는 사용자가 할 일이 다르기 때문이다. 429는 기다리고, 503은 다시 시도하고, 키 오류는 설정을 고친다. 원문 JSON은 화면에 내지 않는다

고칠 때 함께 볼 곳. quota(429 정보와 usage의 모양 — 4.5절) · ui/chat.py(예외별 화면 문구) · models(파라미터 번역의 출처).

관련 절. 3.3(모델별 능력 차이) · 7.1·7.2(오류 형태와 스펙 실측) · 8.1절 「Gemma에 medium을 보내 400」

5.6 export.py — Markdown 내보내기

책임. 대화를 Markdown 문서로 만든다. 이 모듈이 영구 저장을 대신한다 (6.2절).

주의점.

  • 본문을 다시 감싸지 않는다. 모델 답변에는 코드 블록이 들어 있으므로, 인용이 필요한 곳에서는 더 긴 울타리를 골라 중첩 펜스가 깨지지 않게 한다
  • 서버 파일시스템에 쓰지 않는다. 문자열을 만들어 다운로드 버튼에 넘길 뿐이다
  • 시각은 KST로 변환한다. 배포 서버는 UTC로 돈다 (11장)
  • 토큰 수를 "토큰"이라고 정확히 쓴다. 화면에서는 단위를 주장하지 않는 이름을 쓰지만 (8.4절), 내보낸 파일은 나중에 다시 읽는 기록이라 정확한 이름이 낫다

고칠 때 함께 볼 곳. state(대화 구조) · ui/export_ui.py(버튼).

관련 절. 6.2절 「대화 영구 저장」 · 8.4(화면과 문서의 어휘가 다른 이유)

5.7 ui/ — 화면

책임. streamlit 위젯을 직접 다루는 유일한 계층. chat(대화·입력·오류), sidebar(목록·게이지·설정), controls(설정 내용과 배지), export_ui(내보내기 버튼).

주의점. 이 계층의 함정은 대부분 8장에 사례로 있다.

  • 즉시 반응해야 하는 UI를 본문 흐름에 그대로 얹지 않는다. 대화가 길어지면 사용자는 늘 문서 맨 아래에 있어 본문 상단은 화면 밖이다. 고정하거나 조작한 위젯 옆에 그린다 (9장, 8.2절)
  • 위젯이 그려진 뒤 그 키에 대입하면 예외가 난다. 되돌리기가 필요한 조작은 on_click 콜백으로 처리한다 (8.3절)
  • 상태를 바꾸는 일은 그리기 전에 끝나야 한다. streamlit은 위에서 아래로 한 번 훑는다 (8.2절 「중단분이 다음 조작 전까지 안 보임」, 8.3절 「인증에 성공해도 비밀번호 칸이 남음」)
  • 화면 문구에 개발 용어를 쓰지 않는다. 라벨을 바꿀 때는 표시되는 숫자의 단위가 라벨과 맞는지 확인한다 (8.4절)
  • 버튼 라벨의 글자 크기는 button이 아니라 그 안쪽 p에 걸어야 한다 (7.7절)

고칠 때 함께 볼 곳. app.py(배선 순서가 곧 배치다). 이 계층에는 자동 테스트가 없으므로 브라우저에서 눈으로 확인해야 하고, 배치 관련이면 메시지 20개 이상 쌓인 긴 대화에서 봐야 한다 (12장).

관련 절. 6.2절 「설정 컨트롤의 자리」 · 8.2 · 8.3 · 8.4 전체

5.8 auth.py — 비밀번호 게이트

책임. 앱 전체를 비밀번호 하나로 막는다. 목적은 보안이 아니라 API 키 남용으로 인한 과금 방지다.

주의점.

  • st.form을 쓰는 것이 핵심이다. 키 없는 text_input은 리런마다 같은 값을 돌려주므로, 반환값을 그 자리에서 판정하면 제출과 무관한 리런에서도 실패 횟수가 올라간다 (8.3절 「키 없는 text_input이 리런마다 재평가됨」)
  • 인증 성공 시 st.rerun()이 필요하다. 안 그러면 이미 그려진 폼이 화면에 남는다
  • 비밀번호를 session_state에 저장하지 않는다. 비교는 상수 시간 함수로 한다
  • 이건 문 잠금이지 암호화가 아니다. 앱 URL은 공개이고 서버는 계속 떠 있다

고칠 때 함께 볼 곳. app.py(게이트 통과 전에는 아무것도 그리지 않는다).

관련 절. 8.3절 「인증에 성공해도 비밀번호 칸이 남음」 · 12장 검증 1번

6장. 설계 판단과 그 근거 ★

바꾸기 전에 읽는 장이다. 여기 적힌 것들은 대부분 한 번 다른 방향으로 가봤다가 돌아온 것이며, 되돌린 이유가 결론보다 중요하다.

8장과의 경계는 이렇다.

  • 8장 — 잘못돼서 고친 것. 의도대로 동작하지 않았다
  • 6장 — 틀리지 않았는데 바꾼 것. 의도대로 동작했지만 그 의도가 원하는 결과를 내지 못했다

같은 대상이 두 장에 나뉘어 들어간 경우가 있다. 계열 전환 확인이 그렇다 — 확인 절차를 두기로 한 판단은 이 장이고, 그 확인 창이 화면 밖에 그려져 안 보였던 것은 8.2절 「계열 전환 확인 창이 안 뜬다」다. 대화 목록 제목 크기도 마찬가지로, 어느 크기로 할지는 6.3절이고 CSS가 글자에 닿지 않았던 것은 8.3절이다.

6.1 확정된 판단

되돌린 적이 없고 앞으로도 유지할 것들이다. 각 판단의 근거를 함께 적는다.

판단 근거
샘플링 파라미터를 아예 전달하지 않는다 Gemini 3.x가 폐기했고 Gemma는 문서에 언급조차 없다. 조절해도 아무 일이 없는 손잡이가 최악이다 (3.3절)
응답은 항상 스트리밍한다 Gemma는 답 하나에 30~45초가 걸린다 (7.3절). 다 만들어 한 번에 주면 멈춘 것처럼 보인다
오류를 조용히 삼키지 않는다 무엇이 왜 실패했는지 보인다. 다만 원본 JSON은 접기 안으로 (8.4절)
모델별 값은 models.py 테이블에만 쓴다 하드코딩이 흩어지면 새 모델 추가가 전수 검색이 된다 (3.6절)
계열이 바뀌면 새 대화를 시작한다 컨텍스트 예산이 32,000 ↔ 9,000으로 달라져 절단이 불가피하다. 절단된 채 어색하게 잇는 것보다 끊는 편이 명확하다
내보내기는 download_button만 쓴다 서버 파일시스템에 쓰지 않는다. 배포 환경에서 그 파일은 사라지고, 남으면 그게 더 문제다
비밀번호는 게이트 하나로 끝낸다 목적이 "보안"이 아니라 API 키 남용으로 인한 과금 방지다. 그 목적에는 충분하다
Gemma는 minimal 고정이다 사고를 켜면 사고 745 + 답변 1,300 = 2,045로 상한 2,048에 부딪혀 잘린다 (7.3절). 상한을 올리면 턴당 컨텍스트가 불어나 비상용이라는 성격과 충돌한다
Gemini 기본은 medium이다 응답 모드는 한도에 영향이 없고 대가는 시간뿐이다. 바닥값을 기본으로 둘 이유가 없다 (7.3절)

유형별로 세면 실사용 4 · 실측 3 · 외부 제약 2 · 사용자 결정 2다.

만들기 전에 정한 것 중 뒤집힌 열한 건 가운데 일곱 건이 "재보거나 써봐야 알 수 있는 것"이었다. 문서를 아무리 읽어도 나오지 않는 종류다 — Gemma의 TPM이 실사용에서 걸리지 않는다는 것(8번)은 여섯 턴을 실제로 주고받아야 나왔고, popover가 무겁다는 것(1번)은 만들어서 눌러봐야 나왔다. 외부 제약 두 건도 문서에는 없었다. 무료 등급에서 검색 도구가 막혀 있다는 사실(5번)은 호출해봐야 알 수 있었고, Streamlit에 시간 기반 자동 소멸 수단이 없다는 것(6번)도 만들려다 알았다.

후임자에게 주는 함의는 이것이다. 새 판단을 세울 때 먼저 물어야 할 것은 "이건 재볼 수 있나, 써볼 수 있나"다. 잴 수 있으면 재고 나서 정하는 편이 빠르다. 이 프로젝트에서 문서만 보고 정한 값은 거의 예외 없이 한 번씩 고쳐졌다.

아래는 각 결정의 상세다.

1. 설정 컨트롤의 자리 (실사용)

세션 4에서 "설정 메뉴를 둘 만큼 항목이 없다"고 판단해 없애고, 모든 컨트롤을 입력창 위 컨트롤 바(popover)에 몰아넣었다. 세션 5 실사용에서 두 가지가 드러났다.

  • 대화 중에 모델을 바꿀 일이 거의 없다. 시작할 때 정하고 끝까지 간다. 입력창 바로 위라는 가장 좋은 자리를 거의 안 쓰는 컨트롤이 차지하고 있었다
  • popover는 열고 고르고 닫을 때마다 리런이 걸려 체감이 무겁다. 자주 안 쓰는 컨트롤일수록 이 비용이 아깝다

되돌린 뒤 배치는 조작은 사이드바, 표시는 입력창 위 배지로 나뉜다 (커밋 32e9fa7). 배지에는 조작 요소를 넣지 않는다. 그 사이 시스템 인스트럭션과 예산 슬라이더가 들어와 항목이 넷이 됐으므로, "설정 메뉴를 둘 만큼 항목이 없다"는 전제 자체도 더 이상 참이 아니었다.

2. 사이드바 항목 순서 (실사용)

하루 써보니 실제로 만지는 것은 새 대화·대화 목록·내보내기·삭제였고, 설정은 처음 한 번 정하면 거의 안 건드렸다. 자주 쓰는 것을 위로 올리고 설정을 맨 아래 접었다.

3. 제목 편집 방식 (실사용)

popover는 여는 데 리런이 한 번 더 들고, 라벨 옆에 아래꺾쇠가 붙어 보기에도 나빴다. 1번과 같은 이유다 — Streamlit에서 popover는 "가벼운 상호작용"이 아니다.

4. 메시지 복사 방식 (실사용)

처음에는 st.code로 원문을 펼쳐 보이고 Streamlit이 붙여주는 복사 아이콘을 쓰게 했다. 동작은 했지만 펼치고 다시 누르는 두 단계였다. 실사용에서 불편하다는 요청을 받아 navigator.clipboard.writeText()를 쓰는 한 번 클릭으로 바꿨다.

이 결정에는 위험이 있었다. 자동화로는 성공을 확인할 수 없어(8.7절) 사람이 눌러볼 때까지 되는지 몰랐다. 실제 판정까지 네 세션이 걸렸고, HTTPS 배포 환경에서 통과했다. 안 됐다면 st.code 방식으로 되돌리는 것이 대비책이었다.

5. 웹 검색 그라운딩 (외부 제약)

v1에 넣기로 하고 설계까지 했으나, 측정에서 무료 등급은 검색 도구를 붙이면 모델과 무관하게 즉시 429를 받는다는 것이 드러났다. 같은 시각 같은 모델에 도구만 빼면 정상 응답하므로 모델 단위 한도 소진이 아니라 검색 전용 할당량이 0인 것이다.

켤 때마다 실패하는 스위치를 두는 것이 최악이므로 v1에서 뺐다. 코드는 tools 파라미터를 아예 다루지 않는다. 되살리려면 무엇이 달라져야 하는지는 10.3절에 있다.

6. 삭제 되돌리기 지속 시간 (외부 제약)

"5초 후 자동으로 사라진다"로 설계했으나 Streamlit에는 시간 기반 자동 소멸 수단이 없다. 상호작용이 없으면 화면을 다시 그리지 않기 때문이다. 억지로 만들려면 타이머와 강제 리런이 필요한데, 그 비용이 기능의 값어치보다 크다. "다음 조작까지 유지"로 바꿨고 실사용에서 불편이 없었다.

7. 휘발성 경고 (사용자 결정)

대화가 세션에만 존재한다는 경고를 상시로 띄우기로 했다. 자리를 두 번 옮긴 끝에 (상단 고정 → 내보내기 버튼 바로 위) 화면에서 뺐다. 매번 보는 사람에게는 정보가 아니라 소음이었다. 문구 상수는 코드에 남겨 뒀다 — 되살릴 때를 위해서다.

8. Gemma 기본 컨텍스트 예산 (실측)

3,000은 "TPM 16,000이 대화를 조인다"는 전제에서 나온 값이다. 세션 4 실사용에서 그 전제가 뒤집혔다 — 여섯 턴 내내 TPM 대기가 0회였고 창 사용률은 최대 29%였다 (3.5절). 3,000은 실제로 걸리지 않는 병목을 피하려고 답변 길이를 희생하고 있었고, 그 결과 한 답변을 받으려면 "계속"을 서너 번 입력해야 했다. 9,000으로 올렸다 (커밋 9b9ce6b).

9. 예산 슬라이더 옆 표시 (실측)

처음에는 "이 예산이면 요청 사이에 몇 초 기다린다"를 보이려 했다. 8번과 같은 실측에서 기본 설정의 대기 시간은 항상 0이라는 것이 드러났다. 항상 0인 숫자는 정보가 아니다. 대신 "유지되는 대화 턴 수"를 보이고, 경계를 넘어설 때만 대기 경고를 덧붙인다.

10. Gemini 기본 응답 모드 (실측)

minimal이 API 기본값이라 그대로 뒀는데, 측정해보니 응답 모드는 한도에 전혀 영향이 없었다. 세 모드의 입력 토큰이 54로 같았다 (TPM은 입력만 센다 — 3.2절). 대가는 응답 시간 2.2초뿐이고 Gemini는 출력 상한이 넉넉해 사고 토큰이 답변 자리를 빼앗지도 않는다. 바닥값을 기본으로 둘 이유가 없어 medium으로 올렸다.

같은 측정이 Gemma에서는 반대 결론을 냈다 (6.1절). 같은 실측 한 번이 두 모델에 서로 다른 판단을 준 사례다.

11. 대화 영구 저장 (사용자 결정)

초판 설계에는 저장소 프로토콜 하나와 SQLite·Supabase 두 어댑터, 그리고 conversations / messages 테이블 스키마가 있었다. 세션 하나가 통째로 저장소 구현이었고 배포 세션에 원격 어댑터를 붙이는 일정이었다.

"영속성이 코드에서 비중이 높다면 제외해 달라"는 요청으로 v1에서 뺐다. 그 자리에 Markdown 내보내기가 신설됐고, 전체 세션 수도 일곱에서 여섯으로 줄었다. 기능 하나를 뺀 것이 아니라 앱의 성격을 바꾼 결정이다.

이 결정이 낳은 결과가 오늘의 동작이다. 12시간 무접속이면 앱이 잠들고 깨어날 때 대화가 전부 사라진다. 고장이 아니라 이 판단의 결과이며, 그래서 내보내기가 v1에 들어갔다 — 남기고 싶으면 내려받는다. 되살리는 길은 10.1절에 있다.

근거 주의. 계획서 초판은 커밋된 적이 없어 저장소에 흔적이 없다. 위 설계 내용은 사용자 기록에 따른 것이다. 저장소에서 확인되는 것은 결과뿐이다 — v1 제외 목록과 export.py의 존재.

6.3 여러 번 고친 값과 그 궤적

여섯 개의 값이 두 번 이상 바뀌었다. 되돌린 값을 지우지 않고 궤적 그대로 남긴다 — 최종값만 보면 왜 그 값인지 알 수 없기 때문이다.

값 궤적 고친 횟수
Gemma 최대 출력 2,048 → 768 → 1,536 → 2,048 → 4,096 → 2,048 (코딩만 4,096) 5
TPM 병목 경계 12,000 → 11,000 → 9,100 → 유도식 3
답변 길이 인스트럭션 없음 → 상한만 제시 → 상한과 하한을 함께 2
턴당 토큰 추정 600 → 1,750 → 용도별 상수 → 대화 실측 평균 3
Gemma 기본 예산 3,000 → 9,000 1
대화 목록 제목 크기 16px → 14px → 12px → 10px → 11px 4

Gemma 최대 출력 — 왜 다섯 번이나 고쳤나

이 값이 대표 사례다. 궤적을 따라가면 매번 다른 이유였다.

값 왜 바꿨나
2,048 (초안) 문서를 보고 잡은 잠정값
768 TPM은 입력만 센다는 실측 후. 출력은 TPM을 쓰지 않지만 다음 턴의 입력이 되어 예산을 채운다. 768이라야 예산 3,000에서 "약 5턴"이 성립한다
1,536 예산을 9,000으로 올린 뒤 768이 너무 좁아졌다. 한 답변에 "계속"을 서너 번 쳐야 했다
2,048 목표 답변 길이가 1,000~1,500토큰인데 상한 1,536은 목표 상단과 너무 가까워 잘림이 생겼다
4,096 코딩 답변의 코드가 끊긴다는 실사용 신고
2,048 (코딩만 4,096) 범용 답변까지 4,096을 허용할 이유가 없다. 용도별로 나눴다

다섯 번 고친 이유는 이 값이 다른 세 값에 매여 있었기 때문이다 — 컨텍스트 예산, 목표 답변 길이, 용도. 셋 중 하나가 움직일 때마다 이 값도 따라 움직여야 했다. 마지막에야 "용도별로 다른 값"이라는 형태를 찾았고, 그 뒤로는 안 고쳤다.

최종값 2,048만 보면 아무것도 알 수 없다. 왜 4,096이 아닌지(범용에 그만큼이 필요 없어서), 왜 1,536이 아닌지(목표 상단과 가까워 잘려서)는 궤적에만 있다. 이것이 되돌린 값을 지우지 않는 이유다.

TPM 병목 경계 — 어떻게 끝냈나

같은 값을 세 번 고쳤다는 점에서는 위와 같지만, 끝낸 방식이 다르다.

값 왜 바꿨나
12,000 생성 속도를 초당 30토큰으로 가정해 계산
11,000 생성 속도를 실측하니 33.1이었다
9,100 평균 답변 길이가 1,301토큰으로 안착하면서 경계가 내려왔다
유도식 상수를 버리고 계산으로 바꿨다

세 번 모두 "입력이 바뀌어서" 고쳤다. 경계는 생성 속도와 답변 길이에서 나오는 값인데, 그 둘이 측정될 때마다 경계도 다시 계산해야 했다. 상수로 두는 한 이 수정은 끝나지 않는다.

네 번째에 식으로 바꿨다.

경계 = (평균 답변 토큰 ÷ 초당 생성 토큰) × (요청당 상한 ÷ 60)

그 뒤로는 한 번도 고치지 않았다. 답변 길이가 바뀌면 경계가 알아서 따라오고, 모델마다 다른 값이 같은 식에서 나온다 (7.6절). 앞의 최대 출력 사례와 대비된다 — 그쪽은 마지막에 형태를 바꿔서 끝났고(단일 값 → 용도별 값), 이쪽은 종류를 바꿔서 끝났다(상수 → 유도).

값을 세 번 이상 고치고 있다면 다음 수정을 하기 전에 물어볼 만하다. 이 값은 무엇에서 나오는가. 그것을 식으로 쓸 수 있는가.

답변 길이 인스트럭션 — 세 번의 측정

문구를 두 번 고쳤고, 매번 같은 질문 3개로 측정했다 (7.5절).

문구 평균 출력 잘림
없음 1,221토큰 (968~1,542) 3턴 중 1턴
1차 — 상한만 제시 435토큰 없음
2차 — 상한과 하한을 함께 1,301토큰 (1,144~1,447) 없음

1차 문구는 "2,000자 이내"였고 그것은 약 1,250토큰에 해당한다. 결과는 435토큰, **지시의 38%**였다. 문구가 작동하지 않은 것이 아니라 너무 잘 작동했다 — "간결하게"와 "불필요한 서론·요약·반복을 넣지 않는다"에 강하게 반응했다.

2차에서 목표를 범위로 주고 "너무 짧게 줄이지 말고" 라는 하한을 넣자 목표 대역에 들어왔고, 편차도 절반으로 줄었다(574 → 303).

인스트럭션 없이도 평균은 비슷하다(1,221 대 1,301). 다른 것은 편차와 잘림이다. 지금 이 문구의 역할은 답을 짧게 만드는 것이 아니라 길이를 목표 대역에 묶어 두는 것이다.

문구를 고칠 때 조심할 것. 상한만 주면 결과가 그 아래 어디에 놓일지 알 수 없다. 그리고 문구 변경은 컴파일도 테스트도 되지 않으므로, 고쳤으면 다시 재야 한다. 1차 개정 때 재지 않았다면 "지시대로 2,000자 이내에 들어왔다"고 만족했을 것이다.

턴당 토큰 추정 — 상수의 수명

600 → 1,750 → 용도별 상수 → 대화 실측 평균. 앞의 두 값은 "출력 상한을 매 턴 다 채운다"는 가정에서 나왔고, 시스템 인스트럭션이 들어오면서 그 가정이 깨졌다. 실측에서 턴당 증가가 인스트럭션 유무에 따라 445와 1,080으로 갈렸다 (7.4절).

TPM 경계와 같은 방식으로 끝냈다 — 상수를 버리고 그 대화의 실제 증가폭 평균을 쓴다. 모델 응답이 2턴 이상 쌓이기 전에만 기본값 1,500을 쓴다.

대화 목록 제목 크기 — 네 번 고친 다른 이유

16px → 14px → 12px → 10px → 11px. 앞의 사례들과 달리 이 값은 판단이 흔들려서가 아니라 측정이 틀려서 여러 번 고쳐졌다. 14px과 12px 단계에서는 CSS가 실제 글자에 닿지 않아 화면이 바뀌지 않았다 (8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」). 10px까지 내려간 뒤 11px로 한 단계 올린 것만이 실제 취향 조정이다.

궤적을 남기는 것은 같지만, 이 경우 읽는 사람이 알아야 할 것은 "왜 11px인가"가 아니라 "측정 대상을 잘못 고르면 네 번을 고쳐도 안 바뀐다" 는 쪽이다.

6.4 판단 보류 항목

정하지 않은 채로 둔 것들이다. 정보가 부족해서이며, 운영하면서 채운다.

항목 왜 보류인가 무엇이 있으면 정할 수 있나
RPD 리셋 시각 하루 이상 관찰이 필요해 세션 안에서 확인할 수 없었다. 문서 근거는 태평양 자정이고 코드도 그 기준이다 실사용 중 일일 한도 429를 만났을 때의 quotaId와 retryDelay
가격 필드 API가 단가를 돌려주지 않는다 (7.2절). 현재 None이라 비용 표시가 비어 있다 공개 가격표를 보고 손으로 입력. 무료 등급만 쓰면 필요 없다
턴 수 표시의 체감 정확도 계산은 맞지만 사용자가 느끼는 것과 맞는지는 써봐야 안다 며칠 실사용 후의 느낌
멈춤 후 "계속"의 자연스러움 기능은 동작한다. 중단 지점이 문장 중간일 때 이어붙인 글이 매끄러운지는 읽어야 안다 실사용 판정 (8.7절)
"코딩은 Gemini 권장" 안내 실측에서 Gemma도 잘리지 않아 근거가 없었다 (7.5절). 다만 Gemma는 4.4배 느리다 느려서 불편하다는 실사용 피드백이 쌓이면
승급 후보 2건 8.8절의 보류 항목 — 문서 동기화 검사와 라벨-단위 검사 문서 동기화는 계획서 이동이 끝난 뒤, 라벨-단위는 오탐을 줄일 방법이 생기면

보류를 보류로 적어 두는 것도 판단이다. 근거 없이 정하면 다음 사람이 그 값을 근거 있는 것으로 오해하고 그 위에 무언가를 쌓는다.

7장. 실측 기록 ★

문서로만 알던 값과 실제가 여러 번 달랐다. 이 장은 실호출로 확인한 값만 담는다. 각 값에 측정일·측정 방법·다시 재야 하는 시점을 붙인다. API 모델은 바뀌므로 "언제 잰 값인가"가 값 자체만큼 중요하다.

7.0 측정 도구와 원본 기록

측정 도구는 scripts/probe_models.py 하나다. 서브커맨드로 나뉜다.

python scripts/probe_models.py sdk         # SDK 표면 (API 호출 없음)
python scripts/probe_models.py list        # 사용 가능한 모델 목록
python scripts/probe_models.py specs       # 모델별 컨텍스트·출력 상한
python scripts/probe_models.py tokens      # count_tokens — 언어별 자/토큰
python scripts/probe_models.py stream      # 스트리밍 동작
python scripts/probe_models.py thinking    # thinking_level 수용값
python scripts/probe_models.py turns       # 한국어 대화의 턴당 토큰 증가
python scripts/probe_models.py tpm         # TPM 산정 기준 (3.2절의 세 실험)
python scripts/probe_models.py grounding   # 웹 검색 그라운딩 가용성
python scripts/probe_models.py modes       # 응답 모드별 토큰·시간·잘림

두 번째 인자로 파일 경로를 주면 결과 JSON을 그 파일에도 쓴다. tpm과 turns, modes는 토큰을 의도적으로 많이 쓰므로 RPD에 유의한다.

원본 관측 기록: docs/archive/api_findings.md. 429 응답 전문, 실험별 조건과 원시 수치가 그 파일에 있다. 이 장은 그것을 재가공한 요약이며, 세부가 필요하면 원본을 본다. 이 원본은 2026-08-13자 관측에서 동결됐고 갱신하지 않는다.

재측정을 쌓는 규칙. 모델이 바뀌어 다시 측정하면 원본을 고치지 않고 docs/archive/api_findings_YYYYMMDD.md로 새 파일을 만든다. 이 장은 항상 최신값만 유지한다. 옛 값은 이 장에서 지우고 날짜별 원본에만 남긴다. 7장의 존재 이유가 "모델이 바뀌면 다시 재야 하는 값"이므로, 여기에 낡은 값과 새 값이 함께 있으면 목적을 잃는다.

생성 속도는 세 번 독립적으로 측정돼 수렴했다.

Gemini는 훨씬 빠르다 — 1,346토큰을 6.9초에 냈으니 초당 약 195토큰으로 Gemma의 5.6배다 (2026-08-16, 실사용 1회). 코딩처럼 긴 출력이 필요한 작업에서 두 모델의 체감이 갈리는 지점이다.

응답 모드는 한도에 영향을 주지 않는다. 대가는 시간뿐이다.

모델 모드 입력 사고 답변 시간 잘림

읽을 것은 세 가지다.

  • 입력 토큰이 모드와 무관하게 같다. Gemini 세 모드가 모두 54였다. TPM은 입력만 세므로 (3.2절) 모드를 올려도 한도 소비가 늘지 않는다. 명령 출력에 _input_tokens_identical_per_model 항목으로 이 판정이 함께 나온다.
  • 대가는 응답 시간이다. Gemini는 minimal 대비 medium이 2.2초 더 걸린다. 기본값을 medium으로 둔 근거가 이것이다.
  • Gemma는 사고를 켜면 잘린다. 사고 745 + 답변 1,300 = 2,045로 출력 상한 2,048에 부딪혔다. Gemma가 minimal 고정인 이유가 이론이 아니라 실측으로 확정된 지점이다.

다시 재야 하는 시점. 모델 버전이 올라갈 때. 생성 속도가 바뀌면 3.6절의 경계가 함께 움직이므로, 속도를 다시 잰 뒤에는 GENERATION_TOKENS_PER_SECOND를 갱신한다.

콜드 부팅 시간은 미측정이다 (초 단위 기록 없음). 12시간 슬립 후 첫 접속에서 상당한 시간이 걸리고, 로그가 멈춘 것처럼 보이는 구간이 길다. 재부팅과 새로고침을 반복하면 프로비저닝이 매번 처음부터 다시 시작되어 오히려 더 안 뜬다. 다음 슬립이 자연히 발생하면 그때 재서 채운다.

버튼 라벨의 글자 크기를 다룰 때 주의할 점이 하나 있다. Streamlit은 라벨을 버튼 안쪽 markdown 컨테이너의 p 요소로 그리고, 그 p가 font-size를 16px로 다시 잡는다. button에만 크기를 걸면 상자만 줄고 글자는 그대로다 (8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」).

8장. 트러블슈팅 사례집 ★

겪은 것만 적는다. 일반적인 Streamlit 요령이나 API 사용법은 없다. 이 프로젝트에서 실제로 난 33건과, 자동화로는 판정할 수 없어 사람이 봐야 했던 3건이다.

각 사례는 다음 형식이다. 알아챈 방법을 반드시 붙였다 — 특히 8.1절은 예외도 안 나고 화면도 멀쩡한 부류라, 다음 사람이 같은 증상을 알아채는 단서가 이 장의 값어치다.

  • 증상 — 겉으로 무엇이 보였는가
  • 알아챈 방법 — 어떻게 발견했는가 (우연이면 우연이라고 적는다)
  • 원인 — 실제로 무엇이 잘못됐는가
  • 해법 — 무엇을 고쳤는가
  • 재발 방지 — 등급과 내용
  • 근거 — 커밋·파일·테스트

  • 어디까지 확인했는가 — iframe에 clipboard-write 권한이 있고 보안 컨텍스트도 참이라는 것까지는 확인했다. 성공 여부만 확인하지 못했다.
  • 최종 판정 — 사람이 눌러 통과. 로컬(localhost)은 보안 컨텍스트가 자동 통과라 판정이 되지 않았고, HTTPS 배포 환경의 확인이 진짜 판정이었다. 네 세션을 끌었다.
  • 재발 방지 (D) — 없다. 확인 절차를 12장에 둔다.

시각적 배치 (C)

  • 어디까지 확인했는가 — 요소의 좌표를 재는 방식으로 판정 가능해졌다. 존재 여부만 보면 통과하지만 좌표를 보면 화면 밖인 것이 드러난다.
  • 최종 판정 — 통과 (긴 대화 상태에서 확인).
  • 재발 방지 (C) — 12장에 수동 확인 절차를 뒀다. 스크립트로 만들지 않은 이유는 브라우저 자동화 의존성을 상시로 들일 만큼 자주 쓰지 않기 때문이다.

문장이 자연스러운가 (D)

  • 왜 자동화가 안 되는가 — 멈춤 뒤 "계속"으로 이어받은 글이 매끄러운지는 읽어야 안다. 중단 지점이 문장 중간이면 어색할 수 있다.

9장. 작업 원칙

9.1 값을 다루는 원칙

모델별 값은 models.py 테이블에만 쓴다. 어디서 왔나 — 3.6절. 같은 숫자가 여러 파일에 있으면 새 모델 추가가 전수 검색이 된다. 슬라이더 상한도 UI에 적지 않고 max_request_tokens()로 유도한다. 지금 코드에 경계값 하드코딩은 0건이다.

바뀔 값은 상수가 아니라 유도로 둔다. 어디서 왔나 — 6.3절 「TPM 병목 경계 — 어떻게 끝냈나」. 같은 값을 12,000 → 11,000 → 9,100으로 세 번 고쳤고, 세 번 모두 "입력이 바뀌어서"였다. 네 번째에 식으로 바꾼 뒤로는 한 번도 고치지 않았다. 값을 세 번 이상 고치고 있다면 그 값이 무엇에서 나오는지 묻고, 식으로 쓸 수 있는지 본다.

측정한 값에는 측정일과 방법을 붙인다. 어디서 왔나 — 7장 전체. 모델은 바뀌고 그때 다시 재야 하는데, 언제 어떻게 잰 값인지 모르면 다시 잴 수도 없다.

9.2 잘못할 자리를 없애는 원칙

주석으로 막지 말고 구조로 막는다. 어디서 왔나 — 8.1절의 A등급 세 건. 셋 다 "조심하자"로 끝낼 수 있었지만 구조를 바꿨다.

  • record_usage_from()이 usage에서 입력 토큰을 자기가 뽑는다. 호출자가 total을 넘길 자리가 없다
  • record_sent()가 핸들을 돌려주고 보정은 그 값만 바꾼다. 시각을 건드릴 자리가 없다
  • 비밀번호는 st.form 안에서만 판정한다. 제출하지 않은 리런에서 실패가 쌓일 자리가 없다

막을 수 없으면 테스트로 잡는다. 어디서 왔나 — 8.1절의 B등급 다섯 건. 구조로 못 막는 것은 잘못하면 실패하게 만든다. client.py가 샘플링 파라미터를 쓰지 않는다는 것은 소스에 그 이름이 등장하는지까지 검사한다.

소스를 검사하는 테스트는 변형 시험으로 검출을 확인하기 전까지 믿지 않는다. 어디서 왔나 — 8.8절 승급 작업. 소스 검사는 동작 테스트와 달리 "통과했다"가 "안전하다"를 뜻하지 않는다. 위반을 하나 심어 넣고 실제로 실패하는지 본 뒤에야 그 테스트를 신뢰한다. 실제로 위젯 키 검사를 ui/ 로만 한정했다면 대상이 0건이라 언제나 통과하는 테스트가 될 뻔했고, 변형 시험이 아니었다면 그대로 남았을 것이다. 같은 이유로 각 소스 검사에는 무엇을 못 잡는지를 주석으로 적는다.

측정할 때는 무엇을 재는지 정확히 고른다. 어디서 왔나 — 8.3절 「버튼 라벨의 글자 크기가 안 줄어듦」. 버튼 요소의 글자 크기를 재고 "줄었다"고 두 번 보고했지만, 실제 글자는 그 안쪽 요소에 있었다. 잘못 고른 측정은 통과 판정을 만들어내므로 측정하지 않는 것보다 나쁘다.

문서와 코드가 어긋나면 고치기 전에 보고한다. 어디서 왔나 — 8.6절. 이 프로젝트에서 실제로 쓴 방식이고 잘 작동했다. 조용히 맞추면 어느 쪽이 옳았는지가 사라진다.

10장. 확장하려면

v1에서 뺀 것들이다. 각 항목에 먼저 읽을 절, 첫 손댈 파일, 걸리는 것을 적었다. 설계와 조사가 이미 있으니 그 지점부터 시작한다.

10.1 대화 영구 저장

먼저 읽을 절 — 6.2절 「대화 영구 저장」. 왜 뺐는지가 거기 있다. 기능이 어려워서가 아니라 개인용 앱에 코드 비중이 맞지 않아서였고, 그 자리에 Markdown 내보내기가 들어왔다.

첫 손댈 파일 — 새 모듈 하나(store.py)와 state.py. 대화를 읽고 쓰는 지점이 state.py에 모여 있으므로, 그 함수들이 저장소를 거치게 바꾸는 것이 시작이다.

걸리는 것.

  • 계층상 위치를 먼저 정해야 한다. 저장소는 바깥과 닿으므로 client와 같은 층이 맞고, state가 그것을 직접 부르면 계층이 뒤집힌다. quota ↔ client에서 쓴 Protocol 방식이 그대로 참고가 된다 (4.5절)
  • session_state만 있다는 전제가 코드 곳곳에 깔려 있다 (4.4절). 동시성 문제가 없다는 가정, 한도 추적기가 세션과 함께 사라진다는 가정이 그것이다
  • 내보내기와 역할이 겹친다. 영구 저장이 들어오면 export.py의 위치를 다시 정해야 한다
  • 접근 통제가 비밀번호 하나뿐이다 (5.8절). 데이터가 서버에 남으면 그 수준으로 충분한지 다시 판단해야 한다

10.2 파일 첨부

먼저 읽을 절 — 3.3절 모델별 능력 차이. Gemma는 파일 입력을 지원하지 않는다.

첫 손댈 파일 — client.py의 요청 조립부와 ui/chat.py의 입력부. models.supports_file_input이 이미 있으므로 UI 게이팅은 그 값으로 한다.

걸리는 것.

  • 모델 전환과 충돌한다. Gemini에서 파일을 붙인 대화를 Gemma로 옮기면 그 첨부는 보낼 수 없다. 계열 전환이 새 대화를 시작하는 지금 규칙이 이 문제를 반쯤 덮어주지만, 계열 내 전환은 이력을 유지하므로 별도 처리가 필요하다
  • 토큰 산입이 미확인이다. PDF 페이지당·이미지 타일당 실제 토큰 수를 재지 않았다. count_tokens로 확인할 수 있고, 그 값이 예산 계산에 들어가야 한다 (3.4절)
  • 파일 크기와 형식 제한, 업로드한 파일의 수명도 확인 대상이다

10.3 웹 검색 그라운딩

먼저 읽을 절 — 6.2절 5번과 7.2절. 무료 등급에서는 호출 자체가 막혀 있다 — 검색 도구를 붙이면 모델과 무관하게 즉시 429가 오고, 같은 시각 도구만 빼면 정상 응답한다. 모델 단위 한도 소진이 아니라 검색 전용 할당량이 0인 것이다.

전제 — 유료 전환이 필요하다. 이 항목만은 코드를 고쳐서 될 일이 아니다. 결제를 붙이지 않으면 켜는 순간 실패하는 스위치가 된다. 10.4절을 함께 본다.

첫 손댈 파일 — client.py의 build_config(). 지금은 tools 파라미터를 아예 다루지 않으며, 테스트가 소스에 GoogleSearch와 tools=가 등장하는지까지 검사한다. 되살리려면 그 테스트부터 고쳐야 한다 — 실수로 되살아나는 것을 막으려고 넣은 장치이므로, 의도적으로 되살릴 때는 그 의도가 테스트에 드러나야 한다.

걸리는 것.

  • 출처 표시 의무를 확인해야 한다. 검색 결과를 쓰면 그것을 화면에 표시할 요건이 따라붙는 것으로 알려져 있으나, 이 프로젝트에서 확인하지 않았다. 되살리기 전에 API 문서에서 확인할 것
  • 분기 자체는 간단하다. 측정에서 grounding_metadata는 속성이 항상 존재하고 값이 None임을 확인했다 (7.2절). 출처 영역 표시 여부는 이 값 하나로 갈린다
  • 과금 필드가 미확인이다. 검색 쿼리 과금이 응답의 어느 필드로 잡히는지 그라운딩 응답을 한 번도 받지 못해 확인할 수 없었다. 유료 전환 후 재측정 대상이다
  • Gemma는 도구를 거부하지 않지만 검색하지도 않는다. 200이 오지만 grounding_metadata가 항상 None이다. Gemini 전용으로 두는 것이 맞다
  • TPM 영향도 재측정 대상이다. 검색 결과가 입력에 합쳐지면 입력 토큰이 늘어난다 (3.2절)

10.4 유료 전환 시

먼저 읽을 절 — 7.1절(한도)과 7.2절(가격이 조회되지 않는다는 것).

첫 손댈 파일 — models.py. 두 가지가 한 곳에서 끝난다.

  • price_in_per_mtok / price_out_per_mtok를 공개 가격표에서 채운다. API가 단가를 돌려주지 않으므로 손으로 넣어야 한다
  • RateLimits를 새 등급 값으로 바꾼다. 요청당 상한과 TPM 경계는 따라 움직인다 (5.1절)

걸리는 것.

  • 한도가 올라가면 3장의 전제 일부가 바뀐다. Gemma가 비상용인 이유가 TPM 16,000이었으므로 (3.4절), 그 값이 달라지면 모델 배치를 다시 판단할 여지가 생긴다
  • 비용 표시는 값이 채워지면 바로 살아나지만, 사고 토큰을 출력으로 볼지 결정해야 한다 (7.2절)
  • 검색 그라운딩이 열린다 (10.3절)

10.5 새 모델 추가

먼저 읽을 절 — 5.1절 「여기만 고치면 되는 것들」. 코드 수정은 models.py의 MODELS에 ModelSpec 하나를 더하는 것으로 끝난다.

표에 없는 것이 하나 더 필요하다 — 실측이다. 새 모델의 값은 문서만 보고 채우면 안 된다 (8.1절 「모델 스펙을 문서만 보고 잘못 적음」). 다시 재야 할 항목은 다음과 같다.

11장. 운영

11.1 배포와 재배포

배포 절차는 2장에 있다. 여기서는 다시 배포할 때 주의할 것을 적는다.

  • 앱을 지우고 새로 만들면 URL이 바뀐다. 그리고 Secrets를 다시 등록해야 한다 — 앱 설정에 넣은 값은 저장소가 아니라 그 앱에 붙어 있다
  • Python 버전을 3.12로 명시한다. 기본값이 더 높으면 의존성 설치가 어긋날 수 있다
  • Secrets는 TOML이므로 값에 따옴표가 필요하다. 빠뜨리면 앱은 "키가 없다"고 안내한다
  • 첫 접속 점검 순서 — 설치 로그 3줄(streamlit·google-genai·tzdata) → 비밀번호 화면이 먼저 나오는지 → 틀린 비밀번호로 잠금 안내 → 맞는 비밀번호로 입장 → 질문 하나 → 내보낸 md의 시각이 KST인지 (서버는 UTC로 돈다)

git push는 사람이 해야 한다. 자격 증명 관리자가 GUI 로그인 창을 띄우므로 비대화형 셸에서는 끝나지 않는다. 최초 1회 이후에는 캐시돼 창 없이 진행된다 (8.5절 「git push가 에이전트 셸에서 끝나지 않는다」).

11.2 백업

git bundle create ../gchat-backup/gchat_YYYYMMDD_HHMM.bundle --all
git bundle verify ../gchat-backup/gchat_YYYYMMDD_HHMM.bundle

번들 하나에 전체 이력이 들어간다. verify가 "complete history"라고 답하면 그 파일만 있으면 저장소를 복원할 수 있다.

주의 — .streamlit/secrets.toml은 번들에 들어가지 않는다. 추적 대상이 아니기 때문이다(그것이 맞다). 따라서 API 키와 앱 비밀번호는 따로 보관해야 한다. 백업을 복원해도 이 둘이 없으면 앱은 뜨지 않는다. 키는 발급처에서 다시 만들 수 있지만 앱 비밀번호는 그렇지 않다.

11.4 문서 빌드

기술서는 Markdown이 원본이고 HTML은 거기서 생성한다.

python scripts/build_docs.py            # docs/gchat_기술서.html 갱신
python scripts/build_docs.py --check    # 갱신이 필요한지만 확인

HTML 은 단일 파일 자체 완결형이다. CSS 를 문서 안에 넣고 외부 링크를 걸지 않으므로 인터넷 없이 열리고, 파일 하나만 보내면 그대로 읽힌다. 목차는 제목에서 자동으로 만들고 앵커는 절 번호에서 뽑으므로(s-3-2 같은 형태) 문장을 다듬어도 링크가 깨지지 않는다.

드리프트를 테스트로 막는다. md 를 고치고 HTML 을 다시 만들지 않으면 tests/test_docs.py 가 실패한다. 이 프로젝트가 반복해서 겪은 문서 어긋남(8.6절)을 같은 방식으로 두지 않으려는 것이다.

그러려면 같은 md 에서 언제나 같은 HTML 이 나와야 한다. 생성 시각을 넣으면 매번 달라지므로 그렇게 하지 않았다.

  • 본문과 목차는 md 내용만으로 결정된다
  • 하단에 md 의 내용 해시(SHA-256 앞 16자)를 적는다. 이 값은 결정론적이다
  • 원본 커밋 해시와 커밋 시각은 git 에서 읽으므로 실행 환경에 따라 달라질 수 있다. 그 줄에는 data-volatile 표시를 달았고, 비교할 때 그 줄만 제외한다

같은 검사를 명령으로도 할 수 있다 — --check 는 갱신이 필요하면 1을 돌려준다.

12.3 긴 대화에서만 재현되는 항목

메시지 20개 이상 쌓인 상태에서 봐야 하는 것들이다. 짧은 대화에서는 통과한다.

  • 멈춤 버튼이 화면 안에 있는가 (스트리밍 중)
  • 계열 전환 확인 창이 보이는가 (모델을 바꾼 직후, 스크롤을 올리지 않은 채)
  • 컨텍스트 절단 안내가 뜨는가
  • 새로 추가한 즉시 반응 UI가 보이는가

앞의 둘은 실제로 짧은 대화에서 재현되지 않아 배포 후에야 잡혔다 (8.2절).

## 원칙

값을 다루는 원칙 (기술서 9.1절)

- 모델별 값은 `gchat/models.py` 테이블에만 쓴다. UI·client·quota는 참조만 하고

- **바뀔 값은 상수가 아니라 유도로 둔다.** 같은 값을 세 번 이상 고치고 있다면
  그 값이 무엇에서 나오는지 묻고 식으로 쓸 수 있는지 본다 (TPM 경계가 그 사례다).

## 제약 (기술서 3장)

- **TPM은 입력 토큰만 센다** (실측). 창 추적에는 `prompt_token_count`만 쓰고
  `total_token_count`는 표시용으로만 쓴다. 출력과 사고 토큰은 TPM에 안 잡히지만
  `max_output_tokens` 예산에서는 차감된다.
- Gemma는 **모든 요청에 `thinking_config`를 명시**한다. 생략하면 사고가 켜진 채로
  동작해 짧은 출력 한도에서 빈 응답이 나온다.
- Gemma에 `medium`을 보내면 400이다. 전송 전에 걸러진다.
- 실제 병목은 TPM이 아니라 **생성 시간**이다. Gemma는 답 하나에 30~45초가 걸려
  60초 창이 저절로 비워진다.
- 응답은 항상 스트리밍한다.
