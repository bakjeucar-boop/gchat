## 1. 대상 모델

### 1.1 모델 목록과 한도

| 표시명 | 모델 ID | 계열 | RPM | TPM | RPD |
|---|---|---|---|---|---|
| **Gemini 3.5 Flash-Lite** (기본) | `gemini-3.5-flash-lite` | Gemini 3.x | 15 | 250,000 | 500 |
| Gemma 4 31B | `gemma-4-31b-it` | Gemma | 30 | 16,000 | 14,400 |
| Gemma 4 26B A4B | `gemma-4-26b-a4b-it` | Gemma | 30 | 16,000 | 14,400 |

**기본 선택 모델은 Gemini 3.5 Flash-Lite다.**

각 모델의 병목이 서로 다르다는 점이 설계의 출발점이다.

- **Gemini 3.5 Flash-Lite** — TPM은 넉넉하나 **RPD 500이 하루 병목**이다. 하루 500회 대화 턴이 상한.
- **Gemma 4 (양쪽 모두)** — RPD는 매우 넉넉하나 **TPM 16,000이 치명적 병목**이다.
  - 단일 요청이 16,000 토큰을 넘으면 **무조건 실패**한다
  - 요청당 8,000 토큰을 쓰면 분당 2회밖에 못 보낸다
  - 즉 Gemma에서는 긴 대화를 이어가는 것 자체가 물리적으로 어렵다

### 1.2 샘플링 파라미터 — 전면 미사용 (결정)

**`temperature` / `top_p` / `top_k` / `candidate_count`는 어느 모델에도 전달하지 않는다.**

- Gemini 3.x는 이들을 공식 폐기했다. 현재는 무시되고 향후 모델에서는 HTTP 400을 반환한다.
- Gemma 4는 Gemini API 문서의 Gemma 페이지에 이 파라미터가 **언급되지 않는다.**
  동작 여부가 불확실한 값을 UI에 노출하면 사용자가 조절했다고 믿는데 실제로는
  아무 일도 일어나지 않는 최악의 상황이 된다.

따라서 **응답 성향을 조절하는 유일한 수단은 `thinking_level`이다.**

| 모델 | 선택지 | 기본값 |
|---|---|---|
| Gemini 3.5 Flash-Lite | `minimal` / `medium` / `high` (3단계) | `minimal` |
| Gemma 4 (26B / 31B) | `minimal` / `high` (끄기 / 켜기) | `minimal` |

- Gemini 3.x에는 "사고 없음"이 없다. `minimal`이 바닥값이며 완전 비활성화는 불가능하다.
  `minimal`은 3.5 Flash-Lite의 API 기본값이다. **Gemma는 다르다 — 아무것도 지정하지
  않으면 사고가 켜진 채로 동작한다 (세션 2 실측 A-4). `client.py`는 모든 요청에
  `thinking_config`를 명시적으로 보낸다.**
- Gemma 4는 켜기/끄기만 지원한다 (`medium` 없음).
- **사고 토큰은 TPM에 산입되지 않는다** (세션 2 실측으로 확정, 1.4절). 다만 두 가지는
  여전히 영향받는다: (1) `max_output_tokens` 예산에서 차감되므로 출력 한도가 작으면
  사고만 하다 잘려 빈 응답이 나올 수 있고, (2) 응답 생성 시간이 늘어 체감 지연이
  커진다. Gemma는 비상용 성격상 기본 꺼짐(`minimal`)을 유지한다 — 지연·출력 예산
  관점만으로도 충분한 근거다.

이 결정으로 `ModelSpec`에서 `supports_sampling` 필드는 불필요해진다.

### 1.3 모델 스펙 테이블 (코드로 구현)

`gchat/models.py`에 선언적 테이블을 두고, UI·API 호출·한도 관리자가 모두 이것을 참조한다.
새 모델 추가 시 이 테이블만 수정하면 되도록 한다.

```python
@dataclass(frozen=True)
class RateLimits:
    rpm: int
    tpm: int
    rpd: int

@dataclass(frozen=True)
class ModelSpec:
    id: str
    label: str
    family: str                       # "gemini3" | "gemma4"
    is_default: bool
    thinking_levels: tuple[str, ...]  # ("minimal","medium","high") | ("minimal","high")
    default_thinking_level: str       # 항상 "minimal"
    supports_system_instruction: bool
    default_system_instruction: str   # 모델별 기본 인스트럭션 (2.6.2절). 없으면 ""
    supports_file_input: bool         # 2.9절 — v1에서는 UI 게이팅용으로만 사용
    max_output_tokens: int            # 모델 상한
    context_window: int
    limits: RateLimits
    default_context_budget: int       # 아래 1.4절
    default_max_output: int
    price_in_per_mtok: float | None
    price_out_per_mtok: float | None
```

사고 수준의 표시 라벨은 계열별로 다르므로 별도 매핑을 둔다.

```python
THINKING_LABELS = {
    "gemini3": {"minimal": "빠름", "medium": "보통", "high": "깊게"},
    "gemma4":  {"minimal": "사고 끄기", "high": "사고 켜기"},
}
```

### 1.4 모델별 컨텍스트 토큰 예산 (TPM 대응)

**세션 2 실측으로 확정됨** (`docs/api_findings.md` B절). 429 오류가 스스로 밝히는
지표 이름이 `generate_content_free_tier_input_token_count`였다 — **TPM은 입력
토큰만 센다. 출력도, 사고 토큰도 산입되지 않는다.** 큰 출력을 병렬로 쏟아부은
직후에도 곧바로 보낸 요청이 통과하는 것으로 직접 확인됐다.

| 모델 | 기본 컨텍스트 예산 (=TPM 소비) | 기본 최대 출력 | 분당 가능 횟수 (TPM상) |
|---|---|---|---|
| Gemini 3.5 Flash-Lite | 32,000 | 4,096 | 약 7회 (TPM 225,000 가용 기준) |
| Gemma 4 31B | **9,000** | **2,048** | 약 1.6회 (TPM 14,400 가용 기준) |
| Gemma 4 26B A4B | **9,000** | **2,048** | 약 1.6회 |

**Gemma 값은 세션 4 실사용 후 3,000·768에서 위 값으로 상향했다.**
근거는 세션 4의 예상 밖 관측이다 — **6턴 대화 내내 TPM 대기가 0회였고
창 사용률이 최대 29%에 그쳤다.** 생성에 22~25초가 걸려 60초 창이 저절로
비워지기 때문이다. 즉 **사용자가 겪는 간격은 TPM이 아니라 생성 시간이
지배한다** (1.5절). 3,000·768은 실제로 걸리지 않는 병목을 피하려고 답변
길이를 희생하고 있었고, 그 결과 한 답변을 받으려면 "계속"을 3~4번
입력해야 했다.

출력 1,536토큰은 생성에 약 50초가 걸린다(실측 초당 약 30토큰). 예산 9,000의
TPM상 최소 간격은 37.5초이므로 **생성 시간이 더 길어 TPM은 여전히 걸리지
않는다.** 예산 12,000부터 두 값이 50초로 만나 비로소 TPM이 병목이 되므로,
9,000이 안전 여유를 남긴 상한선이다.

턴당 컨텍스트 증가는 약 1,750토큰(사용자 입력 약 200 + 출력 1,536)이므로
예산 9,000에서 **온전한 길이의 답변으로 약 5턴**이 유지된다. 이전 설정
(3,000·768)의 4턴보다 턴 수도 늘고 답변도 잘리지 않는다.

**Gemma 최대 출력을 1,536 → 2,048로 재상향했다 (세션 5 후).**
목표 답변 길이가 1,000~1,500토큰(2.6.2절)이므로 상한 1,536은 목표 상단과
너무 가까워 잘림이 생긴다. 2,048이면 1,500토큰 답변에 여유가 남는다.

상한은 어디까지나 안전장치이고, 실제 길이를 정하는 것은 모델별 기본 시스템
인스트럭션이다 (2.6.2절). 위 "잘리지 않는다"는 그 인스트럭션이 목표 범위
안에서 작동하는 것을 전제로 한 값이다.

**Gemma 4의 모델 자체 상한은 컨텍스트 262,144 / 출력 32,768이다**
(문서마다 256K·1M로 엇갈리던 부록 B-5가 262,144로 확정됨). 위 9,000·1,536은
이 상한과 무관하게 **비상용 성격과 TPM 여유에 맞춰 앱이 정한 기본값**이다.
Gemini 3.5 Flash-Lite의 상한은 컨텍스트 1,048,576 / 출력 65,536이다.

**Gemma는 비상용(fallback) 모델로 자리매김한다.**
Gemini의 RPD가 소진되었거나 응답이 불안정할 때 임시로 쓰는 용도이며,
4~5턴 정도의 짧은 대화를 온전히 주고받을 수 있으면 충분하다는 것이 설계
목표였다. 위 설정으로 **약 5턴에 답변 잘림 없음**이 되어 목표를 충족한다.

- 사용자가 컨트롤 바에서 예산을 올릴 수 있으나, **Gemma에서 컨텍스트 예산이
  TPM의 90% (14,400 토큰)를 넘으면 슬라이더를 그 지점에서 막고 사유를 표시한다.**
  (출력은 이 계산에 포함하지 않는다 — 위 확인 사항 참조)
- 대화가 길어져 예산을 초과하면 오래된 턴부터 제거한다 (2.2절).
- **Gemma에 `thinking_config`를 생략하면 안 된다.** 생략 시 모델이 사고 모드로
  동작해(끄기가 기본이 아님) 짧은 `max_output`에서는 사고 토큰이 출력 예산을
  전부 삼켜 빈 응답이 나온다 (세션 2 A-4). `client.py`는 모든 요청에
  `thinking_config`를 명시적으로 보낸다.

### 1.5 어느 한도가 실제로 문제인가 (설계 근거)

| 한도 | 실질 영향 | 판정 |
|---|---|---|
| **RPM** | 사람이 타이핑해 분당 15~30회를 보낼 수 없다. 다만 롤링 60초 윈도우라 프로브처럼 짧은 시간에 여러 요청을 몰아 보내면 쉽게 닿는다 (세션 2에서 실제 발생) | 대화 중에는 무시해도 됨 |
| **RPD** | Gemini 500회가 하루 상한. **태평양 시간 자정(한국시간 오후 4~5시경, DST에 따라 다름)에 초기화되는 것으로 문서에 나와 있으나, 하루 이상 관찰이 필요해 실측으로는 확인하지 못했다** (부록 B). 소진 시 Gemma(14,400회)로 전환하면 됨 | 하루가 끝나는 사건. 대화 중 마찰 아님 |
| **TPM** | 입력 토큰만 소비한다. Gemma 16,000이 세 모델 중 가장 좁지만, **세션 4 실사용에서 6턴 내내 한 번도 걸리지 않았다** (창 사용률 최대 29%) | **실사용에서는 병목이 아니다** — 아래 참조 |

**핵심 발견 (세션 4) — 실제 병목은 TPM이 아니라 생성 시간이다**

이 프로젝트는 "Gemma의 TPM 16,000이 대화를 조인다"는 전제 위에 설계됐다.
세션 4 실사용에서 그 전제가 뒤집혔다.

- 6턴 대화 내내 TPM 대기가 **0회**, 창 사용률 최대 **29%**
- 이유: Gemma는 768토큰 출력에 22~25초가 걸린다. 60초 창이 저절로 비워진다
- 즉 사용자가 겪는 간격은 **TPM 대기가 아니라 응답 생성 시간**이다

TPM이 실제 병목이 되려면 "TPM상 최소 간격 > 생성 시간"이어야 한다.
세션 5에서 생성 속도를 실측했다 — **초당 33.1토큰** (계획서 가정 30보다 빠름).
출력 1,536이면 약 **46초**다.

| Gemma 예산 | TPM상 최소 간격 | 출력 1,536의 생성 시간 | TPM이 병목인가 |
|---|---|---|---|
| 3,000 | 12.5초 | 약 46초 | 아니오 (여유 큼) |
| 6,000 | 25초 | 약 46초 | 아니오 |
| **9,000 (기본)** | **37.5초** | **약 46초** | **아니오 (여유 남음)** |
| **약 11,000** | **약 46초** | 약 46초 | **경계 — 여기서부터 걸리기 시작** |
| 14,400 (상한) | 60초 | 약 46초 | 예 |

**경계는 12,000이 아니라 약 11,000이다** (세션 5 실측으로 정정).
기본 예산 9,000은 여전히 경계 아래에 여유를 두고 있다.

**예산별 유지 가능한 대화 — 턴당 토큰은 고정값이 아니다**

당초 이 표는 "출력 1,536을 매 턴 다 채운다"고 보고 턴당 1,750토큰으로 계산했다.
세션 5 실측에서 그 전제가 깨졌다 — **기본 시스템 인스트럭션이 켜진 상태의
실제 턴당 증가는 약 445토큰**이다(2.6.2절). 1,750으로 계산하면 예산 9,000이
"약 5턴"으로 표시되지만 실제로는 **약 20턴**이다. 4배 차이로 과소 예고한다.

| 상황 | 턴당 증가 | 예산 9,000에서 |
|---|---|---|
| 개정 전 인스트럭션 (과소 생성) | 약 445토큰 | 약 20턴 |
| **개정 후 목표 (1,000~1,500토큰 답변)** | **약 1,450토큰** | **약 6턴** |
| 인스트럭션 없음 | 약 1,300토큰 | 약 7턴 |
| 출력 상한 2,048을 매 턴 채우는 최악 | 약 2,250토큰 | 약 4턴 |

**따라서 턴 수 표시는 상수가 아니라 현재 대화에서 계산한다.**

- 대화에 model 응답이 2턴 이상 쌓이면 **그 대화의 실제 평균 턴 크기**로 계산한다
- 그 전(새 대화)에는 기본값 **1,450토큰**을 쓴다 (개정 후 목표 기준)
- 이렇게 하면 사용자가 인스트럭션을 지우거나 길게 쓰라고 바꿔도 표시가
  스스로 따라온다. 상수를 계속 고쳐 맞출 필요가 없다

슬라이더 범위는 1,000 ~ 14,400, 기본값 9,000, 500 단위.

**컨트롤 바의 예산 슬라이더 옆 표시는 "예상 대기 시간"이 아니라
"유지되는 대화 턴 수"여야 한다.** 대기 시간은 11,000 미만에서 항상 0이라
사용자에게 아무 정보도 주지 못한다. 대신 11,000을 넘어서면 그때부터
"이 값부터는 요청 사이에 대기가 생깁니다"를 함께 띄운다.

Gemini 3.5 Flash-Lite는 TPM 250,000이라 위 계산에서 완전히 자유롭다.
32,000 예산에서도 TPM상 분당 7회가 가능해 생성 시간이 언제나 먼저 걸린다.

## 2. 기능 요구사항

### 2.1 대화 (필수)

- **멀티턴 컨텍스트 유지** — 매 요청에 대화 이력을 `contents` 배열로 전송한다.
- **스트리밍 출력** — `client.models.generate_content_stream()` + `st.write_stream()`
- **모델 전환 — 계열이 바뀌면 새 대화를 시작한다** (2.1.1절)
- **금지** — 요청의 마지막 턴을 `model` 역할로 끝내지 않는다 (Gemini 3.x에서 400 오류).

### 2.1.1 모델 전환 규칙

계열(`family`)이 바뀌면 컨텍스트 예산이 32,000 ↔ 9,000으로 달라져 절단이
불가피하다. 절단된 채 어색하게 이어가는 것보다 **새 대화로 끊는 편이 명확하다.**

| 전환 | 동작 |
|---|---|
| `gemini3` ↔ `gemma4` (계열 변경) | 확인 후 **새 대화 시작** |
| `gemma-4-31b-it` ↔ `gemma-4-26b-a4b-it` (계열 내) | 이력 유지, 확인 불필요 |

계열 내 전환은 한도·예산·지원 파라미터가 동일해 절단이 발생하지 않으므로 굳이 끊지 않는다.

**전환 확인 절차**

계열이 다른 모델을 선택하면 즉시 전환하지 않고 확인 단계를 띄운다.

> **모델 계열을 바꾸면 새 대화가 시작됩니다.**
> 현재 대화 12개 메시지는 새 대화로 이어지지 않습니다.
> 대화 내용은 이 세션 안에서만 보관되므로, 필요하면 지금 Markdown으로 내려받으세요.
>
> `[Markdown으로 저장]` `[저장했음 · 전환]` `[취소]`

**이전 대화는 삭제하지 않고 사이드바 목록에 그대로 남긴다.**
사용자는 언제든 다시 열어보고 나중에 내보낼 수 있다. 세션이 끝나면 어차피 사라지므로
굳이 즉시 지울 이유가 없고, 실수로 백업을 놓쳤을 때 복구 여지가 된다.

**구현 주의**

- `st.selectbox`는 선택 즉시 값이 바뀌므로, 취소를 누르면 **드롭다운을 이전 모델로
  되돌려야 한다.** `session_state`에 확정된 모델(`active_model_id`)과 UI 선택값을
  분리해 관리하고, 확인 완료 시에만 `active_model_id`를 갱신한다.
- 새 대화는 직전 대화의 응답 모드와 시스템 인스트럭션을 이어받되,
  컨텍스트 예산은 새 모델의 기본값으로 초기화한다.
  응답 모드가 새 모델에 없는 값이면 `minimal`로 되돌린다.
- `[Markdown으로 저장]`은 `st.download_button`이므로 클릭해도 페이지가 리런된다.
  다운로드 후에도 확인 단계가 유지되도록 상태를 관리할 것.

### 2.2 컨텍스트 윈도우 관리

`gchat/context.py`

- 모델별 토큰 예산(1.4절)을 초과하면 **오래된 턴부터 user/model 쌍 단위로 제거**
- 시스템 인스트럭션은 항상 유지
- 절단 발생 시 UI에 명시: "앞선 8개 메시지가 컨텍스트에서 제외됨 (모델 한도)"
  — 절단된 메시지도 화면과 MD 내보내기에는 그대로 남는다. 컨텍스트에서만 빠진다
- 토큰 추정: 문자 수 기반 1차 추정(**한국어 1.6자/토큰, 영어 3.5자/토큰** — 세션 2
  실측 확정치. 실측은 한국어 1.63~1.70, 영어 3.63이었고, 영어 3.5는 실측보다
  토큰을 조금 많게 세는 안전한 방향이다)으로 판정하고, 예산 경계 ±15% 구간에서만
  `count_tokens()` 실호출
- 단일 사용자 입력 하나만으로 예산을 넘는 경우 → 전송을 막고
  "이 입력은 <모델>의 요청당 한도를 넘습니다. Gemini 3.5 Flash-Lite로 전환하세요" 안내

### 2.3 한도 관리 (핵심 기능)

`gchat/quota.py`

**추적 방식**

세션 상태에 모델별 사용량을 기록한다.

```python
class QuotaTracker:
    # 모델별로 유지
    requests: deque[float]            # 최근 60초 요청 타임스탬프
    tokens: deque[tuple[float, int]]  # 최근 60초 (타임스탬프, 입력 토큰수) — TPM은 입력만 셈 (1.4절)
    daily_requests: int               # 당일 요청 수
    daily_reset_at: datetime          # 태평양 시간 자정 기준 (1.4절)
```

- 요청 **전**: 추정 토큰(=전송할 컨텍스트 크기)으로 사전 판정. 출력 예상치는 TPM
  판정에 넣지 않는다 (1.4절 — TPM은 입력 전용)
- 요청 **후**: 응답의 `usage_metadata.promptTokenCount`로 실제 입력 토큰 수를
  기록해 보정. `candidatesTokenCount`(출력)는 TPM 추적에는 반영하지 않되,
  비용 표시(2.8절)에는 그대로 사용한다
- 안전 여유: 모든 한도의 **90%**를 실사용 상한으로 삼는다
- 429를 실제로 받으면 `quotaId` 문자열로 어느 한도에 걸렸는지 구분한다
  (`...PerMinute...` → RPM/TPM, `...PerDay...` → RPD — 세션 2 B-3 실측).
  `retryDelay`가 없는 429도 실재하므로(세션 2 C-2), 파싱 실패 시 초 단위
  안내 없이 "서버가 대기 시간을 알려주지 않았습니다"로 처리한다
- `usage_metadata`의 각 필드는 `None`일 수 있다 (세션 2 A-6) — 0으로 다룬다.
  TPM 추적에는 `prompt_token_count`만 쓰고, `total_token_count`(입력+출력+사고
  합계)는 비용·표시용으로만 쓴다

**사전 판정 결과 4가지**

| 결과 | 조건 | UI 동작 |
|---|---|---|
| `OK` | 여유 있음 | 그대로 전송 |
| `WAIT(n초)` | RPM 또는 TPM 초과 | 카운트다운 표시 + "n초 후 자동 전송" / "다른 모델로 지금 보내기" 버튼 |
| `DAILY_EXHAUSTED` | RPD 소진 | 전송 차단, 여유 있는 모델 추천 + 원클릭 전환 버튼 |
| `TOO_LARGE` | 단일 요청이 TPM 자체를 초과 | 전송 차단, 모델 전환 또는 대화 새로 시작 안내 |

**모델 추천 로직**

차단 시 여유가 있는 모델을 골라 제시한다. 판단 순서:

1. RPD 여유가 있는 모델만 후보
2. 그중 이번 요청의 추정 토큰이 TPM 여유 안에 들어가는 모델
3. 후보가 여럿이면 기본 모델(Gemini 3.5 Flash-Lite) 우선
4. 후보가 없으면 가장 빨리 풀리는 모델과 대기 시간을 안내

안내 메시지 예:

> Gemma 4 31B의 분당 토큰 한도(16,000)에 도달했습니다. 42초 후 다시 사용할 수 있습니다.
> 지금 바로 보내려면 **Gemini 3.5 Flash-Lite**로 전환하세요. (오늘 잔여 372회)

**대기 시간 사전 예고 — 필요할 때만 표시 (세션 4 이후 조정)**

당초 계획은 Gemma 사용 중 대기 시간을 상시 예고하는 것이었다. 그러나 세션 4
실사용에서 **기본 설정으로는 대기가 0회**임이 확인됐다(1.5절). "대기 없이 전송
가능"을 매 턴 띄우는 것은 정보가 아니라 소음이다.

따라서 **대기가 실제로 예상될 때만** 입력창 위에 표시한다.

> (대기가 예상될 때만) 다음 요청까지 약 18초 남았습니다

TPM은 60초 슬라이딩 윈도우이므로, 필요한 만큼의 토큰 기록이 만료되는 시각을
계산하면 정확한 대기 시간을 알 수 있다. 추정이 아니라 계산으로 낼 것.
대기가 0이면 아무것도 표시하지 않는다.

**사이드바 상시 표시**

현재 선택 모델의 잔여량 3종을 진행바로 표시한다.
RPM과 RPD는 부가 정보이고, **Gemma에서는 TPM 게이지를 가장 크게·위에 배치한다.**

```
Gemini 3.5 Flash-Lite
  분당 요청  ██░░░░░░░░   2 / 15
  분당 토큰  ███░░░░░░░  38K / 250K
  일일 요청  █░░░░░░░░░  128 / 500
```

**반드시 지킬 정직성 원칙**

- 이 추적기는 **추정치**다. 실제 할당량은 API 키 단위로 모든 세션·기기에 걸쳐 공유되며,
  앱이 재시작되면 카운터가 0으로 초기화되어 실제보다 적게 셀 수 있다
- **서버가 반환하는 429가 최종 진실이다.** 429를 받으면 응답의 `retry_delay`를 파싱해
  추적기를 서버 기준으로 보정하고, "실제 한도에 먼저 도달했습니다"라고 알린다
- 추적기가 OK라고 판정했는데 429가 나는 상황을 정상 동작으로 간주하고 처리할 것

### 2.4 대화 이력 — 세션 한정

**영구 저장은 구현하지 않는다.** 모든 대화는 `st.session_state`에만 존재한다.

- 여러 대화를 만들 수 있고 사이드바에서 전환한다 (최신순)
- 개별 삭제 (되돌리기 제공 — **다음 조작 시까지** 유지. 당초 "5초"로 적었으나
  Streamlit에는 시간 기반 자동 소멸 수단이 없어 세션 4에서 조정)
- 일괄 삭제 (2단계 확인: 체크박스 + 버튼, 되돌리기 없음)

**제목 표시 (세션 5 실사용 후 개정)**

첫 사용자 메시지에서 자동 생성하되 목록에서 읽기 쉽게 줄인다.

- **20자로 자르고 넘치면 뒤에 `…`을 붙인다** (기존 30자 전체 노출은 너무 길었다)
- 줄바꿈은 공백으로 바꾸고 앞뒤 공백을 정리한다
- **글자 크기를 본문보다 작게** 표시한다 (`st.caption` 수준). 대화 목록은
  훑어보는 곳이지 읽는 곳이 아니다
- 수동 변경 가능. 사용자가 지정한 제목은 자르지 않는다
- 전체 제목은 툴팁(`help=`)으로 볼 수 있게 한다

**빈 대화는 만들지 않는다 (세션 5 실사용 후 추가)**

메시지가 하나도 없는 상태에서 모델을 바꾸면 "새 대화"가 목록에 쌓이는
문제가 있었다. 다음 규칙으로 막는다.

- 계열 전환 시 **현재 대화가 비어 있으면** 확인 절차를 건너뛰고 새 대화도
  만들지 않는다. 지금 있는 빈 대화의 모델만 교체한다
- "새 대화" 버튼을 눌렀을 때 현재 대화가 이미 비어 있으면 새로 만들지 않고
  그대로 둔다
- 요약하면 **빈 대화는 언제나 최대 1개**만 존재한다

**휘발성 경고 — 사이드바 맨 아래 (세션 5 실사용 후 이동)**

브라우저 새로고침, 탭 닫기, 앱 대기 상태 전환 시 대화가 모두 사라진다.

### 2.4.1 메시지 복사 (세션 5 실사용 후 추가)

내보내기(2.5절)는 대화 전체를 파일로 받는 기능이고, 답변 한 조각을 다른
곳에 옮길 때는 과하다. **메시지 단위 복사**를 따로 둔다.

- 각 메시지(사용자·모델 양쪽) 아래에 작은 **복사 버튼**을 둔다
- 복사되는 것은 화면에 렌더링된 HTML이 아니라 **원본 Markdown 텍스트**다.
  코드 블록·목록·표가 그대로 살아 있어야 다른 곳에 붙일 때 쓸모가 있다
- 토큰 수·지연 시간 같은 메타 정보는 복사에 포함하지 않는다

**구현 방식**

Streamlit의 컴포넌트 iframe에는 `clipboard-write` 권한이 부여되어 있으므로
`st.components.v1.html`에 `navigator.clipboard.writeText()`를 쓰는 버튼을
넣으면 동작한다. 복사 후 "복사됨" 표시를 잠깐 띄운다.

이 방식이 환경에 따라 실패하면 **대안은 `st.code(content, language=None)`**
이다. Streamlit이 코드 블록에 기본 복사 아이콘을 붙여주므로 추가 구현 없이
같은 목적을 달성한다. 다만 본문이 코드 스타일로 보이므로,
`st.expander("복사용 원문")` 안에 넣어 평소에는 접어 둔다.

**어느 쪽을 쓸지는 세션 6에서 실제로 동작을 확인한 뒤 정한다.**
자바스크립트 방식이 되면 그쪽이, 안 되면 `st.code` 대안이 채택된다.

### 2.5 Markdown 내보내기 (필수)

`gchat/export.py` — `st.download_button` 사용. 서버에 파일을 쓰지 않으므로
Streamlit Cloud의 휘발성 파일시스템과 무관하다.

**두 가지 버튼**

1. **현재 대화 저장** — 채팅 화면 상단 우측

   - 파일명: `gchat_전체_20260813_1430.md`
   - 대화들을 `---` 구분선으로 이어붙인다

**출력 형식**

```markdown

### 2.6 컨트롤 배치 — 사이드바 설정으로 되돌린다 (세션 5 실사용 후 개정)

**개정 사유.** 세션 4에서 설정 메뉴를 없애고 모든 컨트롤을 입력창 위
컨트롤 바(popover)에 몰아넣었다. 세션 5 실사용에서 두 가지가 확인돼
되돌린다.

1. **대화 중 모델을 바꿀 일이 거의 없다.** 대화를 시작할 때 정하고 끝까지
   간다. 입력창 바로 위라는 가장 좋은 자리를 거의 안 쓰는 컨트롤이 차지하고
   있었다.
2. **Streamlit의 반응 속도가 popover 상호작용을 따라오지 못한다.** 열고
   고르고 닫을 때마다 리런이 걸려 체감이 무겁다. 자주 안 쓰는 컨트롤일수록
   이 비용이 아깝다.

**따라서 배치를 이렇게 나눈다.**

| 위치 | 내용 | 성격 |
|---|---|---|
| **사이드바 "설정"** | 모델 · 응답 모드 · 컨텍스트 예산(Gemma) · 시스템 인스트럭션 | **조작** |
| **입력창 위 배지** | 현재 모델 · 현재 응답 모드 · 맥락 사용량 | **표시 전용 (읽기만)** |

세션 4에서 "설정 메뉴를 둘 만큼 항목이 없다"고 판단해 없앴는데, 그 뒤
시스템 인스트럭션과 예산 슬라이더가 들어오면서 네 항목이 됐다. 지금은
사이드바 한 섹션을 채울 만하다.

### 2.6.1 입력창 위 배지 — 표시 전용

클릭해서 펼치는 popover가 아니라 **한 줄 상태 표시**다.

```
Gemini 3.5 Flash-Lite · 빠름 · 맥락 12/32,000
```

```
Gemma 4 31B · 사고 끄기 · 맥락 3,200/9,000
```

- 지금 어떤 모델이 어떤 수준으로 답하고 있는지만 알린다
- 조작 요소를 넣지 않는다. 바꾸려면 사이드바 설정으로 간다
- 대기 시간은 대기가 실제로 예상될 때만 오른쪽에 덧붙인다 (2.3절).
  대기가 0이면 아무것도 표시하지 않는다

### 2.6.1.1 사이드바 "설정" 섹션

| 컨트롤 | 형태 | 노출 조건 |
|---|---|---|
| 모델 | selectbox | 항상 |
| 응답 모드 | radio (모델별 선택지, 1.2절) | 항상 |
| 컨텍스트 예산 | slider 1,000~14,400 (500 단위) + **유지되는 대화 턴 수** 실시간 표시. 11,000 초과 시 대기 발생 경고 병기 (1.5절) | Gemma일 때만 |
| 시스템 인스트럭션 | text_area (2.6.2절) | 항상 |

기본은 접힌 `st.expander`로 두되, 대화가 하나도 없는 첫 화면에서는 펼쳐
둔다 (처음 쓰는 사람이 모델을 고르는 자리를 찾아야 하므로).

**동작 규칙**

- 응답 모드·예산·시스템 인스트럭션 변경은 **세션을 초기화하지 않는다.**
  다음 요청부터 적용된다
- 모델 **계열** 변경만 새 대화를 시작한다 (2.1.1절)
- **단, 현재 대화가 비어 있으면(메시지 0개) 확인 절차를 건너뛰고 새 대화도
  만들지 않는다.** 지금 있는 빈 대화의 모델만 바꾼다 (2.4절 참조)
- 취소 시 드롭다운이 이전 모델로 되돌아가야 한다
  (`active_model_id`와 UI 선택값 분리)
- 모델 변경으로 현재 응답 모드가 새 모델에 없으면 (Gemini `medium` → Gemma)
  `minimal`로 되돌리고 그 사실을 표시한다
- 컨텍스트 예산을 **줄일 때만** "현재 대화에서 N개 메시지가 컨텍스트에서
  제외됩니다"를 먼저 표시하고 적용한다

### 2.6.2 시스템 인스트럭션 — 대화 속성

- 새 대화를 시작할 때 접힌 입력란으로 제공한다. 비워두면 사용하지 않는다
- 진행 중인 대화에서도 컨트롤 바 popover 하단에서 편집할 수 있다
  (컨텍스트에 영향이 없으므로 초기화 불필요)
- 설정되어 있으면 대화 상단에 회색 한 줄로 요약 표시한다
- Markdown 내보내기의 frontmatter 아래 인용 블록으로 포함한다

**모델별 기본 시스템 인스트럭션 (세션 5 추가)**

세션 4 실사용에서 모델별 답변 길이가 크게 달랐다.

| 모델 | 자연 답변 길이 | 판정 |
|---|---|---|
| Gemini 3.5 Flash-Lite | 약 1,000토큰 | 적당함. 개입 불필요 |
| Gemma 4 (26B / 31B) | **약 3,000토큰** | 장황함. 개입 필요 |

**`max_output_tokens`로는 이 문제를 해결할 수 없다.** 2.6절에 적은 원칙 그대로,
그 값은 자르는 칼이지 짧게 쓰게 만드는 손잡이가 아니다. 상한을 1,536으로 두면
결과는 "1,500 이하의 답변"이 아니라 "3,000짜리 답변이 절반에서 잘린 것"이다.
실제로 생성 길이를 바꾸는 유일한 수단은 시스템 인스트럭션이다.

따라서 `ModelSpec`에 `default_system_instruction` 필드를 두고, 모델별로 다른
기본값을 갖게 한다.

| 모델 | 기본값 |
|---|---|
| Gemini 3.5 Flash-Lite | 비어 있음 |
| Gemma 4 (양쪽) | `"답변은 보통 1,600~2,400자 정도로 충분히 설명한다. 너무 짧게 줄이지 말고, 필요한 근거와 예시는 포함한다. 다만 같은 내용을 반복하거나 형식적인 서론·맺음말은 넣지 않는다."` |

동작 규칙:

- **화면에 보이고 수정 가능해야 한다.** 숨겨서 몰래 덧붙이면 사용자가
  "왜 이렇게 답하지?"를 추적할 수 없다. 컨트롤 바의 시스템 인스트럭션
  칸에 그대로 채워 넣는다
- 사용자가 직접 편집한 적이 있으면(`system_instruction_customized` 플래그)
  모델을 바꿔도 덮어쓰지 않는다. 편집한 적이 없을 때만 모델 기본값을 채운다
- 새 대화 시작 시: 사용자가 편집한 값이 있으면 그것을 이어받고,
  없으면 새 모델의 기본값을 채운다
- `max_output_tokens`(Gemma 1,536)는 그대로 두되, 이제 **일상적 상한이 아니라
  안전장치**로 기능한다. 인스트럭션이 통하면 대부분 여기 닿지 않는다.
  자주 닿는다면 인스트럭션 문구를 조정한다

**세션 5 실측 — 효과는 확실하나 크게 과했다**

| 항목 | 인스트럭션 없음 | 있음 | 변화 |
|---|---|---|---|
| 평균 출력 | 1,221토큰 | **435토큰** | −64% |
| 1,536 상한 도달 | 3턴 중 1턴 | **0턴** | 해소 |

실사용에서는 300~400토큰까지 떨어져 **쓰기에 너무 짧다**는 판단이다.
목표는 **출력 1,000~1,500토큰**이다.

**단위 혼동을 바로잡는다.** 첫 문구의 "2,000자"는 한국어 기준 약 1,250
**토큰**이다(2.2절 상수 1.6자/토큰). 목표인 1,000~1,500 토큰은 글자로
환산하면 **1,600~2,400자**다. 즉 첫 문구는 목표 자체를 낮게 잡고 있었고,
거기서 모델이 다시 38%로 줄여 300~400토큰이 나온 것이다.

과소 생성의 원인은 두 가지로 본다.
1. 모델이 "이내"를 상한이 아니라 **목표**로 읽고 그 아래로 크게 내려간다
2. "불필요한 서론·요약·반복을 넣지 않는다"가 압축을 더 밀어붙였다

**따라서 문구를 위 표대로 다시 개정했다.**
- 목표를 글자 기준 **1,600~2,400자**로 올렸다 (= 1,000~1,500토큰)
- "이내"라는 상한 표현을 버리고 "정도로 충분히 설명한다"로 바꿨다
- **"너무 짧게 줄이지 말고"라는 하한 지시를 명시적으로 넣었다.**
  이것이 이번 개정의 핵심이다 — 상한만 주면 모델은 계속 아래로 간다
- 금지 조항은 "같은 내용 반복 / 형식적 서론·맺음말"로 좁혔다

LLM은 글자 수를 정확히 지키지 못하므로 이는 정확한 값이 아니라
**경향을 바꾸는 지시**다. 세션 6에서 재측정해 1,000~1,500토큰 구간에
들어오는지 확인하고, 여전히 짧으면 범위를 더 올린다 (부록 B).

### 2.6.3 사이드바 구성 (위에서 아래로)

1. **새 대화** 버튼
2. **설정** expander (2.6.1.1절 — 모델·응답 모드·예산·시스템 인스트럭션)

5. **일괄 삭제** (2단계 확인)
6. **휘발성 경고** (2.4절)
7. **Markdown 내보내기** (현재 대화 / 전체 대화)

6·7번을 붙여 두는 것이 핵심이다 — 경고를 읽은 자리에서 바로 내려받을 수 있다.

### 2.7 접근 통제 (비밀번호)

`gchat/auth.py`

```python
import hmac, streamlit as st

def check_password() -> bool:
    if st.session_state.get("authed"):
        return True
    pw = st.text_input("비밀번호", type="password")
    if pw:
        if hmac.compare_digest(pw, st.secrets["APP_PASSWORD"]):
            st.session_state["authed"] = True
            return True
        st.error("비밀번호가 일치하지 않습니다")
    return False

if not check_password():
    st.stop()
```

**반드시 지킬 것**

- `hmac.compare_digest` 사용 (`==` 금지 — 타이밍 공격 방어)
- 입력받은 비밀번호를 `session_state`에 저장하지 않는다 (인증 플래그만)
- 비밀번호는 `st.secrets`에만 둔다. 저장소에 절대 커밋하지 않는다
- 20자 이상 무작위 문자열 사용
- 세션당 실패 5회 시 잠금

**한계 (정직하게 인지할 것)**

이건 암호화가 아니라 "문 잠금"이다. 앱 URL은 공개이고 서버는 계속 떠 있다.
진짜 목적은 **API 키 남용으로 인한 과금 방지**이며, 그 목적에는 충분하다.

### 2.8 부가 표시와 오류 처리

- 메시지별 입·출력 토큰, 누적 예상 비용(USD), 응답 지연 시간, 사용 모델 배지
- 오류 처리 (세션 2에서 `client.py`가 아래 예외로 구분해 올린다 —
  `RateLimited` / `ServiceUnavailable` / `InvalidApiKey` / `RequestRejected` /
  `ResponseBlocked` / `EmptyResponse`):
  - **429 (`RateLimited`)** → 2.3절대로 처리. 스택트레이스 노출 금지.
    `retry_after_s`가 없는 429도 실재하므로(2.10절 실측) "서버가 대기 시간을
    알려주지 않았습니다"로 정상 처리한다
  - **503 (`ServiceUnavailable`)** → 일시적 과부하. 429와 다른 문구로 안내하고
    재시도 버튼을 둔다 (세션 2 실측으로 실제 발생 확인)
  - `finish_reason`이 SAFETY / RECITATION / MAX_TOKENS → 사유를 그대로 표시.
    조용히 빈 응답을 내보내지 않는다
  - MAX_TOKENS로 잘린 경우 → "출력 한도로 잘렸습니다. '계속'이라고 입력하면
    이어서 답합니다" 안내 (2.6절 결정 — 출력 토큰 슬라이더는 UI에 없음)
  - **사고만 하다 잘린 빈 응답 (`EmptyResponse`)** → "사고만 하다 답변이
    잘렸습니다"처럼 원인을 구분해 표시한다. 조용히 빈 말풍선을 띄우지 않는다
    (세션 2 A-4 — Gemma에서 실제 관측됨)
  - **잘못된 API 키 (`InvalidApiKey`)** → 원문 JSON을 노출하지 않고
    안내 문구만 표시한다
  - 네트워크 오류 → 사용자 입력을 잃지 않고 재전송 가능하게

### 2.9 파일 첨부 (Gemini 전용)

**모델별 지원 범위 (공식 문서 확인, 2026-08 기준)**

| 입력 | Gemini 3.5 Flash-Lite | Gemma 4 (26B / 31B) |
|---|---|---|
| 이미지 | 지원 | **지원** |
| PDF·문서 | 지원 | 문서에 없음 (미지원으로 간주) |
| 오디오 | 지원 | 문서에 없음 |
| 비디오 | 지원 | 문서에 없음 |

Gemma 4도 `client.files.upload()`를 통한 이미지 입력은 공식 지원된다.
다만 **TPM 16,000과 3,000 토큰 예산 아래에서는 첨부가 실질적으로 무의미하다.**
PDF는 페이지당 약 258토큰, 이미지는 768×768 타일당 약 258토큰 수준이므로
20페이지 문서 하나가 예산의 1.7배를 소모한다.

**결정: 파일 첨부는 Gemini 3.5 Flash-Lite에서만 활성화한다.**
Gemma 선택 시 업로더를 비활성화하고 "이 모델에서는 파일 첨부를 지원하지 않습니다
(분당 토큰 한도 제약)"를 표시한다.

**구현 방식**

- `st.file_uploader`로 받고, 총 요청 크기 20MB 미만이면 인라인 파트로 전송한다.
  그 이상이거나 재사용이 필요하면 Files API(`client.files.upload`)를 쓴다.
  Files API에 올린 파일은 일정 기간 후 만료되므로 대화 중 재전송 실패를 처리할 것.
- **첨부 토큰을 컨텍스트 예산과 한도 추적에 반드시 산입한다.**
  전송 전에 `count_tokens()`로 실제 토큰을 계산해 사용자에게 보여준다
  (예: "첨부 3개 · 약 4,200 토큰 · 이번 요청 총 12,400 토큰").
- 첨부는 해당 턴에만 붙이고 이후 턴에서는 재전송하지 않는다.
  단, 모델이 이전 첨부를 참조해야 하는 경우 맥락이 끊기므로,
  **"첨부는 보낸 턴에서만 유효합니다"를 UI에 명시**한다.
- Markdown 내보내기에는 파일명·크기·토큰 수만 기록한다 (파일 자체는 포함하지 않음).

**v1 범위 판단**

파일 첨부는 업로드 UI, 토큰 산입, 모델별 게이팅, 만료 처리까지 걸쳐 있어
가벼운 기능이 아니다. **세션 6 이후 별도 확장으로 두는 것을 권장한다.**
v1에 넣을 경우 세션 5.5를 신설해 위 항목을 한 세션으로 처리할 것.

### 2.10 웹 검색 그라운딩 (Google Search Grounding) — v1 제외 (세션 2 실측으로 확정)

**무료 티어 API 키에서는 이 기능을 호출할 수 없다.** 세션 2 실측(`docs/api_findings.md`
C절)에서 `google_search` 도구를 붙인 요청이 **모델·모델군과 무관하게 즉시 429**를
받았다. 같은 시각 같은 모델에 도구만 빼면 정상 응답했으므로 모델별 RPM/RPD 소진이
아니라 **검색 그라운딩 전용 할당량이 무료 등급에서 0**인 것으로 판단한다. 이 429에는
`retryDelay`도 없어 "잠시 후 재시도"로 안내할 수도 없다 — 코드로 우회할 방법이 없는
하드 블록이다. 따라서 **v1에서 제외한다.**

아래는 결제를 연결해 재도입할 때를 위한 설계 기록이다. **되살릴 때는 출처 표시
의무(라이선스 조건)를 다시 확인할 것** — 이 부분은 아직 실측되지 않았다.

**당시 설계했던 결정 사항**

| 항목 | 결정 |
|---|---|
| 기본값 | 꺼짐 — 검색어 실행마다 과금되고 지연이 늘어나므로 자동 켜짐은 부적절 |
| 노출 모델 | Gemini 3.5 Flash-Lite만. Gemma는 TPM이 좁아 제외
(세션 2 확인: Gemma도 도구 자체는 거부하지 않지만 실제 검색 여부는 미확인 — C-4) |
| 위치 | 컨트롤 바 popover에 토글 하나 추가 (모델이 Gemini일 때만 노출) |
| 대화별/전역 | 대화별로 보관. 새 대화 시작 시 꺼짐으로 초기화 |

**재도입 시 구현 요구사항 (미검증 항목 포함)**

```python
grounding_tool = types.Tool(google_search=types.GoogleSearch())
config = types.GenerateContentConfig(tools=[grounding_tool], ...)
```

- 검색 그라운딩이 사용된 응답에는 **반드시 출처 목록을 함께 표시한다**
  (`grounding_metadata.grounding_chunks`). Google 라이선스가 요구하는 표시 의무이며,
  임의로 생략하면 안 된다 — 재도입 시 최우선으로 재확인할 것
- 검색을 쓰지 않은 턴과의 구분은 간단하다: **세션 2 확인 결과, `grounding_metadata`
  속성은 항상 존재하고 값이 `None`이다.** `grounding_metadata is None`
  하나로 출처 영역 표시 여부를 가르면 된다 (부록 B-13 해소)
- **비용 표시** — 검색은 토큰이 아니라 검색어 실행 횟수로 과금된다
  (Gemini 3 모델은 쿼리 1회당). 어느 응답 필드로 쿼리 횟수를 세는지는
  **미확인 — 그라운딩 응답을 한 번도 받지 못해 확인 불가했다** (부록 B-12, 유료
  전환 후 재측정 필요)
- 검색 결과가 컨텍스트에 포함되어 다음 턴 토큰이 늘어나지만 Gemini TPM 250,000이라
  실질적 문제는 아니다
- 토글이 꺼져 있으면 `tools` 파라미터 자체를 빼서 보낸다

## 5. 검증 항목 (세션 6 통합 시험)

1. 비밀번호 오입력 차단 / 정입력 통과 / 5회 실패 잠금
2. 첫 화면 기본 모델이 Gemini 3.5 Flash-Lite인지
3. 3턴 대화 후 4턴째에서 1턴 내용을 참조하는 질문 → 정확히 답하는지
4. **Gemini → Gemma 전환 → 확인 단계 표시 → 취소 시 드롭다운이 Gemini로 되돌아가는지**
5. **전환 확인에서 Markdown 저장 → 다운로드 후에도 확인 단계가 유지되는지**
6. **전환 확정 → 새 대화 시작, 이전 대화가 사이드바에 남아 있는지**
7. **Gemma 31B ↔ 26B 전환 → 확인 없이 이력 유지되는지**
8. **Gemma에서 연속 전송 → TPM 한도 도달 → 대기 안내 + Gemini 전환 버튼 표시**
9. **Gemini에서 medium 선택 후 Gemma로 전환 → minimal로 되돌아가고 안내가 뜨는지**
10. **Gemma 컨텍스트 예산 슬라이더 조작 → 유지되는 대화 턴 수가 실시간 갱신되고, 11,000 초과 시에만 대기 경고가 붙는지**
11. **입력창 위 대기 예고 초와 실제 대기 시간이 일치하는지**
12. **상태 배지의 표시값이 설정 패널의 실제 값과 일치하는지**
13. 단일 입력이 Gemma TPM을 넘는 경우 → 전송 차단 + 모델 전환 안내
14. 실제 429를 유발(또는 모의)해 추적기가 서버 기준으로 보정되는지
15. 응답이 출력 한도로 잘림 → 잘림 표시 후 "계속" 입력으로 이어지는지
16. 컨텍스트 예산을 낮춤 → 사전 절단 안내 후 적용
17. 대화 도중 응답 모드 변경 → 이력이 유지되고 다음 응답부터 적용되는지
18. Gemini 선택 시 예산 슬라이더가 보이지 않고, Gemma 선택 시 나타나는지
19. 진행 중 대화에서 시스템 인스트럭션 편집 → 초기화 없이 다음 응답에 반영
20. Gemma 선택 시 `thinking_config`가 항상 명시되어 전송되는지 (생략 시 사고 모드로
    빠지는 회귀를 막는 항목 — 세션 2 A-4)
21. Gemma에서 사고 켜기(`high`) 선택 + 낮은 최대 출력 조합 → 빈 응답이 아니라
    "사고만 하다 잘렸습니다" 같은 사유가 표시되는지
22. 503(일시적 과부하)을 유발(또는 모의)해 429와 다른 문구·재시도 버튼이 뜨는지
23. retry_delay가 없는 429(예: 검색 그라운딩류)를 만나도 "서버가 대기 시간을
    알려주지 않았습니다"로 처리되고 죽지 않는지
24. 코드 블록 포함 대화를 md로 내보내기 → 마크다운 뷰어에서 깨지지 않는지
25. 전체 대화 내보내기 → 대화 구분과 frontmatter 정상
26. 대화 10개 생성 → 개별 삭제 1건 + 되돌리기, 일괄 삭제
27. 새로고침 → 대화가 사라지는 것과 사전 경고가 있었는지 확인
28. 잘못된 API 키로 실행 → 원문 JSON 노출 없이 안내 문구만 표시 (스택트레이스 노출 금지)
29. **모델·응답 모드가 사이드바 설정에 있고, 입력창 위 배지는 표시 전용인지**
30. **대화가 하나도 없는 상태에서 모델을 바꿔도 "새 대화"가 목록에 쌓이지 않는지**
31. **대화 목록 제목이 20자 + `…`로 잘리고 작은 글씨로 보이는지. 툴팁에 전체 제목**
32. **휘발성 경고가 사이드바 맨 아래, 내보내기 버튼 바로 위에 있는지**
33. **메시지 복사 버튼 → 코드 블록·목록이 살아 있는 원본 Markdown이 복사되는지**
34. **Gemma 답변이 1,000~1,500토큰 구간에 들어오는지 (2.6.2절 개정 문구 효과)**

## 6. 배포 시 확인 사항

- Cloud secrets는 앱 설정 화면에서 별도 등록 (`secrets.toml` 커밋 금지)
- 12시간 무접속 시 대기 상태 → 깨어나면 **모든 대화가 사라진다**. v1의 설계 결과임
- 메모리 상한 약 2.7GB — 이 앱은 여유롭다

## 부록 B — 실측이 필요한 미확정 사항

세션 2에서 확인하고 계획서를 갱신할 것.

### 문서로 확인 완료 (2026-08-13, 세션 2에서 재확인만)

- Gemma 4는 Gemini API에서 **시스템 인스트럭션, 멀티턴, 함수 호출, Google 검색,
  이미지 입력(Files API)**을 모두 지원한다
- **Gemma 4의 사고 모드는 켜기/끄기만 가능**하다. `thinking_level="high"`가 켜짐,
  `"minimal"`이 꺼짐이며 `medium`은 없다
- Gemini 3.x는 `temperature` / `top_p` / `top_k` / `candidate_count`를 지원하지 않는다
- Gemini 3.5 Flash-Lite의 기본 사고 수준은 `minimal`이다
- **TPM은 "Tokens per minute (input)"으로 공식 문서에 명시 — 입력 토큰만 센다.**
  출력·사고 토큰은 TPM에 포함되지 않는다. **세션 2 실측으로 확정** — 429 오류의
  지표 이름이 `generate_content_free_tier_input_token_count`였고, 출력을
  대량으로 쏟아낸 직후에도 바로 다음 요청이 통과했다 (`docs/api_findings.md` B절).
  1.4·1.5절을 이 기준으로 확정했다
- **사고 토큰은 TPM에 산입되지 않는다.** 사고 토큰 5,729를 포함해 한 창에 16,486
  토큰을 출력해도 통과했다. 다만 `max_output_tokens` 예산은 그대로 차감한다 —
  작은 출력 한도에서 사고만 하다 잘려 빈 응답이 나올 수 있다 (세션 2 A-4)
- **Gemma는 `thinking_config`를 생략하면 사고가 켜진 채로 동작한다.** Gemini의
  "생략 시 minimal"과 다르다. `client.py`는 모든 요청에 이 값을 명시한다
- **Gemma 4의 컨텍스트 윈도우는 262,144, 최대 출력은 32,768로 확정** (문서마다
  256K/1M로 엇갈리던 것 해소). Gemini 3.5 Flash-Lite는 컨텍스트 1,048,576 /
  출력 65,536
- 세 모델의 `thinking_level` 수용값이 계획서 1.2절 표와 정확히 일치함을 확인.
  Gemma에 `medium`을 보내면 400, 메시지는 "지원하지 않는다"지만 실제로는
  `minimal`/`high` 둘 다 정상 수용된다 (메시지 문구가 오해를 부를 뿐 동작은 맞음)
- `count_tokens`·`generate_content_stream`은 세 모델 모두 정상 동작
- **429 응답에 `retryDelay`가 존재하는 경우와 없는 경우가 둘 다 있다.**
  RPM/RPD 초과 시에는 `RetryInfo.retryDelay`("31s" 형식)와 `message` 안의
  초 단위 소수("Please retry in 31.69s.") 둘 다 온다. `quotaId`로 어느 한도인지
  (`...PerMinute...`/`...PerDay...`) 구분 가능하다. **검색 그라운딩의 429에는
  이 필드가 전혀 없다** — 파싱 실패를 정상 경로로 처리해야 한다
- **RPD 리셋 시각은 여전히 미확정.** 태평양 시간 자정이라는 문서 근거는 있지만
  세션 하나로는 실측(하루 이상 관찰 필요)이 불가능했다. 실사용 중 RPD 429가
  나면 `quotaId`와 `retryDelay`를 기록해 확정한다
- **웹 검색 그라운딩은 무료 티어에서 호출 자체가 막혀 있다** (모델 무관 즉시 429,
  `retryDelay` 없음). v1 제외로 확정 (2.10절)
- Gemma도 `google_search` 도구를 400으로 거부하지는 않지만(200 응답),
  `grounding_metadata`가 항상 `None`이라 실제 검색 여부는 확인 불가
- `grounding_metadata`는 검색을 안 쓴 턴에서도 속성 자체는 항상 존재하고
  값이 `None`이다 — `is None` 하나로 출처 영역 표시 여부를 가르면 된다
  (재도입 시에만 해당하는 항목)
- 토큰 추정 상수 실측: 한국어 **1.63~1.70**자/토큰, 영어 **3.63**자/토큰.
  이에 따라 2.2절 상수를 **한국어 1.6 / 영어 3.5**로 확정했다 (둘 다 실측보다
  토큰을 조금 많게 세는 안전한 방향이다 — 초안의 1.5 / 4.0 중 영어 4.0은
  토큰을 과소 추정해 위험했다). 세 모델의 토크나이저 결과는
  사실상 동일해 Gemini로 센 토큰 수를 Gemma 예산 판정에 그대로 써도 된다
- 가격 정보는 `models.get()`/`models.list()` 어디서도 조회되지 않는다.
  `price_in/out_per_mtok`는 공개 가격표를 보고 수동으로 채워야 한다

### 아직 열려 있는 사항

1. **RPD 정확한 리셋 시각.** 문서 근거(태평양 시간 자정)는 있으나 세션 내
   실측으로는 확인하지 못했다 — 실사용 중 RPD 429를 만나면 `quotaId`와
   `retryDelay`를 기록해 확정한다 (1.5절 표기도 이에 맞춰 단정 대신
   "문서 근거, 세션 내 미검증"으로 표현한다)
2. (파일 첨부를 나중에 구현할 경우) PDF 페이지당·이미지 타일당 실제 토큰 수는
   미확인. `count_tokens`로 그때 확인할 것
3. (검색 그라운딩을 나중에 되살릴 경우) 검색 쿼리 과금이 응답의 어떤 필드로
   확인되는지, `grounding_chunks`/`search_entry_point.rendered_content`의
   실제 형태 — 둘 다 유료 전환 후 재측정 필요
4. **(해소, 세션 4)** Gemma 실제 턴 수를 실사용으로 측정했다 — 턴당 증가
   782~786토큰, 예산 3,000에서 4턴으로 1.5절 추정과 일치했다. 1~4턴 응답이
   모두 768 한도에 걸려 잘렸다. 이 결과와 "TPM이 실제로는 걸리지 않는다"는
   관측을 근거로 기본값을 9,000·1,536으로 상향했다 (1.4·1.5절)
5. **(해소, 세션 5)** 생성 속도 실측 초당 33.1토큰, 출력 1,536이면 약 46초.
   TPM 병목 경계를 12,000 → **약 11,000**으로 정정했다 (1.5절)
6. **(해소, 세션 5)** 기본 인스트럭션이 출력을 1,221 → 435토큰(−64%)으로
   줄이고 1,536 상한 도달을 없앴다. 다만 **과하게 짧아져** 문구를 개정했다
   (2.6.2절) — 목표 범위 방식으로 전환
7. **재개정한 인스트럭션 문구의 효과는 미확인.** 세션 6에서 재측정해 출력이
   **1,000~1,500토큰** 구간에 들어오는지 확인할 것. 이번 개정의 핵심은
   하한 지시("너무 짧게 줄이지 말고")이므로, 그것이 실제로 먹히는지가 관건이다.
   여전히 짧으면 목표 글자 수를 더 올린다
8. **턴 수 표시를 대화 실측 평균으로 계산하는 방식(1.5절)의 체감 정확도 미확인.**
   세션 6 통합 시험에서 표시값과 실제 유지 턴 수를 대조할 것
9. **메시지 복사를 자바스크립트(`navigator.clipboard`)로 구현할 수 있는지 미확인.**
   Streamlit 컴포넌트 iframe에 `clipboard-write` 권한이 있다는 근거로 설계했으나
   실제 동작은 세션 6에서 확인할 것. 실패 시 `st.code` 대안으로 전환 (2.4.1절)

**참고용 (구현에 영향 없음)**

Gemma 4가 `temperature` / `top_p` / `top_k`를 실제로 반영하는지는 세션 2에서
확인하지 않았다. v1에서는 어차피 전달하지 않으므로 구현을 막지 않는다.
